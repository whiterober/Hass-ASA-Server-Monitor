## 进度 68 · 安全回档「刷新后取不到在线状态」根因定位与修复（v6650）

日期：2026-11-13

### 用户口径
「每次刷新后新打开安全回档总是取不到在线状态。找根因」

### 根因（已抓网络时序实证）

页面加载时前端**同毫秒并发**发出两类请求：

```
dt=0ms   /api/arkbackup/paths?hours=0        ← 安全回档数据源（要立刻出结果）
dt=1ms   /api/list_players?server=Isl        ← 真正写 <abbr>_online.json 的（走 RCON）
dt=1ms   /api/list_players?server=Sco  ...Val/Bob/Los/Gen（11 个全在 1ms 内）
```

断链四步：
1. `list_players` 走 **RCON**，每服 1~8 秒后才写 `X_online.json`
2. `paths` 同毫秒开始算，读到的是**上一轮**快照
3. `ark_backup.read_online()` 只采信 `age <= ONLINE_TTL_DEFAULT(300s)` 的快照，
   `player_paths_payload` 条件为 `if _ro.get('ok') and _ro.get('fresh', True)` ⇒
   **过期就整批放弃校正** ⇒ `_onl_eos` 空 ⇒ 所有角色判离线
4. 后端 `PS_PATHS_TTL = 30` + 前端 `LB_ARKBK.pathsAt` 30s TTL ⇒
   一旦拿到「全离线」，**最长 60 秒不会自愈**

**现场实证**：修复前后端 `/api/arkbackup/paths` 返回
`Isl onlineAge=899 · Sco onlineAge=900` —— 刷新页面时快照已 **15 分钟**旧，远超 300s。

### 修复（方案 A：后端加时段标记 + 前端一次性补拉）

后端 `ark_backup.player_paths_payload()`：
- `servers[]` 新增 `onlineOk` / `onlineAge` / `onlineStale`
- `onlineStale = (onlineAge is None) or (onlineAge > ONLINE_TTL_DEFAULT)`

前端 `app_core.js`：
- `LB_ARKBK` 新增 `onlineRetry`
- `lbArkBkOpen()` 每次打开重置 `onlineRetry = 0`
- `lbArkBkTraceLoad()` 成功分支：`servers[].onlineStale` 为真且未补拉过 ⇒ **6 秒后强清 TTL 重拉一次**
  （6 秒 ≈ RCON 批量刷新 11 服快照的实测耗时 3 秒 + 余量；只补一次，避免死循环）

### 补充（v6651）：补拉为什么第一次仍无效 —— 第二层根因「后端 30s 缓存」

v6650 上线后实测：`onlineRetry` 确实变成 1（补拉触发），但 `players` 仍全离线。
读回 `LB_ARKBK.paths.cache` 得到关键证据：

```json
{"hit": true, "ageMs": 7947}
```

⇒ 补拉（6 秒后）**命中了后端 `PS_PATHS_CACHE` 里 7.9 秒前那份旧结果**，
`PS_PATHS_TTL = 30` 秒，所以「补拉」等于把同一份 stale 数据又拿了一遍。

同时发现第二个时间误差：服务器上 `X_online.json` 的 `ts` 全部落在 `23:53:23~24`，
而页面加载约 `23:53:05` ⇒ **11 服 RCON 批量刷新快照实测需约 18 秒**，6 秒的补拉时机太早。
