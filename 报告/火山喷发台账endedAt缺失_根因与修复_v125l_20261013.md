# 火山喷发台账 endedAt 长期缺失：根因与 v125l 修复

> **交付对象**：前端（Hass ASA Server Monitor）
> **日期**：2026-10-13
> **涉及图**：创世（Gen，RCON 32329）。仙境（Rag）另有游戏自带的结束戳，**不受此问题影响**
> **修复版本**：v125l　`md5 = 80c5c7a644f105fd73b6c4bb2585f42b`　（2,020,352 B，2026-10-13 17:31 构建，编译 0 错误）

---

## 0. 一句话结论

创世图火山台账里 **多数喷发记录的 `endedAt` 都是 `null`**，这不是"偶尔丢一次"，而是**插件把结束判据挂在了错误的标志上**（一直等 `AnyEventActive` 下降，而创世实际给出的结束信号是 `WarmUpActive` 下降）⇒ **8 次喷发里只有 2 次拿到了结束时刻（75% 缺失）**。

v125l 已修正。部署到 Gen 后，**从下一轮自然喷发开始**，`endedAt` / `durSec` 会首次出现真实值。

---

## 1. 现象（前端侧表现）

| 位置 | 修复前的表现 |
|---|---|
| `volcanoHistory.lastEvent.endedAt` | **8 次喷发中 6 次为 `null`**（75% 缺失；另 2 次有值）|
| `volcanoHistory.lastEvent.durSec` | 同上，缺失 75% |
| `volcanoHistory.lastEvent.running` | 缺失的条目恒为 `1`（看上去“永远在喷”）|
| `volcanoHistory.recent[]` | 多数 `kind="begin"` 条目的 `endedAt` / `durSec` 为 `null` |

⇒ 前端**大部分时候算不出喷发时长**，也**无法判定喷发是否已结束**。

---

## 2. 根因

### 2.1 主因：结束判据用错了标志

插件原逻辑：

```cpp
// 旧：只认 AnyEventActive 的下降沿
if (!a && g_vol_p.pending_seq > 0) { VolCloseOpenBegin(-1.0, wts); }
```

但读实服台账 `volcano_history_Gen.tsv`（34 行，10-13 17:27 采集）发现两条硬事实：

| 观察 | 实测值 | 含义 |
|---|---|---|
| `begin` 总数 | **8**（seq 341/346/349/352/357/360/363/367）| — |
| **已闭合**（`endsAt != -1`）| **2**（`R 341` dur **348.9 s**、`R 352` dur **347.3 s**）| 这两轮的 `AnyEventActive` 真的升起并落下了 |
| **未闭合** | **6**（75%）| 这些轮次**从未产生 `activeOff`** |
| `activeOff`（kind 6）/ `activeOn`（kind 5）| **2 次** / **3 次** | 并非不出现，而是**只在部分轮次出现** |

台账原文（节选，列顺序 `R seq kind at endsAt durSec src cls`）：

```
R  362  3  208244937.027  -1  -1  0  Volcanic_Eruption_Hazard_C   warmupOn
R  363  1  208244936.158  -1  -1  1  Volcanic_Eruption_Hazard_C   begin
R  364  5  208245033.339  -1  -1  0  Volcanic_Eruption_Hazard_C   activeOn
R  365  4  208245283.362  -1  -1  0  Volcanic_Eruption_Hazard_C   warmupOff   <-- 本轮真正结束
R  366  3  208246252.956  -1  -1  0  Volcanic_Eruption_Hazard_C   warmupOn
R  367  1  208246250.689  -1  -1  1  Volcanic_Eruption_Hazard_C   begin
R  368  4  208246347.421  -1  -1  0  Volcanic_Eruption_Hazard_C   warmupOff   <-- 本轮真正结束
R  369  3  208246997.158  -1  -1  0  Volcanic_Eruption_Hazard_C   warmupOn
```

⇒ **`begin` 之后的 `warmupOff` 才是每次都出现的结束信号**；旧插件只在少数轮次等到了 `activeOff`，其余轮次**一直等不到**。

### 2.2 第二层（叠加）：重启落在喷发中间

插件台账的"进行中"状态是内存态。若服务器恰好在"喷发进行中"重启，重启后不再补写"结束"边。
（这一层已在 v125k/v125l 的恢复逻辑里处理，但**它不是主因** —— 即使不重启，那 75% 的轮次也照样拿不到 `endedAt`。）

| # | 修改 | 效果 |
|---|---|---|
| 1 | 创世分支：`WarmUpActive` 下降（`warmupOff`）**也触发闭合** | `endedAt` / `durSec` 首次落真实值，`running` 转 0 |

## 4. 前端字段口径

`volcanoHistory` 结构与 `weatherHistory` 同形态（32 条滚动窗口）：

| 字段 | 语义 | 修复前 | 部署 v125l 后 |
|---|---|---|---|
| `endedAt` | 喷发结束时刻；`null` = 未结束或未知 | 恒 `null` | 下一轮喷发起为真实值 |
| `durSec` | 喷发时长（秒） | 恒 `null` | 同上有值 |
| `running` | 1 = 尚在进行 | 恒 `1` | 结束后转 `0` |
| `at` / `atSource` | 事件时刻 + 来源 | `atSource="gameStamp"`（创世 = 游戏 `TimeLastEvent`）；边沿类事件为 `"observedWindow"`（插件观测，1 Hz 采样） | 不变 |
| `count` / `beginCount` | 累计事件数 / 累计喷发次数（落盘，重启不清零） | — | 不变 |
| `seenAt` / `prevSeenAt` | 本次 / 上次调用的 worldTime | — | 不变 |

---

## 5. 三条硬限制（前端必须知道）

1. **接口不暴露 `src`**：JSON 的 `atSource` 只有 `"gameStamp"` / `"observedWindow"` 两种取值，
   而插件内部还有一个 `src=2`（= **重启后推算出来的结束时刻**，取重启前后两次采样的**中点**）**在 JSON 里没有独立字段**。
   ⇒ 前端**无法区分**"真实观测到的结束"与"重启后推算的结束"。
   *如需区分，建议插件后续补一个 `endedAtSource` 字段（小改动，本次未做）。*

2. **历史 `endsAt = -1` 的行不可回溯**：那些数值**从未落盘过**（不是接口没给）⇒ 台账里已存在的旧行**永远**是 `null`，做统计时请**按 `endedAt != null` 过滤**。（注意：**并非全部** `begin` 都是 `-1` —— 8 条里有 2 条本来就有值，dur ≈ 348 s）

3. **`durSec` 在修复前不要用"当前时间 − at"代替**：`at` 可能来自很久以前（如重启后），
   `now - at` 会得到数小时甚至数天的荒谬值。

## 6. 建议的前端兜底逻辑

```
if (lastEvent.endedAt === null && lastEvent.running === 1) {
    显示「进行中 / 结束时刻未知」          // 不要渲染负倒计时
} else if (lastEvent.endedAt !== null) {
    显示「时长 durSec 秒」                // 真实值，可直接用
}
```

判"是否已结束"的顺序建议：
1. 优先看 `endedAt` 是否有值（v125l 后可靠）
2. 兼容旧数据：`recent[]` 中若某 `begin` 之后出现了 `kind="warmupOff"`，可视为本轮已结束
3. **不要**仅凭 `hooks.events` 或 `count` 变化推断结束
