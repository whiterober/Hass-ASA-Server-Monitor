# WorldProbe 本轮改动通告（v122b12 → v122b16）

- 日期：2026-10-07
- 范围：`TransferIdentityFixAPI` 的 WorldProbe **只读**命令
- 状态：**Sco 已部署验证通过**；其余图待推 dll + 重启
- 配套文档：同目录 `WorldProbe_全服事件对接文档_20261006.md`（§30.9 ~ §30.11 为本轮细节）

## 0. 一句话
本轮是**性能优化 + 修掉 1 个老 bug**：判据数据的**语义与数值完全不变**（已逐字段对拍证明），
但有 **2 处需要前端配合的行为变化**（见第 1 节）。

## 1. 必须配合的两处行为变化

### 1.1 `actor`：对象名兜底改为 `byname=1` 显式开启
- 之前：`filter=` 先比类名，不中再比**对象名**（对每个 actor 逐个取名字，单次约 172 ms）
- 现在：默认只比类名；要按对象名/实例名选实例，必须显式加 `byname=1`（单次约 2 ms）

```diff
- TransferIdentityFix.WorldProbe actor filter=ElectricalStormPointNorthWest
+ TransferIdentityFix.WorldProbe actor filter=ElectricalStormPointNorthWest byname=1
```

- 影响范围：仅"用对象名（含 `UAID_...` 后缀）当 filter"的调用；**只按类名过滤的调用不受影响**
- 示例：`actor filter=UDS_SE_Weather props=1 fields=CurrWeatherType` 这类写法**无需改动**

### 1.2 `weather slim=1` 的两个诊断计数恒为 0
- `probedProperties` / `matched` 在 `slim=1` 下**恒为 0**（该次 738 项属性遍历已不再执行）
- 判据字段（`weatherState` / `wxSemantics` / `electricalStorm.regionPoints` / `matinee[]` …）**完全不变**
- 需要真实计数时：用 `weather`（不带 `slim`）

## 2. 已修的老 bug：非 Extinction 图的 `meteor`
- 之前：`meteor` 在非灭绝图返回的 JSON **没有闭合的 `}`**（自 v117 起就存在），任何严格 `JSON.parse` 都会抛错
- 现在：返回完整 JSON，例如 `{"ok":true,"sub":"meteor",...,"supported":0,"error":"no WeatherSystem actor exposes bMeteorFXActive (Ext-only field)",...}`
- 前端若为此写过 try/catch 或整条跳过，可以改为按 `supported` 字段正常判断

## 3. 新增可选字段（想用才用，不读不影响）

### 3.1 `cache{}` 缓存自诊断
| 字段 | 含义 |
|------|------|
| `cached` / `ageMs` | 本次是否走响应缓存、缓存体年龄（ms）。默认 TTL 已由 3 s 降到 **1 s**（更实时） |
| `bypass` / `bypasses` | 本次是否 `fresh=1`/`rescan=1` 强制重扫、累计强制次数 |
| `workUs` / `lastMissUs` / `savedEstUs` | 插件内部实际耗时（µs）/ 最近一次全扫描成本 / 累计估算节省 |
| `ptrActors` / `ptrBuilds` / `ptrHits` / `ptrAgeSec` | actor 索引规模 / 重建次数 / 复用次数 / 索引年龄（秒） |
| `clsBuilds` / `clsHits` | 类属性表构建 / 复用次数 |
| `key` | 归一化缓存键（`fresh`/`rescan` 已剥离） |

> 注：`fresh=1` 现在**也会返回 `cache{}`**（`bypass:1`），并且刷新结果写进**归一化键**——
> 紧随其后的普通调用会直接命中刚刷新的数据。

### 3.2 不要用"墙钟耗时"判断缓存是否生效
RCON 往返本身固定约 1.1~1.5 s，与插件做了多少活无关；要看收益请读 `cache.workUs`。

## 4. 建议后端顺手做的优化
- `WP_ZONES_TTL_MS`（当前 60 s）可以降到 **3 s**：插件侧单次只需 0.5~3 ms，秒级轮询完全承受得住。

## ⚠️ 重要补记：v122b17 修复「`slim=1` 下 `weatherState` 变空」

### 问题（v122b14 ~ v122b16 期间存在，已确认并修复）
- 现象：用 **`weather slim=1`**（前端轮询用的模式）时，`weatherState` 会**变空**：
  - Sco：`weatherState = null`（整个语义块丢失）
  - Ext：只剩 1 个字段、`semFieldsFound=1`，且 `family` 被误标为 `uds`（应为 `ext_gen`）
  - 不带 `slim` 的 `weather` 调用不受影响（Sco 38 键、Ext 30 键，均正常）
- 根因：`weatherState` 的数据（`sem_val` / `sem_sz` / `sem_bad` / `weatherName`）
  原本是「属性全量 dump」过程的**副产品**；v122b14 为省 200 ms 在 `slim=1` 下跳过了那次 dump，
  于是语义数据没有来源。
- **v122b17 修法**：`slim=1` 时改为从**已缓存的类属性表**直接读取这些语义键
  （同样的名字、同样的按宽度取值规则：8 字节 double、4 字节 float（`DayNumber` 例外按 int）、
  1 字节 byte、`CurrSequenceSettings` 取字符串天气名）⇒ `weatherState` 恢复，且仍是**亚毫秒级**。

### 请注意
1. **以 v122b17 为准**：v122b14~b16 期间前端若发现 `weatherState` 为空/不全，那不是数据源问题，
   是这版回归，v122b17 已修。
2. `wxSystems[].currentWeather` 在 **Ext 上仍为 `null`**，这与本回归**无关**（历史行为）：
   Ext 的 `CurrentWeather` 是**整数枚举**（不是 FName），FName 读取必然失败。
   **Ext/灭绝系请改用**：`wxSemantics.extWeather.currentName`（实测 `WeatherPreset_EXT_Cloudy`）
   ＋ `wxSemantics.extWeather.currentId`，或用 `wxSemantics.presetTable.entries[].{id,name}` 自行映射；
   UDS 图（Sco/Isl/Cen…）继续用 `weatherState.weatherName`。
3. 本文档第 1.2 节「`slim=1` 下 `probedProperties`/`matched` 恒为 0」仍然成立（只影响这两个诊断计数）。

## 📌 补记二：对前端 v4410 / v4411 修复的核对（2026-10-07 15:0x，实测数据）

### 1. 该回归的影响面**比 `family` 更大**（同一根因）
v122b14~b16 的 `slim=1` 下，`weatherState` 不是"只错 family"，而是**大量字段整体缺失**（实测）：

| 图 | slim 下 `weatherState` 键数 | 缺失字段数 | 缺失示例 |
|----|--------------------------:|----------:|----------|
| Sco | **null（整块为空）** | 38 | 全部 |
| Isl / Cen | 7 | 24 | `currWeatherType` / `transitionProgress` / `windStrength` / `rainVolume` / `fogStrength` / `baseSummerTemperature` … |
| Ext | 7 | **23** | `currentWeatherId` / `windStrength` / `fogStrength` / `temperatureOffset` / `inTransition` / `secondsUntilChange` / `transitionElapsed|Begin|End` / `heatWaveActive` / `weatherTimerEnabled` … |

⇒ 若 v4411 之后卡片能渲染但**温度/风/雾/倒计时等数值为空**，属同一根因，**v122b17 一到即自动恢复**（前端无需再改）。
`slim=0` 一直是正确的（38/31/30 键），所以"用非 slim 对照"是有效方法 —— 与前端所做一致。

### 2. v4411 的替换规则：**当前安全，但依赖运气，建议加一道 Abe 保险**
规则「报 `uds` 但有 `wxSystems` ⇒ 当 `ext_gen`」的实测前提核对：

| 图 | `wxSystems` 条数 | `family`（slim 现状） | 规则是否触发 |
|----|-----------------|----------------------|-------------|
| Sco / Isl / Cen（UDS） | **0** | uds | 不触发 ✓ |
| Ext / Ast / Rag / Val / Los / Gen | ≥1（如 Ext 1 条 `BP_EXT_WeatherSystem_C`） | 误报 `uds` | 触发 ✓（正是想要的） |
| **Abe（畸变）** | **4 条 `BP_AB_WeatherSystem_C`** | `ab`（兜底恰好捡到 18 个语义键） | **不触发** ✓ |

⚠️ **注意**：Abe 有 4 条 `wxSystems`，所以"有 wxSystems 就当 ext_gen"这条规则**对 Abe 是有风险的**——
它今天不触发只是因为 Abe 的 `family` 恰好读出 `ab`；而 Abe 的 `family` 同样来自那条被破坏的路径，
一旦兜底捡到别的对象，Abe 就可能报 `uds` 并被这条规则误判为 `ext_gen`。
建议：给规则加一条 Abe 保险（例如同时要求 `weatherState` 缺少 Abe 的 4 个温度键，或直接排除 4 条 `BP_AB_*` 的情况）。
**v122b17 之后**：slim 下 `family` 恢复正确（Ext/Ast/Rag/Val/Los/Gen=`ext_gen`、Abe=`ab`、UDS=`uds`），
该规则自然全程不触发，可作为无害的兜底保留或后续删除。

### 3. `extWeather.currentName`（v4410）**仍然需要**
`wxSystems[].currentWeather` 在 Ext 为 `null` 属历史行为（Ext 的 `CurrentWeather` 是**整数枚举**、不是 FName），
**v122b17 不会改变这一点** ⇒ Ext/灭绝系的天气名继续用
`wxSemantics.extWeather.currentName`（实测 `WeatherPreset_EXT_Cloudy`）+ `currentId`，或 `presetTable` 自映射。✓ 做法正确。
