# 聚落按服增量重建 + 构建耗时优化方案

> 版本基线：`dino-import.html` `LB_VERSION = 'v20260909-935'`
> 日期：2026-09-09
> 范围：`lbBuildSettlements` / `lbEnsureSettlements` / `lbSettlePosFingerprint` 耗时优化（前端 dino-import，CF 部署）

---

## 1. 问题定义

### 1.1 现象
- 服务器数据变化（任一服设施/生物变更）→ 全量重建聚落，实测约 **80s**，期间页面主线程冻结。
- 用户已感知：`lbSettleBuildShow` 预估提示「数据量 2 万条全服约 80s」（v934 注释自证）。

### 1.2 根因（已确认）
| # | 环节 | 现状 | 问题 |
|---|------|------|------|
| 1 | **指纹粒度** | `lbEnsureSettlements` 用 `lbSettlePosFingerprint(data.recs)` 算**全服汇总一个**指纹（L4104） | 任一服容器位置变 → 指纹变 → 全量重建 |
| 2 | **重建粒度** | `lbBuildSettlements(data)` 遍历全部 10 服，每服跑完整管线（DBSCAN + 床消费 + 命名 + 索引） | 未变服也白跑 DBSCAN |
| 3 | **函数规模** | `lbBuildSettlements` 约 530 行整体函数，无 `onlyAbbr` 参数 | 无法只重建变化服 |

### 1.3 关键事实（代码勘察结论）
- 5 个产出结构**全部按服务器前缀命名空间隔离**：
  - `byServer[abbr]`、`byDinoKey[abbr+'_'+k]`、`byContainer[abbr+'_'+cid]`、`byGeneDevice[abbr+'_'+key]`、`byBed[abbr+'_'+bedKey]`
- 即：**单服重建后只需增删该服前缀的键，不需要动其他服的键** → 索引"跨服引用"复杂度关卡比预期低。
- 每服内部流程（以当前 L3530-3873 为准）：
  1. `recs.filter(r.server===abbr)` → 容器聚合（cid/x/y/z/tribeId/count/imps/impEos/keys）
  2. 排除无坐标容器（posCtn）
  3. 按 `tribeId` 分组 → 组内 **DBSCAN**（`lbDbscan`，空间网格 O(n)）
  4. 床消费唯一化 + 大簇拆分 + 候选排序 + 聚落成立
  5. 离散兜底 + 离散吸收（ABSORB_EPS=20000）
  6. 床纳入中心 + 命名设施最近归属 + 冠名（§8 反查）
  7. 基因设备归属（`data.geneDevices[abbr]`）→ `byGeneDevice`
  8. 床归属 → `byBed`；设施唯一归属 → `s.facilityList`
  9. `byDinoKey` / `byContainer` 建立
  10. `byServer[abbr] = {settlements, scattered}`
- 注意：`structsByTribe`（床/命名/设施数据源）在函数顶部按 **tribeId**（非 server）一次性预分组；部落 ID 跨服可能重复，现有逻辑即按 tribeId 全量匹配——**按服重建时必须保持同一语义**（见 §5 风险）。

### 1.4 现有优化（v935，勿破坏）
- `lbSettlePosFingerprint` + `_prevSettles`：容器**结构**未变（仅球/内容变）→ 复用结构 + `lbRefreshSettleStats` 秒级刷统计。
- 局限：**结构一变就退回全量 80s**，无法区分"哪几服变了"。
- 本方案是 v935 的**升级版**：把"全服一个指纹"细化成"每服一个指纹 + 只重建变化服"。

## 2. 收益预估

| 场景 | 现状 | 目标 | 依据 |
|------|------|------|------|
| 单服设施变（其余 9 服未变） | ~80s 全量 | **变化服构建 + 索引线性增删**（预计 10-20s） | 病态服 DBSCAN Isl ~19.7s / Abe ~15.5s 是大头 |
| 多服同时变（K 服） | ~80s | 变化 K 服构建 + 复用其余 (10-K) 服 | 收益随 K 递减 |
| 结构未变（仅球内容变） | 秒级（v935 已支持） | 秒级（保持） | 不变 |
| 首次加载 / 算法升级 | ~80s | ~80s（无旧结构可复用，不可避免） | 全量仍存在 |

> ⚠️ 收益数字需以 **Phase 0 探针实测**为准——若 80s 大头不在 DBSCAN 而在线性索引/聚合，则按服跳过收益有限，需回到"索引也要按服增量"（复杂度关卡 2 全开）。

---

## 3. 方案对比

### 方案 A（推荐 · 低风险先行）：跳过未变服 DBSCAN
**思路**：指纹拆到每服；未变服**整体复用旧 `byServer[abbr]` + 旧索引前缀条目**；只对变化服跑完整构建；4 个全局索引**仍整表线性重建**（或按前缀删除+写入）。
- ✅ 不动索引结构（关卡 2 关闭）
- ✅ 复用 v935 已有指纹/复用框架，改动集中在 `lbEnsureSettlements` + 拆分出 `lbBuildSettlementsServer`
- ⚠️ 若索引段本身占时明显（线性 2 万条 ×几处遍历），重建整表仍有固定成本——但通常远低于 DBSCAN

### 方案 B（高收益 · 高风险）：完整按服增量（含索引按服增删）
**思路**：A 之上，索引也只重建变化服前缀（复用旧对象引用 + 删除旧服键 + 写入新键）。
- ✅ 收益最大
- ⚠️ 需处理旧索引键清理、引用共享后的意外变异、`_fpByServer` 持久化版本管理
- ⚠️ 改动面大，回归风险高（多个消费方读这些索引）

### 方案 C：纯测量先行（必做，独立于 A/B）
先用打点确认每服/每段耗时，再决定 A 还是 B。

> **推荐路径**：C（探针）→ A（先落地，验证一致性）→ 若索引仍是瓶颈再评估 B。

## 4. 分阶段实施步骤

### Phase 0：耗时探针（先测量，约 1 次构建）
**目的**：确认 80s 里 DBSCAN vs 聚合 vs 索引 vs 床/命名各占多少；确认病态服清单。

1. `lbBuildSettlements` 内加细粒度打点（复用 `LB._bd`）：
   - `bs:srv:<abbr>:dbscan:in` / `:out`（tribe 分组 DBSCAN 段）
   - `bs:srv:<abbr>:bed`（床消费+中心+命名段）
   - `bs:srv:<abbr>:idx`（byGeneDevice/byBed/facility/byDinoKey/byContainer 段）
   - 每服结束打 `bs:srvEnd:<abbr>`
2. 触发一次全量重建 → 读 `LB._bootDiag.marks`（内存数组，构建完成后可 console 导出）或 `localStorage dino_pfdiag`。
3. 产出表：每服总时长、DBSCAN 占比、索引占比。
4. **决策门**：DBSCAN 若占大头（预期）→ 走方案 A；否则评估索引优化。
5. 打点代码保留（v920 已同款模式，低成本诊断资产），或临时注入后移除。

### Phase 1：按服指纹拆分（低风险，前置）
1. 新增 `lbSettlePosFingerprintServer(recs, abbr)`：只对该服 recs 计算指纹（复用现有 FNV 逻辑，加 server 过滤）。
2. 构建结果上记录 `_fpByServer = {abbr: fp}`（替代/兼容现有 `_fp` 全局字段）。
3. `lbEnsureSettlements` 逻辑改为：
   - 无旧结构 → 全量构建（`_fpByServer` 记录）
   - 有旧结构 → 逐服比对指纹，得 `changed[]` / `unchanged[]`
4. 兼容：旧缓存结构无 `_fpByServer` → 视为全变（重建一次后回写）。

### Phase 2：按服增量重建（方案 A 主体）
1. **抽取单服构建函数** `lbBuildSettlementsServer(data, abbr, oldSv)`：
   - 把 L3530-3873 的每服循环体原样搬出（**零逻辑改动**，只改缩进/变量作用域），返回 `{ settlements, scattered, idx:{byGeneDevice,byBed,byDinoKey,byContainer} 增量 }`。
   - `structsByTribe` 预分组保留在顶层（供单服构建用），一次 `data.structures` 线性扫描。
2. `lbEnsureSettlements` 增量分支：
   ```
   changed 为空 → 复用旧结构 + lbRefreshSettleStats（现 v935 路径）
   changed 非空 →
     新 byServer = {}；未变服 from 旧 _settlements.byServer[abbr]（引用）
     changed 服 → lbBuildSettlementsServer(...)
     4 索引：方案A=整表重扫（从 data.recs 逐服重建全部前缀）
            方案B=旧对象为基底，删 changed 服前缀键 + 写新键
   ```
3. 更新 `data._settlements` + `_settleVer` + `lbCacheSet` 持久化（含 `_fpByServer`）。
4. 蛋缓存并入（L4149-4160 现有逻辑）在增量路径同样前置。

### Phase 3：版本管理 & 回归验证
1. `LB_SETTLE_VER` +1（结构/算法变强制重建）。
2. 一致性验证（见 §6）。

## 5. 风险与边界

| # | 风险 | 说明 | 缓解 |
|---|------|------|------|
| R1 | **tribeId 跨服重复**：`structsByTribe`/床消费/命名按 tribeId 匹配，未过滤 server | 单服重建时若床/命名设施实际来自其他服的同号部落，可能归属不同 | 单服构建与全量构建**跑同一代码路径**（`lbBuildSettlementsServer` 即原循环体），语义天然一致；增量只影响"未变服复用旧结果"——只要旧结果来自同语义全量/单服构建即等价 |
| R2 | **未变服复用引用 → 后续被变异** | `lbRefreshSettleStats` 会替换 `sv.settlements` 数组、`lbCacheSet` 持久化 | 复用的是值语义结果对象；任何对复用的 `byServer[abbr]` 的写操作需改为"整体替换数组"，不原地 mutate（现有 `lbRefreshSettleStats` 已整体 map 替换，安全） |
| R3 | **旧缓存缺 `_fpByServer`** | 首轮增量无从比对 | 缺字段 → 全变一次，回写后收敛 |
| R4 | **fingerprint 与结构段不同步** | 指纹只覆盖容器位置/坐标/tribeId，未覆盖 structures（床/墓碑名）本身 | 现状全量指纹同样只覆盖 recs；床变化会经 facility rec 进容器体系（v821 已统一），故指纹可代表结构。增量分支应与 v935 同一信任级别（已在线上验证）。若后续发现结构-only 变化漏重建，再在指纹加 structures 维度 |
| R5 | **主线程冻结 UI** | 增量后仍可能数秒冻结（变化服 DBSCAN） | `lbSettleBuildShow` 已有；增量时估算按变化服数据量显示 |
| R6 | **多入口并发** | `lbSilentRefresh` / `lbReloadIncremental` / `lbEnsureSettlements` 时序 | `LB._prevSettles` 生命周期已管理（L8263/8302 赋值、null 清理）；增量改造保持同一模式 |
| R7 | **530 行函数抽取引入回归** | 纯搬移出错（变量提升/闭包/死代码） | 抽取阶段零逻辑改动 + `py`/`node --check` 类语法校验 + 全量/增量双跑一致性对比（§6） |

## 6. 验证方案

1. **一致性（核心）**：同一份 `data` 下，全量重建结果 vs 增量重建（全部服视为 changed）结果做**深比较**：
   - `byServer` 各服 settlements 的 `id/tribeId/center/containers.length/name/owners` 全等
   - 4 索引键集合全等、值全等（JSON.stringify 对比，忽略顺序）
2. **增量正确性**：构造"仅 Isl 一个容器坐标偏移" → 增量后：
   - 其他 9 服 `byServer` / 索引前缀键 **内容零变化**（与改动前逐键对比）
   - Isl 相关键正确更新
   - `scattered` 计数、`_fpByServer` 更新
3. **耗时**：增量路径 console.time 对比全量（预期 80s → 10-20s）。
4. **功能冒烟**：聚落列表/详情/归属/追踪/设施列表 UI 正常；刷新一次（silent/incremental）后结构仍一致。
5. **部署后浏览器验证**：CF 部署 → 页面加载 → 无 JS 错误 → 触发一次单服数据变更刷新 → 观察 spinner 时长 + 结果正确。
