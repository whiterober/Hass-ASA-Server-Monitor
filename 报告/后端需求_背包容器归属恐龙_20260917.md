# 后端需求：恐龙背包容器 → 所属恐龙 的关联字段

> 提出日期：2026-09-17
> 前端文件：`dino-import.html`（当前 v20260917-3311）
> 提出原因：装备榜「鞍」条目配生物卡需要，前端侧已无解，卡在数据缺字段

---

## 1. 背景（为什么需要这个字段）

装备榜里有一类鞍，放在**恐龙的背包容器**里（例：`DinoTamedInventoryComponent_Argent_C_2146405256`，阿根廷鹫的背包）。

需求是：这类鞍点开后，除了鞍卡，还要显示**装着它的那只生物的卡片**。

但当前数据无法把「背包容器」关联到「恐龙本体」⇒ 前端拿不到"哪只恐龙"，卡片生不出来。

---

## 2. 现状实测（证据）

### 2.1 该鞍在物品数据里的记录（`Isl_item.json.gz`）

```json
{
  "class": "PrimalItemArmor_ArgentavisSaddle_C_2146404743",
  "containerClass": "DinoTamedInventoryComponent_Argent_C_2146405256",
  "containerId": "9adef6ad06fabc42822b3a2cdc17bb12",
  "containerTribe": 1621369181,
  "containerTribeName": "北境游骑兵",
  "x": -273338.38, "y": -259525.14
}
```

### 2.2 关键结论：三类数据之间缺一座「桥」（实测）

**先澄清一个容易混淆的点：球能关联，鞍不能，差别在于「位置信息记在哪边」。**

| 对象 | 位置信息在哪 | 能否反查 |
|---|---|---|
| **球内生物** | 生物记录**自己带** `containerId`（"我在谁那儿"） | ✅ 能（角色背包 107 条、低温冰箱 7057 条、恐龙背包 1 条，实测都能对上） |
| **恐龙背包里的物品（鞍）** | 只存在于**物品记录**里（"我在容器 X 里"） | ❌ 缺一半 |

物品侧给出的容器 GUID = `9adef6ad06fabc42822b3a2cdc17bb12`，据此反查：

| 检查 | 结果 |
|---|---|
| cryo 中 `containerId` = 该 GUID 的记录 | **0 条** |
| 原因 | 这只鹰**未装球（活体）** ⇒ 活体恐龙**不进 cryo** |
| 活体恐龙在 `tamed` 里？ | 在，但 `tamed` **不含任何容器字段** ⇒ 反查断链 |

**三数据集的实际覆盖面（Isl 实测）**

| 数据 | 覆盖 | 带容器信息？ |
|---|---|---|
| `cryo`（球内生物） | 装球的生物 | ✅ 带 `containerClass` + `containerId` |
| `tamed`（活体/放出） | 活体恐龙 | ❌ 只有 `dinoId1/2` + 坐标，**无容器字段** |
| `item`（按容器扫物品） | 所有有物品的容器 | ✅ 带 `containerClass` + `containerId`，但**不知容器主人是谁** |

**规模（说明这不是个例）**

- `item` 中「恐龙背包容器」= **127 个 / 2526 件物品**
- 而 `cryo` 中「容器为恐龙背包」的记录 = **仅 1 条**
- ⇒ **绝大多数活体恐龙的背包内容，当前无法关联到它的主人**

**另外注意**：背包容器的尾号（如 `2146405256`）是**背包组件自身的实例号**，与恐龙实例号（cryo 的 `dinoInstanceId`）**不是同一套编号** —— 实测用它在 cryo / tamed 里搜索均为 0 命中，因此不能拿它当关联键。


---

## 3. 需求

### 3.1 【必须】恐龙背包容器补「主人」标识

在**物品数据**中，凡 `containerClass` 以 `DinoTamedInventoryComponent_` 开头的记录，在其物品项上补两个整数字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ownerDinoId1` | int | 所属恐龙的 `dinoId1` |
| `ownerDinoId2` | int | 所属恐龙的 `dinoId2` |

> 若 DLL 侧取 `dinoId` 不便，**替代方案**：补 `ownerDinoInstanceId`（int，所属恐龙的 Actor 实例号）—— 前端可用它与 cryo 的 `dinoInstanceId` 匹配（覆盖率 86%，仅空球缺）。

**期望输出示例**（在现有字段基础上新增两个 key）：

```json
{
  "class": "PrimalItemArmor_ArgentavisSaddle_C_2146404743",
  "containerClass": "DinoTamedInventoryComponent_Argent_C_2146405256",
  "containerId": "9adef6ad06fabc42822b3a2cdc17bb12",
  "ownerDinoId1": 326976865,
  "ownerDinoId2": 176449817
}
```

（`ownerDinoId1/2` 的示例值仅为格式示意，实际由 DLL 从背包组件反查其 owner actor 得出）

### 3.2 【建议】tamed 数据补实例号

`Isl_tamed.json` 的每条 dino 补：

| 字段 | 类型 | 说明 |
|---|---|---|
| `dinoInstanceId` | int | 恐龙 Actor 实例号（与 cryo 侧同名字段对齐） |

好处：前端可统一按「实例号」关联 **球内 / 放出 / 活体背包** 三种形态，不再依赖两套编号。

---

## 4. 验收标准

1. 任取一个 `DinoTamedInventoryComponent_*` 对应的物品记录，其 `ownerDinoId1` / `ownerDinoId2` 能在该服 `tamed`（或 `cryo`）数据里找到**同一对** `dinoId1/dinoId2`；
2. 该恐龙记录能被前端 `lbDinoHTML()` 正常渲染成卡片（字段齐全即可）；
3. 若采用替代方案，则 `ownerDinoInstanceId` 必须能在 cryo 的 `dinoInstanceId` 中找到（空球除外）。

---

## 5. 前端侧现状（无需改动即可受益）

前端已具备：

- 按 `dinoId1/dinoId2` 关联并渲染生物卡的能力（`lbDinoHTML(rec)`，与选种/繁育栏同源渲染器）
- 装备榜鞍条目已挂 `_dinoRec` 占位链路（放出鞍 / 球内鞍已可用）
- 为「库存实物鞍」预留的配对索引（`_dinoBySaddle`，按 `server + containerId + 鞍基名` 匹配）

⇒ 后端补上 `ownerDinoId1/2` 后，前端只需在该索引里追加一条「按 ownerDinoId 匹配」的分支即可，改动量极小。

---

## 6. 附：为什么不能靠坐标/名字兜底

- **坐标**：背包容器坐标 = 恐龙所在地（会随恐龙移动变化），且同位置可能多只恐龙 ⇒ 不可靠
- **鞍名 + 物种**：一只鹰可能带多把同款鞍/多只同类鹰 ⇒ 会错配
- ⇒ 只有 DLL 能给出**精确的 owner 关系**，因此必须由后端补字段
