## 二、🔴 P0 — 线上已失效

### P0-1　`pwa/sw.js` 语法错误 → Service Worker 更新永久失败（旧版仍在跑）　✅ 已修复

**现象**

```
node --check pwa/sw.js
→ SyntaxError: missing ) after argument list   (sw.js:103)
```

**证据链**

| 项 | 值 |
|---|---|
| 本地 `pwa/sw.js` md5 | `bb3418d6ef9247392820921f5b108fb4` |
| 线上 `/sw.js` md5 | `bb3418d6ef9247392820921f5b108fb4`（**完全一致**） |
| 线上 `/sw.js` 大小 | 11,785 B，HTTP 200 |
| 前端注册处 | `dino-import.html` L3720 `navigator.serviceWorker.register('/sw.js').catch(function(){})` ← 错误被静默吞掉 |

**根因（已定位）**

中文注释在某次编辑中编码损坏（UTF-8 文本被按 GBK 处理后再存为 UTF-8，乱码特征命中 134 处），损坏时**吞掉了换行符**，导致 **8 处代码被并进上一行的 `//` 注释**（每处对应一个被 `?` 替换掉的多字节字符）：

| 行 | 被注释吞掉的代码 | 后果 |
|---|---|---|
| L8 | `var SHELL = 'dino-import-shell-' + VER;` | `SHELL` 未定义 → 所有缓存操作失效 |
| L12 | `var RETRY_HTML = '<!doctype html>…'` | 断网兜底页未定义 |
| L47 | `if (!hasDoc) return null;` | 旧壳清理的保护判断缺失 |
| L65 | `if (req.mode === 'navigate') return;` | 导航请求拦截判断失效 |
| L69 | `if (url.pathname === '/' \|\| url.pathname === '/index.html') {` | **`{` 缺失 → 花括号失配 → 全文解析失败** |
| L71 | `var to = setTimeout(function () { … }, 30000);` | 文档请求无超时保护 |
| L87 | `return caches.keys().then(function (keys) {` | 兜底链路断裂 |
| L113 | `var ac = new AbortController();` / `e.respondWith(` | 静态资源分支无超时控制 |

**影响面（2026-11-05 浏览器实测更正）**

> 初版结论写的是「SW 完全没注册」，**实测推翻了这一条**：老客户端仍在正常用缓存。准确表述如下。

| 场景 | 实际表现 |
|---|---|
| **已装过旧版 SW 的设备**（如当前浏览器） | SW **正常工作中**，但版本**永久冻结在 2026-10-30**；11-02 之后所有 SW 侧改动一律不生效 |
| **新设备 / 清过站点数据 / 换浏览器** | `register()` 取到含语法错误的脚本 → 解析失败 → **完全没有 Service Worker**（无离线、无资源缓存、无兜底页） |
| 页面文档本身 | 新旧 SW 的 `fetch` 都不接管 `navigate` 请求，**页面始终走网络** → 所以「页面能打开」从来不是 SW 的功劳 |

**机制说明**：按 Service Worker 规范，新脚本解析失败时**不会卸载已激活的旧 worker**，只会在每次更新检查时静默失败 → 形成「看起来一切正常」的版本冻结。前端 L3720 的 `.catch(function(){})` 又吞掉了注册错误，因此无任何报错痕迹。

## 十一、Wiki 小标题「渲染后再隐藏」根因与修复（2026-11-05）

### 11.1 现象

Wiki 浮窗「概览」页在**数据加载过程中**，小标题不断显影闪现（每约 2 秒一次）。

### 11.2 根因链（三层叠加）

```
① 触发层：进度轮询每 2 秒无条件重绘
   app_ui.js  timer = setInterval(..., 2000)          ← LB_WIKI 进度轮询
   app_ui.js  lbWikiTakePartial(key, p);              ← 返回值被丢弃
   app_ui.js  try { lbWikiRender(); } catch(e1){}     ← 无条件调用

② 渲染层：全量重建，隐藏状态丢失
   app_ui.js  body.innerHTML = h;                     ← .tc-h 的 display:none / data-lf-hide 随旧节点销毁

③ 修正层：隐藏动作晚 60ms 才执行
   app_ui.js  MutationObserver → setTimeout(..., 60) → lbWikiLayoutFix()
              ↑ 这 60ms 内新标题是「可见」的
```

⇒ 每 2 秒：重建（标题露出）→ 60ms 后被隐藏 → 再等 2 秒重演 = **不断显影闪现**。

### 11.3 为什么只有部分标题在闪

| 标题 | 隐藏方式 | 是否闪 |
|---|---|---|
| 「概述」 | CSS `#lbWikiOverlay .tc-h:has(+ .tc-intro){display:none!important}` → 渲染瞬间即隐藏 | ❌ |
| 「基础属性」「技巧」 | 下一个兄弟是 `<table>` / `<p>`，CSS 管不到；只能靠 JS 60ms 后隐藏 | ✅ **就是它们在闪** |
| 概览底部 AI 模块标题 | 同上（JS 后置隐藏） | ✅ |

### 11.4 全项目 `.tc-h` 复检（共 63 处）

| 面板 | 处数 | 有轮询 | 实际表现 |
|---|---:|---|---|
| 物种 Wiki 概览 | `renderOverview` 3（本次已全部不再生成） | 是，每 2s | 曾**不断闪** |
| 物种 Wiki 驯服/繁殖/采集/技能/经验/技巧/生成/装备 | 6+5+2+1+6+2+1+2 = 25 | 是（同一 `lbWikiRender`） | 加载期切过去会同样闪 |
| 物品 Wiki | `lbWikiItemRender` 8 + `lbWikiFbBodyHtml` 5 | 否（全项目只有 1 个 `setInterval`） | 每次重绘闪 1 次 |
| 资讯浮窗 | `lbNewsRender` 3 | 刷新/自动更新驱动 | 每次刷新闪 1 次 |
| 地图 Wiki | `lbWikiStats/Promo/FigHtml` 各 1 | 否 | 每次重绘闪 1 次 |

**结论：同一 bug 类，共 63 处；只有物种 Wiki 因为 2 秒轮询而「不断」闪，其余是「每次重绘闪一下」。**

### 11.5 修复内容（v6106）

| # | 改动 | 依据 |
|---|---|---|
| A1 | `renderOverview()` **不再生成**「概述」「基础属性」「技巧」3 个 `.tc-h` | 用户口径「既然最终不显示，为啥要渲染后再隐藏」——三者判据静态可知、恒不可见 |
| A2 | `lbWikiLayoutWatch` / `lbWikiItemLayoutWatch` / `lbSheetLayoutWatch` 改为在 **MutationObserver 回调里同步**执行修正（微任务阶段，浏览器绘制之前），再保留 60ms 校正兜住异步内容 | 让「隐藏」发生在首帧之前，其余 60 处标题也不再有可见窗口 |
| B | 进度轮询用 `lbWikiTakePartial()` 返回值 + 进度数字是否变化**门控重绘** | 数据没变就不再重建，加载期重绘从约 40 次降到「数据真变化」的次数 |
| D | `_deploy_cf.py` 新增 `== 0/3 同步 sw.js VER ==`，打包前把 `sw.js` 的 `VER` 自动改成当前 `LB_VERSION` | 消灭 P0-2 的人工同步步骤，防再次回退 |
