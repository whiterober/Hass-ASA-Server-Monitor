# 需求稿：UDS「下次变天倒计时」——组件属性读取能力（承接《UDS 变天机制调研》）

> **状态：✅ 已交付（v125f）：组件读取能力已上线；但「秒级精确倒计时」实测不可得，改为「半精确」区间口径**
- **提出方**：前端（dino-import）
- **日期**：2026-10-12
- **承接**：插件侧《UDS 天气「变天机制」调研结论》——已确认「剩余 = `CurrentTimerLength` − `ChangeTimer`」原理可得，堵点仅剩「插件读不到组件属性」。

## 请求（按优先级）

### ① 新增「遍历 Actor 组件读属性」能力（解锁型）

- 现状：`WorldProbe` 的 `actor` 子命令只遍历 Actor 自身的 `FProperty`；`Random_Weather_Variation` 是 **ActorComponent**，其属性在子对象上（这正是此前探针全 ABSENT 的原因——组件不在 Actor 属性表里）。
- 建议实现（供参考）：`actor->GetComponents()` → 遍历组件 → `TFieldIterator<FProperty>` → 复用现有 `TifEmitPayloadProbe` 解码；可加语法如 `actor filter=X comps=1`（或 `comp=Random_Weather_Variation`）选择性输出。
- 目标字段：**`CurrentTimerLength`**（本轮总长）、**`Change Timer`**（已走）、`Running Timer`（是否在跑）、`TargetRandomWeatherType`（抽中的目标天气）。

### ② 输出格式：写入与 BP 族同名的 `weatherState.secondsUntilChange`

- 建议把 **`剩余 = CurrentTimerLength − ChangeTimer`** 直接放进 **`weatherState.secondsUntilChange`**（UDS 三图）——前端已有存在性分支（灰条 `lbWxSegProg` / 回退链 `lbWxSucTxt || lbWxEstTxt`），**字段一出现自动从「≈估算」切到「精确 + 本地外推」——前端零改动**。
- 平行字段可选：`timerLength` / `timerElapsed`（原始值，供前端显示"本轮总长 X 分钟"）。
- 语义对齐：`secondsUntilChange`=「距下次变天秒数」；若需要新标志位（如 `timerSource:"rwv"`）随意，前端按存在性判断。

### ③ 顺带对账（一条命令的事）

- **`Weather Type Change Minimum / Maximum Interval` 的实读/默认值**——我们自检期实测 Sco 变天间隔 **37.6s ~ 48min** 超宽，想核对短端（37s 是否在区间内）。
- **`WeatherWeights_Day/Night` 的实值（8 项）**——前景：前端可做"白天可能出现：X%"（若与既有 wprobs 同源则直接复用）。

## 验证方法（供自测）

- 连采样：2 分钟内拉 3~5 次 weather——`剩余` 应逐次**线性递减**（速率 ≈1s/s）；到 0 前后 5 秒内应观察到新变天条目（可与自检记录交叉验证）。
- 对账锚点：任意时刻读一次 `CurrentTimerLength − ChangeTimer`，与前端显示的倒计时比对（应一致到秒）。

## 验收标准

1. Sco/Isl/Cen 浮窗「距变天」显示**精确倒计时**（秒级连续、本地外推不跳变）；
2. 倒计时归零与自检记录的变天时刻误差 ≤5 秒；
3. 前端零改动兼容（存在性判断；无字段时回落估算——现状可用、非阻塞）。

## 备注

- 不急于一时：现有"最近间隔中位数"估算已能凑合；本需求是把「≈」升级为「精确」的最后一层。
- 若组件读取能力顺带能读 `WeatherWeights_Day/Night`，一并输出则更佳（概率展示素材）。

## 交付结论（2026-10-13 更新）

**状态：✅ 已交付（插件 v125 起；v125f 为定稿版）。结论：组件读取能力已具备，但 UDS 三图得到的是「半精确」区间倒计时 —— 原因见下。**

### 一、需求 ①「遍历 Actor 组件读属性」（解锁型）✅ 已实现

- 语法：`WorldProbe actor filter=<类> comps=1 [slim=1]`（`comps=` 亦可传组件数）
- 输出：`components{prop,num,stride,ptrOff,valid,found,count,list[{i,class,objectName,scalarProps}],timer{...}}`
- 另有 `compsClass=<关键词>` 过滤；`compDiag[]`（**非 slim 时**输出布局诊断，含 `slots[]` 原始槽位）

### 二、需求 ②「秒级精确倒计时」❌ 实测不可得

需求前提是「UDS 的 `Random_Weather_Variation` 组件提供 `CurrentTimerLength / ChangeTimer`」。**实测三图均无该组件**：

| 图 | 天气 Actor | 组件数 | 存在 RWV | 组件清单 |
|---|---|---|---|---|
| Sco | `UDS_SE_Weather_C` | 4 | ❌ | Root / SpatializedAudioRoot / Rainbow / Player Occlusion |
| Cen | `UDS_TheCenter_Weather_C` | 4 | ❌ | AppData |
| Isl | `UDS_Island_C` | 30 槽（首 208 B 全 0） | ❌ | 无 RWV；另有 `Weather_Override_Volume_C` × 3 |

- ⇒ **native 计时器路径在三图都不存在**，`weatherState.secondsUntilChange` 无法由组件给出精确值
- 另：云图帧（`CurWeaTimeFrame` / `CloudTime`）实测在**强制变天与自然变天期间恒为 0** ⇒ 帧推算路线同样否证

### 三、实际交付：`wxClock` 表推算（半精确区间）

```
idx      = 经 presetTable 解析出的下标（table.index）
周期     = WeatherEventLengths[idx] + 过渡（默认 120 s）
已走     = worldTime − 锚点
剩余下限 = 周期 − 已走（负则按周期回绕）
剩余上限 = 剩余下限 + 160 s（载入等待，单样本外推）
```

| 误差项 | 量级 | 说明 |
|---|---|---|
| 锚点 | 0 s（`gameStamp`）/ ≤ 5 s（`observedWindow`） | 与 `lastBad` 同源 |
| 周期 | 0 s | 均为游戏配置值 |
| **载入等待** | **0 ~ +160 s** | `waitingForNewWeather` 恒为 1；**唯一大项** |

### 四、需求 ③ 对账项 ✅

- `WeatherEventLengths` 已随 `wxClock.table.lengths` 输出（Sco 8 项）
- **`idxMapped` 语义（前端必读）**：`2` = 经映射表解析、`1` = id 直接当下标、`0` = 启发式；
  **真正的下标是 `table.index` —— 请用 `index` 去查 `lengths`，勿用 `idxMapped`**
- ⚠️ Isl 的 `presetTable`（6 项）多于 `WeatherEventLengths`（5 项）⇒ 触发边界检查回落（`idxMapped=1`）；
  Isl 的 `lengths` 全为 300，当前无差异

### 五、三图实测（2026-10-13）

| 图 | index / idxMapped | lengths[index] | eventSeconds | remain 区间 |
|---|---|---|---|---|
| Sco | 5 / 2 | 1200 | 1200 | 267.73 – 427.73 |
| Cen | 4 / 2 | 800 | 800 | 920.00 – 1080.00 |
| Isl | 0 / 1 | 300 | 300 | 179.54 – 339.54 |

（Sco：`1052.27 + 267.73 = 1320 = 1200 + 120`，自洽）

### 六、前端对接建议

- 展示为「距变天 ≈ X ~ Y 分钟」（区间），或取 `remainLowerSec` 做本地外推（秒级连续，但**不是精确值**）
- 字段：`wxClock.basis`（`table` = 表推算 / `native` = 组件计时器 / `none` = 不可用）、
  `wxClock.table.{index,idxMapped,eventSeconds,transitionSeconds,anchorAt,anchorAgeSec,anchorSource,remainLowerSec,remainUpperSec,loadWaitSec,lengths}`、
  `wxClock.note`
- **原验收标准第 1 条「秒级精确倒计时」不成立**，请按区间展示以免误导
- 部署：✅ Isl / Sco / Cen；⏳ 其余 7 图仍旧版（**无 `wxClock` 字段**，需前端做存在性兼容）

## 最终结论（2026-10-13）：UDS 倒计时 **不可得**（推翻上节「半精确」口径）

> ⚠️ **请前端停止使用 `wxClock` 的倒计时字段。**

### 一、上节「半精确」口径为何被推翻

上节的 `配置时长 + 过渡 − 已走`（上界再加 160 s）建立在「`WeatherEventLengths` 就是本段时长」这一前提上。
后续实测（Sco 的 `recent[]` 环，**只取锚点干净的 `autoScan` 段**，锚点精度恒 5 s）证明该前提**不成立**：

| 天气 | 配置时长 | 实测周期（s） | 偏差 |
|---|---|---|---|
| Sand_Dust_Storm | 425 | 83.0 / 611.5 / 648.6 | −342 ~ +224 |
| Rain_SE | 750 | 336.0 / 477.9 / 850.7 / 864.9 | −414 ~ +115 |
| Foggy_SE | 650 | 386.4 / 797.3 / 922.6 | −264 ~ +273 |
| HeatWave_SE | 700 | 972.0 | +272 |
| ElectricalStorm | 425 | 260.8 | −164 |

⇒ **同一天气的实测周期波动达 2.4~7.8 倍**，且与配置值无稳定关系。
（更早统计中曾出现 53,059 s 的段 —— 那是 `atSource=observedWindow` 的窗口污染，已剔除：其窗口宽达 7,466 s。）

### 二、根本原因：游戏侧没有可读的真实剩余时间

| 尝试过的来源 | 实测结果 |
|---|---|
| `Random_Weather_Variation` 组件（DevKit 确认这才是"随机变天"的驱动者） | Sco/Cen/Isl 的**天气 actor 与天空 actor 上均不存在**（`probe` 逐项实测：字段全 ABSENT） |
| native 倒计时（`WeatherSystem.TimerNextWeather`） | UDS 三图 `wxSystems` 为空、`activeWxIdx = -1` |
| 计时器字段族（`CurrentTimerLength` / `ChangeWeatherTimer` / `Running Timer` / `TargetRandomWeatherType` / `Total Changes`） | 逐项 `probe` 实测：**全部 ABSENT** |
| 云图帧推算（`CurWeaTimeFrame` / `CloudTime` / `CloudStopedTime`） | 强制变天与自然变天期间**恒为 0** |
| `changeStartTime` | **恒 0**（本需求稿给出的"判死"判据命中） |
| 历史统计外推 | 分布跨度达**小时级**，无预报价值 |

原因层层叠加：

1. 驱动用的是蓝图内部 Timer（`SetTimer` + `FTimerHandle`）—— **UE 不提供从句柄查询剩余时间**的能力
2. 承载计时器字段的 `UDS_and_UDW_State` / `RandomWeatherVariation_State` 结构，**Sco 的 `UDS_SE_Weather` 不含**
3. 时长本身是 `[Min Interval, Max Interval]` **区间随机抽取** ⇒ 即便读到，也只是"本轮总长"，预告不了下一轮

### 三、前端请改用这些字段（全部已存在且可靠）

| 用途 | 字段 | 精度 |
|---|---|---|
| 当前天气 | `weatherState.weatherName` / `currWeatherType` / `currentWeatherId` | — |
| **已持续时长** | `weatherHistory.lastChange.agoSec`（= `worldTime − at`） | **≤5 s**（`atSource=autoScan`） |
| 是否正在变天 | `weatherState.transitionProgress`（0→1）/ `transitionLength` | — |
| 最近变天链 | `weatherHistory.recent[]`（`at` / `endedAt` / `atSource`） | ≤5 s |
| 天气概率 | `wxSemantics.weightsDay` / `weightsNight` | 见注 |

> 注：`weightsDay` 在 **Sco** 上的垃圾值（第 5 槽 `2.72e+23`）**已于 v125i 修复**。
> ⭐ **前端请改读 `asDouble`**：这三个数组的真实类型是 `TArray<double>`（8 字节元素），旧的 `asFloat` 是按 4 字节半读（已移除）。实测正确值：
> - `weightsDay` = `[0.0, 0.1, 0.35, 0.15, 0.7, 0.5, 0.25, 0.15]`
> - `weightsNight` = `[0.5, 0.2, 0.1, 0.2, 0.0, 0.5, 0.2, 0.0]`
> - `eventLengths` = `[800, 425, 750, 650, 700, 1200, 425, 750]`（与 `wxClock.table.lengths` 逐位一致）
> 其余 7 图该字段为 `null`（无此数据）。

### 四、插件侧处置

- `wxClock` 字段**保留**（不破坏已有前端代码），但 `wxClock.note` 已改为**明确警示**文案（自 **v125h** 起生效）：

  > "NOT usable as a countdown: UDS exposes no readable change timer (no Random_Weather_Variation component, no native countdown, cloud frames stay 0, every timer field ABSENT) and the real period is drawn at random from a wide interval. Use weatherHistory.lastChange.agoSec (elapsed, <=5 s accurate) plus weatherState.transitionProgress instead."

- **请勿**再依赖 `wxClock.table.remainLowerSec` / `remainUpperSec` / `loadWaitSec`
- BP 派系图（Abe/Ast/Ext/Gen/Los/Rag/Val）不受影响：它们有 `TimerNextWeather`（绝对时间戳），倒计时**精确**

## 口径修正（2026-10-13）：坏天气「近似可用」、晴天不适用

前节「UDS 倒计时不可得」的表述**过重**，据随后重算与 DevKit 剖析修正如下。

### 一、修正后的口径

| 情况 | 口径 | 误差量级 |
|---|---|---|
| **坏天气**（雨 / 雾 / 沙尘暴 / 热浪 / 电风暴） | ≈ `配置时长 + 过渡 120 s`，**近似可用** | **约 2/3 段落在 ±350 s 内**；其余多为**提前结束** |
| **晴天 / PartlyCloudy** | **不适用**（空闲态，跨度 397 s ~ 数小时） | — |
| 精确秒级倒计时 | 仍**不可得** —— 额外时间来自"新天气云图帧加载等待"，不可预知 | — |

### 二、机制（DevKit 实证）

- 切换的前置条件 = **「新天气的云图帧全部加载完成」**
  蓝图内逐字调试字符串：*"Actually change Weather after all new weather relevant frames loaded"*
- 因此**不是**"当前云图播完就换"（稳态下 `CurWeaTimeFrame` 恒 0）⇒ 时长自然不固定
- **组件计时器确认不存在**：DevKit 提取 Timer 类字段 = 0 条；实服 `probe` 结果亦全 ABSENT
- 沙尘暴另有专用参数（`SandstormDuration` / `SandstormSweepFrameInterval`）

### 三、⚠️ 另一个坑：`recent[]` 的段长不能当天气时长

`recent[]` 的"段"是**名称变化**（含**变体切换**），不等于天气类型持续：

- Cen 实测：`PartlyCloudy_Thin` 段仅 **520.3 / 627.7 s**，而前后都是 `PartlyCloudy`
  ⇒ 同一天气类型内的变体切换被切成独立段
- `recent[].wxId` 恒为 **-1**：`recent[].id`（序列显示名）与 `presetTable`（预设资产名）是**两套命名**

⇒ **请勿用 `recent[]` 相邻 `at` 之差推断天气时长**；若需"已持续"，用 `weatherHistory.lastChange.agoSec`（同口径，且 ≤5 s 精度）。


### 四、⚠️ 过渡时长 120 s 的适用范围（未验证项）

- `wxClock.table.transitionSeconds = 120` 取自天气 actor 的属性 **`WeatherTransitionLength`**
  （Sco / Cen 实测 `property(f64)`；Isl 无该属性 ⇒ 回落 `default120`）
- **该值目前只在晴天（PartlyCloudy）期间被实测过**；极端天气（沙尘暴 / 电风暴等）期间的取值**尚未验证**
- DevKit 证据表明它**设计上按天气可配**，甚至可为"周期的比例"：
  - `RandomWeatherVariation_TransitionSettings.Transition Length`，tooltip 逐字 *"The time it takes to transition to this Weather Type"*
  - 同结构体另有 `Transition Length Is Fraction`
  - `UDS_SE_Weather` 内存在 `K2Node_Event_Transition_Length`（该值由外部推送，非常量）
- ⇒ 请把 `120` 视为**经验值**而非恒定参数
