# 安全回档 · 临时授权监督入口 —— 方案

> 起草：2026-11-15 ｜ 状态：**待确认（未动代码）** ｜ 关联：v6683 回档流程 Session（已上线）
> 修订：2026-11-15 14:45 —— **授权改为全自动**（不再手动指定，直接给「回档主体玩家」）

## 1. 需求

用户口径原文：

> 安全回档，我希望"开始回档流程"，后直接临时给选中玩家（必须是管理者权限）开放 安全回档 的入口；但是浮窗里只显示。风险检查面板 和 任务进度面板；回档流程结束后，入口消失

修订口径：

> 点「开始回档流程」后，不是手动指定，而是**自动**给 选中（当前回档流程的主体玩家）的玩家入口

拆成三条：

| # | 要求 | 关键约束 |
|---|---|---|
| R1 | 点「开始回档流程」时**自动**把入口给本次回档的**主体玩家**（浮窗里选中的角色 `LB_ARKBK.who`），**无需手动指定** | 该玩家**必须是管理者权限**（角色等级 ≥ 2），否则入口对其不显示 |
| R2 | 该玩家打开的浮窗被裁剪，**只保留**「风险检查」+「任务进度」两块 | 其余块（服务器选择 / 回档点列表 / 行程明细 / 执行区）全部不渲染 |
| R3 | 回档流程结束后，入口自动消失 | 不需要人工回收，流程结束即失效 |

已确认口径：

- **受限玩家的操作权限 = 步骤里的按钮全部可点**（用户口径：「步骤里的按钮都算是推进按钮」）——
  含「重新检查」「执行回档」「撤销到上次回档前」「接管」「结束流程」「标记已完成回档流程」。
  **不做任何按钮屏蔽**：他只受**视图裁剪**限制（看不到服务器选择 / 回档点列表 / 行程明细），不受操作限制。
- **授权对象 = 回档主体玩家**，由 `LB_ARKBK.who` 自动提供，不存在"选人"这一步。

## 3. 方案设计

三层，彼此独立可分批上线。

### 3.1 L1 数据层（后端）—— flow 增加 `watchers`

```python
def _arkbk_flow_new(server, point_id, point_ts, user, watchers=None):
    ...
    # 回档主体玩家（start 时由前端自动填 LB_ARKBK.who / whoName）
    'watchers': [{'eosId': '00025A2B9CF14195B9714EDD4EE38AC5', 'name': '板板'}],
    'watchAt': '2026-11-15 14:40:00',
```

改动点：

| # | 内容 |
|---|---|
| 1 | `_arkbk_flow_new()` 增加 `watchers` 可选参数；`_arkbk_flow_norm()` 必须**保留**该字段（否则读回就被丢掉） |
| 2 | `start` 分支解析 `g('watchers')`：前端在 `lbArkBkFlowStart()` 里**自动**填主体玩家（eosId + name），后端原样存 |
| 3 | `GET /api/arkbackup/flow?mine=1`：⚠️ 现有实现 `server` **必填**（空则 400），必须在 `_s_fl` 校验**之前**分流。返回**全部 live 流程**（不按人过滤，见 P4），前端自己比对 `LB.playerEos` |
| 4 | （可选，非主路径）`action=revoke`：主导者主动收回某人；**不提供 `grant`** —— 授权只在 `start` 时自动发生 |

> 🔴 **红线**：`watchers` **只服务前端视图裁剪**，绝不进入 `execute` / `rollback` / `undo` 的任何鉴权分支。
> 后端执行类接口保持现状（`_srvctl_guard` + `_role_level`），被授权者直接 curl 执行必须仍然 403。

> ℹ️ 后端 `_role_level(username)` 只认**账号名**，没有「EOSID → 等级」通道。
> 本方案**不需要**它 —— 「必须是管理者权限」改由被授权者本人登录时的 `lbRoleLevel()` 判定（见 3.2.2），更准也更省。

### 3.2 L2 入口层（前端，**全自动，无授权 UI**）

#### 3.2.1 授权动作：合并进「开始回档流程」

`lbArkBkFlowStart()` 的请求体直接带上主体玩家，**不新增任何选择浮窗、不新增按钮**：

```js
lbArkBkFlowApi('start', {
  pointId: LB_ARKBK.point,
  pointTs: _pt ? lbArkBkFmtTs(_pt.ts) : '',
  // v6742：自动授权给「回档主体玩家」，无需手动指定
  watchers: LB_ARKBK.who ? [{ eosId: LB_ARKBK.who, name: LB_ARKBK.whoName || '' }] : []
});
```

流程条文案（`lbArkBkFlowBarHtml()` 的「我进行中」分支）：

```
你的回档流程进行中 · 目标档 2026-11-15 12:00
   已授权 板板（主体玩家）查看            [结束]
```

| 情况 | 文案 |
|---|---|
| 有 `who` | 已授权 **<名字>**（主体玩家）查看 |
| 无 `who` | 未选主体玩家 ⇒ 本次不授权任何人查看（**不阻断流程**） |

#### 3.2.2 入口派生（被授权者侧）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 新增轻接口 `GET /api/arkbackup/flow?mine=1`，登录后 + 每 60s 拉一次；返回非空 ⇒ 系统管理菜单多一项「回档流程（监督）」 | 一次请求解决，成本最低 |
| B | 前端循环 11 台调 `flow?server=X` | 11 倍请求，否决 |

入口渲染条件（三条全满足）：

1. `mine` 返回里至少一条 `phase ∈ ('active','verifying')`
2. 该流程的 `watchers` 里有 `eosId.toUpperCase() === String(LB.playerEos).toUpperCase()`（**必须统一大写**，见 P5）
3. **`lbRoleLevel() >= 2`** —— 这一条天然完成「必须是管理者权限」的校验：
   被授权者登录时拿到的是**他自己的真实等级**，比后端去查别人等级更准也更省

> 主体玩家若不是管理员 ⇒ 他自己登录后第 3 条不成立 ⇒ 入口不显示。
> 也就是说「必须是管理者权限」这条约束**不需要额外代码**，由身份体系自动落地。

#### 3.2.3 `mine` 轮询策略（自适应降频）

用户口径（2026-11-15）：**只在「曾经收到过至少一条 mine 结果」或「页面空闲」时才高频轮询**。

```js
var LB_ARKBK_MINE = { timer: null, hot: false, last: null };

function lbArkBkMinePollStart() {
  lbArkBkMinePollStop();
  var tick = function () {
    if (document.hidden) { lbArkBkMinePollStart(); return; }   // 页面不可见 ⇒ 不查，直接排下一次
    lbArkBkFlowMine().then(function (j) {
      var items = (j && j.flows) || [];
      LB_ARKBK_MINE.last = items;
      var had = items.length > 0;
      if (had !== LB_ARKBK_MINE.hot) {          // 状态变了才重绘菜单
        LB_ARKBK_MINE.hot = had;
        try { lbMenuRefresh && lbMenuRefresh(); } catch (e) {}
      }
      lbArkBkMinePollStart();                    // 重新排期（间隔按 hot 决定）
    }).catch(function () {
      LB_ARKBK_MINE.hot = false;
      lbArkBkMinePollStart();
    });
  };
  // hot（当前确有别人的流程在跑）⇒ 60s；否则 5 分钟（够发现新授权，又不浪费）
  LB_ARKBK_MINE.timer = setTimeout(tick, LB_ARKBK_MINE.hot ? 60000 : 300000);
}
function lbArkBkMinePollStop() {
  if (LB_ARKBK_MINE.timer) { clearTimeout(LB_ARKBK_MINE.timer); LB_ARKBK_MINE.timer = null; }
}
```

| 状态 | 间隔 | 说明 |
|---|---|---|
| `hot = true`（列表非空，说明有流程在跑） | **60s** | 需要及时感知 `finish` / `abort` 后入口消失 |
| `hot = false`（列表为空） | **5 分钟** | 只为发现"有人新授权给我"，不需要秒级 |
| `document.hidden` | 跳过本次 | 后台标签页不发请求 |

> 好处：稳态下每人每 5 分钟才 1 个轻请求（返回体通常 `{flows: []}`），比固定 60s 省 80% 请求。

**R3 的"入口消失"自动成立**：`finish` / `abort` 后 `phase` 变 `done` / `aborted` ⇒ 不再 live ⇒ `mine` 返回空 ⇒ 入口不渲染；6 小时惰性过期同理。**不需要额外的回收逻辑**。

进入时自动定位（否则风险检查无数据）：

```js
function lbArkBkWatcherOpen(srv, flow) {
  LB_ARKBK.watch = { on:true, srv:srv, point:flow.pointId,
                     by:flow.startedBy, byName:'' };
  LB_ARKBK.srv = srv;
  LB_ARKBK.flow = flow;
  lbArkBkOpen();                     // ⚠️ open 内部会把 point 清空（见下方 P1）
  /* P1：必须**在 open 之后**再锁目标档，否则风险检查没有数据 */
  LB_ARKBK.point = String(flow.pointId || '');
  LB_ARKBK.plan = null;
  LB_ARKBK._flowKey = '';
  lbArkBkRender();
  if (LB_ARKBK.point) lbArkBkPlan();  // 直接跑一次风险检查
  lbArkBkFlowPollStart();             // 30s 轮询沿用
}
```

> ⚠️ **P1（复核发现，原方案有 bug）**：`lbArkBkOpen()` 内部 L9095 有 `LB_ARKBK.point = ''; LB_ARKBK.plan = null;`
> —— 先设 point 再 open 会被抹掉。必须 open 之后设，并且**不要**走 `lbArkBkPickPoint()`
> （它会因 live 流程弹 `lbArkBkFlowGuard` 换档确认），直接调 `lbArkBkPlan()`。

watch 模式下**不屏蔽任何按钮**（用户口径：「步骤里的按钮都算是推进按钮」）：

| 能力 | watch 模式 | 说明 |
|---|---|---|
| 切服务器 / 切档 | 不可用 | ① ② 块不渲染 ⇒ **根本没有入口可点**（不是禁用，是不存在） |
| 重新检查风险 | 可点 | 在 `lbArkBkPlanHtml` 的步骤 tips 里 |
| 执行回档 | 可点 | 同上，属流程推进 |
| 撤销到上次回档前 | 可点 | 同上 |
| 接管 / 结束流程 | 可点 | `lbArkBkFlowBarHtml()` 照常渲染，被授权者看到「接管」 |
| 标记「已完成回档流程」（`lbArkBkFlowFinish`） | 可点 | 步骤 tips 内 |
| 推进 step（start → exec → verify） | 可点 | 同上 |

⇒ **实现上不需要任何 `if (watch) return ''` 判断** —— watch 模式只做视图裁剪（去掉 ①②④ 块），
按钮与流程条沿用现有渲染逻辑原样输出。

> 为什么可以放开：入口本身要求 `lbRoleLevel() >= 2`，**被授权者本来就是管理员**，这些操作他原本就能做；
> 执行类接口的后端鉴权（`_srvctl_guard` + `_role_level`）完全没变 —— 不是"多给了权限"，只是"少跳一次页面"。

### 3.4 轮询键要带上授权变化

```js
var key = [f.id, f.phase, f.step, f.startedBy, f.pointId,
           (f.watchers || []).length].join('|');   // ← 新增
```

否则主导者中途收回授权，被授权者 30s 轮询拿不到重绘信号。

## 4. 风险与兜底

| # | 风险 | 处置 |
|---|---|---|
| 1 | **鉴权被削弱**（最严重） | `watchers` 绝不进入执行类接口鉴权；上线后必须实测「被授权者 curl 执行回档 → 403」 |
| 1b | 被授权者能执行回档 / 撤销 / 接管 / 结束 | **预期行为**（用户口径：步骤按钮都算推进按钮）。他本身就是管理员，原本就有这些权限；后端鉴权一行未改 |
| 2 | 前端等级校验可被绕过 | 一期不做后端复核：入口显示依赖 `lbRoleLevel()`，而执行类接口鉴权本来没变（`_srvctl_guard` + `_role_level`），即使绕过入口也执行不了任何操作 |
| 2b | 主体玩家不是管理员 | 入口对他不显示（`lbRoleLevel() < 2`）；主导者侧无感，属**预期行为**，不额外提示 |
| 2c | 主导者忘了选主体玩家 | `start` 不阻断，只是 `watchers` 为空 ⇒ 本次不授权任何人；流程条明确写出「未选主体玩家」 |
| 3 | `_arkbk_flow_norm` 丢字段 | 改完必须实测「start 带 watchers 后重新 GET，watchers 还在」 |
| 4 | 被授权者看到别人服的数据 | `mine` 只返回 watchers 含本人的流程；watch 模式锁死 `srv`，chips 不渲染 |
| 5 | `mine` 接口失败 | **不显示入口**（宁缺不错），不降级成全量轮询 |
| 6 | 主体玩家离线 | 入口不显示；等他下次上线若流程还在才会出现（接受） |
| 7 | 6 小时过期边界 | 沿用现有惰性过期，watchers 随之失效；到期后 `mine` 返回空即入口消失 |

## 5. 验收清单

| # | 场景 | 通过标准 |
|---|---|---|
| V1 | 主导者在角色 TAB 选中 A（管理员）→ 点「开始回档流程」 | **无需任何授权操作**，A 的系统管理菜单出现「回档流程（监督）」 |
| V1b | 主导者未选主体玩家 → 开始流程 | 流程正常开始；流程条显示「未选主体玩家」；任何人都不出现监督入口 |
| V2 | A 打开浮窗 | 可见：风险检查面板（含全部步骤按钮）+ 任务进度面板 + 流程条；**不可见**：服务器 chips、回档点列表、行程明细 |
| V2b | A 点「执行回档」/「撤销」/「接管」/「结束」 | 与主导者点击效果一致（他本身就是管理员，后端鉴权未变） |
| V3 | A 点「重新检查」 | 正常重新拉风险（有缓存秒回） |
| V4 | 主导者 `finish` | A 的入口 30s 内消失 |
| V5 | 主导者 `abort` / 6 小时过期 | 同上消失 |
| V6 | 未被授权的管理员 B | 看不到入口 |
| V7 | 主体玩家是普通玩家（等级 1） | 他登录后**看不到**入口（`lbRoleLevel() < 2`），且主导者流程不受影响 |
| V8 | **鉴权零变化** | A 直接 `curl` 调执行回档 → 仍 403 |
| V9 | 授权收回 | 主导者 `revoke` 掉 A 后，A 的入口消失 |
| V10 | 多端一致 | 主导者与 A 在两个浏览器，30s 内状态同步 |

## 6. 交付顺序

| 阶段 | 内容 | 风险 | 可独立验证 |
|---|---|---|---|
