## 0. 一句话结论
> ⚠️ **阅读指引**：本文件 **§7.2 / §7.3 已作废**；权威结论见文末 **§9 「更正与最终机制」**。
> 下方第一行为**已作废的旧结论**（仅作记录），第二行起为正确结论。


~~**UDS 的天气切换 = 「按 白天/夜晚 权重表加权随机挑一个天气」→「播放该天气的云图序列，每 N 秒翻一帧」→「播完再挑下一个」。**~~（旧结论，已作废）
**UDS 的天气切换 = `Random_Weather_Variation` 组件排一个「随机时长计时器」→ 到点按季节权重加权随机挑一个天气 → 用 `Transition Length` 过渡 → 再排下一次。**
**计时器时长在 `Weather Type Change Minimum Interval` ~ `Maximum Interval` 之间随机 ⇒ 所以「每次变天都不一样」。**
**「下次变天倒计时」= 读该组件的计时器字段（`Current Timer Length` / `Change Timer`）⇒ 需插件扩展「读组件属性」能力（现有插件只读 actor 属性，故当前读不到）。**

## 3. 变天机制（三层）

### 3.1 选天气 = 白天/夜晚 加权随机 ⭐

在 `UDS_SE_Weather` 上实测存在两份权重表（TMap，各 **8 条目**）：

| 属性（实服实测存在的名字） | 含义 |
|---|---|
| **`WeatherWeights_Day`** | **白天权重表**（每个天气一个权重） |
| **`WeatherWeights_Night`** | **夜晚权重表** |

显示名（DevKit 字符串提取）：`Weather Weights Day` / `Weather Weights Night`
同源配置项（在核心 `Ultra_Dynamic_Weather` 里）：`Weather Type Change Minimum/Maximum Interval`、
`Start With a Random Weather Type`、`Use Random Weather Variation`、`Set Timer to run function again`（**定时器自续**）。

⇒ **选天气用的是"加权随机"，且白天/夜晚权重不同。**

### 3.2 播放 = 云图序列逐帧（不是定时器！）

```
Cloud Time  = Get Game Time in Seconds − Paused Duration      // 云钟：世界时间 − 累计暂停
CurWeaTimeFrame  = Ceil( Cloud Time / CurFrameInterval )      // 当前段已播到第几帧
PrevWeaTimeFrame = Ceil( Cloud Time / PrevFrameInterval )     // 上一段（淡出中）
```
- **每 `CurFrameInterval` 秒自动 +1 ⇒ 翻页无需定时器**（是时间的函数）
- 帧率**每个天气自带**：来自 `S_SE_Cloud_Map_Sequence.Frame Interval`（实测 10 s / 上一段 20 s）
- 触发条件：`AND( PrevWeaTimeFrame != LastPrevWeaTimeFrame , WeatherLerpValue < 1.0 )`

### 3.3 交叉淡出 = 6 帧槽混合

`CurWea{Prev,Cur,Next}FrameTex` + `PrevWea{Prev,Cur,Next}FrameTex`（各 Object + 纹理2D），
配 `CurWeaFrameBlend` / `PrevWeaFrameBlend`，`bTriggerLoadCurWeaNextFrameTex` / `bTriggerLoadPrevWeaNextFrameTex`。

## 6. 前端能做什么 / 不能做什么

| 需求 | 结论 |
|---|---|
| ⚠️ **"下次变天倒计时"** | **需插件扩展** —— 计时器确实存在（组件上的 `Current Timer Length` / `Change Timer`），但**组件属性现有插件读不到**（只读 actor 属性）⇒ 需新增「遍历 Actor 组件并读其属性」；且时长是在区间内**随机**抽取的，故只能读"当前剩余"，无法提前预告准确秒数 |
| ✅ **当前天气名** | 用 §2.1 的枚举表把 `currentWeatherId` 映射成名字 |
| ✅ **变天过渡进度** | `changeStartTime` + `transitionLength`(=120) ⇒「过渡中 45/120 秒」 |
| ✅ **状态** | `waitingForNewWeather` ⇒「云图序列播放中 / 等待新天气载入」 |
| ⭐ **更有价值：变天概率** | 读出 **`WeatherWeights_Day` / `WeatherWeights_Night`** ⇒ 前端可显示「白天可能出现：Cloudy 30% / Rain 20% …」 |
| ✅ 统计式预估 | 插件记录历史变天时刻 ⇒ 给"平均 X 分钟一变天"的经验值 |

## 7. 「变天计时器」的归属（⚠️ 本节 7.2 / 7.3 的结论已于 2026-10-12 晚**作废**，正确结论见 §9）

### 7.1 计时器字段全貌（`UDS_and_UDW_State` 结构体，DevKit 字符串提取）

官方描述：**"Contains the state of things like time and weather, for saving and loading."**

| 字段 | 含义 |
|---|---|
| **`CurrentTimerLength`** | ⭐ **本次计时器长度（= 本轮的变天间隔，秒）** |
| **`Change Weather Timer`**（`ChangeWeatherTimer`） | ⭐ **变天计时器** |
| `TargetRandomWeatherType` | **抽中的目标天气**（enum） |
| `LastRandomWeatherType` | 上一次的天气 |
| `CurrentLerpAlpha` | 过渡进度 |
| `Simulation Date` / `Moon Phase` / `Includes UDW State` | 时间/月亮/含 UDW 状态 |
| `Cloud Coverage` / `Dust` / `Fog` / `Rain` / `Snow` / `Global Material Snow` / `Wetness`（+ 各自 `Old*`） | 天气参数与"上一次"快照 |

**跨资产引用搜索**：`CurrentTimerLength` / `TargetRandomWeatherType` 只出现在
`System\RandomWeatherVariation_State.uasset`、`System\UDS_and_UDW_State.uasset`、
**`Weather_Effects\System\Random_Weather_Variation.uasset`** ⇒ **真正执行"随机变天"的是 `Random_Weather_Variation` 组件**。

### 7.2 ⛔ Sco 上没有这个组件（决赛证据）

实服全图扫描（93,815 actors / 1,301 levels）：

```json
{"sub":"scan","totalActors":93815,"levelCount":1301,"filter":"Weather",
 "returned":1,"classes":[{"class":"UDS_SE_Weather_C","count":1}]}
```

- **Sco 全图只有 `UDS_SE_Weather_C` 一个天气实体**（`distinctClasses: 1`）
- `actor filter=Random_Weather_Variation` / `RandomWeatherVariation` / `Random` / `Weather_Override_Volume`
  ⇒ **全部 matched=0（不存在）**
- 在 `UDS_SE_Weather` 上探测 `CurrentTimerLength` / `ChangeWeatherTimer` / `TargetRandomWeatherType` /
  `CurrentLerpAlpha` / `LastRandomWeatherType` / `SimulationDate` / `MoonPhase` / `IncludesUDWState` / `UDWState`
  ⇒ **全部 ABSENT**（不是它的成员）

### 7.3 ⛔ 本节作废：原结论「Sco 不会自动变天」**方法错误**（用户实测 Sco 正常变天）—— 见 §9 更正

**携带"变天计时器 + 权重随机"的 `Random_Weather_Variation` 组件没有挂在这张图上**，
所以 `UDS_SE_Weather` 只是"待命"——它有权重表、有云图序列播放器，**但没有任何东西来"到点推一个新天气给它"**。

这**完整解释**了全部实测现象：

| 现象 | 解释 |
|---|---|
| `CurrWeatherType` 长期 = 0（晴天） | 没有新天气被推来 |
| **`bWaitForNewWeatherToLoad` 长期 = 1** | 它**在等一个新天气，而那个"新天气"永远不会自己来** |
| 前端读不到任何"下次变天"信息 | 计时器根本不存在于这张图 |
| 长跑观察从未见到 Sco 变天 | 同上 |

**⇒ 除非外部主动推送（管理员/RCon/其他模组），Sco 会一直保持当前天气。**
**⇒ 若要恢复"随机变天"：需在图上挂 `Random_Weather_Variation` 组件并配置权重与间隔区间。**

### 7.4 附带产出：权重表已可读

实服 `WeatherWeights_Day` 解出 **8 个 double 权重**：`0.0 / 0.1 / 0.35 / 0.4 / 0.0667 / …`
（`WeatherWeights_Night` 同理）⇒ **前端可直接做"天气概率"展示**（比倒计时更有价值）。
另实测：`bWaitForNewWeatherToLoad = 1`、`WeatherChangeStartTime = 0`、`SandstormDuration = 480.0`。

### 7.5 插件增强（可选）

新增输出 `weatherWeights{day[],night[]}`（解 TMap）⇒ 前端即可显示"白天可能出现：Cloudy 10% / Rain 35% / …"。

## 8. 方法论沉淀（可复用）

- **`.uasset` 的"名字表"是明文** ⇒ 用 ASCII 字符串提取（`re.findall(rb"[ -~]{4,}")`）就能**读出变量名、函数名、枚举成员、工具提示**，
  等于**半读源码**（本次靠它挖出 `WeatherWeights_Day` / `WeatherTypeChangeMinimumInterval` 等关键名）。
- **DevKit「在蓝图中寻找」(Ctrl+Shift+F) = 全项目搜索**，一次给资产路径 + 命中函数 ⇒ 跨蓝图找人首选。
- **UE「查找结果」只按变量名索引、无 `Set ` 前缀** ⇒ 搜 `Set X` 必 0 命中；搜 `X` 后单击条目即跳转高亮。
- **`probe=` 可穿透 `props=1` 的 400 条上限**做**存在性测试**（返回 null = 不存在）；`probe=` **必须与 `props=1` 同时给**。
- 空格属性名：token 里的 **`+` 会转成空格**（`Weather+Weights+Day` ⇒ "Weather Weights Day"）；
  但 BP 变量真实属性名可能用下划线（`WeatherWeights_Day`）⇒ **两种形式都试**。

## 9. ⭐ 更正与最终机制（2026-10-12 晚 · 用户实测纠正 + DevKit 组件解码）

### 9.1 被推翻的结论与**方法错误**

上一版 §7.3 的结论「**Sco 不会自动变天**」是**错的**（用户实测：Sco 一直在正常变天）。

**错在方法，不在数据**：

| 当时的"证据" | 为什么无效 |
|---|---|
| `scan filter=Weather` → `distinctClasses: 1`（只有 `UDS_SE_Weather_C`） | `scan` / `actor filter=` 只枚举**关卡 Actor**；`Random_Weather_Variation` 是 **ActorComponent**，**永远不会**出现在 Actor 列表里 ⇒ 该证据与"组件是否存在"**无关** |
| `actor filter=Random_Weather_Variation` → `matched=0` | 同上 —— 组件不是 Actor，必然 0 命中（**假阴性**） |
| 在 `UDS_SE_Weather_C` 上探测计时器字段 → 全 ABSENT | 计时器字段属于**组件**（及 `RandomWeatherVariation_State` 结构），**本就不该**出现在 actor 的属性表里（**假阴性**） |

> **⚠️ 教训（通用）**：`scan` / `actor` 的 filter **只认 Actor**。想判断"某个组件是否存在"，用 Actor 扫描是**逻辑上不可能**成功的；必须改用「组件的引用指针（如 `BlueprintCreatedComponents`）」或「组件的类名」去查。
> **✅ 本次的真正判据**：**用户游戏内目视**（Sco 正常变天）—— 比仪器测得的"0 命中"更权威。

### 9.2 变天机制（DevKit `Random_Weather_Variation` 组件字段解码）

驱动者 = **`Weather_Effects\System\Random_Weather_Variation`（ActorComponent）**，成员为：

```
Timer to Select Random Weather     ← 定时器句柄
Start Timer to Select New Weather  ← 排"下一次变天"
Increment Change Timer             ← 每 tick 累加计时器
Running Timer                      ← 计时器是否在跑
Reset Timer                        ← 复位
Current Transition Length          ← 当前过渡时长
Random Float / Random Max Range / Min / Max / Threshold   ← 随机抽取
Filter Probability List            ← 权重过滤
Select New Random Weather Type     ← ★ 到点后：抽下一个天气
Weather Type Probabilities (Spring / Summer / Autumn / Winter)  ← 季节权重（由上游 push）
Total Changes                      ← 累计变天次数
Weather Speed
```

时长与状态的**归属**：

| 字段 | 所在资产 | 含义 |
|---|---|---|
| **`Weather Type Change Minimum Interval`** | `Blueprints\Ultra_Dynamic_Weather.uasset` | **变天间隔下限** |
| **`Weather Type Change Maximum Interval`** | `Blueprints\Ultra_Dynamic_Weather.uasset` | **变天间隔上限** |
| `CurrentTimerLength` | `System\RandomWeatherVariation_State.uasset` | **本轮的计时器长度（秒）** |
| `TargetRandomWeatherType` / `LastRandomWeatherType` / `CurrentLerpAlpha` | 同上 | 目标/上次天气、过渡进度 |
| `Transition Length`（"The time it takes to transition to this Weather Type"）+ `Transition Length Is Fraction` + `RandomWeatherTypesFrom/To` | `System\RandomWeatherVariation_TransitionSettings.uasset` | 过渡时长与起止天气 |
| `RandomWeatherVariation_State` / `UDS_and_UDW_State` | `System\` | 存档/加载用的天气状态快照 |

**⇒ 完整链条**：

```
Random_Weather_Variation（组件）
  ① 取 [Min Interval, Max Interval] → 随机出一个时长 → CurrentTimerLength
  ② Start Timer to Select New Weather（Timer to Select Random Weather）
  ③ Tick: Increment Change Timer → Running Timer 到点
  ④ Select New Random Weather Type：季节权重(Spring/Summer/Autumn/Winter)
       + Random Float / Threshold → Target Random Weather Type
  ⑤ 用 Transition Length 过渡（Current Lerp Alpha 0→1）
  ⑥ Total Changes++，回到 ①
```

**⇒ 因为时长是区间内随机抽取，所以「每次变天都不一样」**（用户实测吻合）。

### 9.3 「下次变天倒计时」到底能不能做

- **计时器客观存在**：`CurrentTimerLength`（本轮总长）与 `Change Timer`（已走时长）
  ⇒ **剩余 ≈ `CurrentTimerLength − ChangeTimer`** ⇒ **原理上可得，不是"天生不可得"**（§7.3 此说法作废）
- **但当前插件读不到**：`WorldProbe` 的 `actor` 子命令只遍历 **Actor 自身的 `FProperty`**；
  组件的属性在**子对象**上 ⇒ 需插件新增能力：
  `actor->GetComponents()` → 遍历组件 → `TFieldIterator<FProperty>` → 复用现有 `TifEmitPayloadProbe` 解码
- **数值本身可先从 DevKit 读默认值**（`Ultra_Dynamic_Weather` 的 Min/Max Interval）

### 9.4 本次新增的实测事实与工具技巧

| 事实 / 技巧 | 内容 |
|---|---|
| **云图帧数** | `Content\ScorchedEarth\...\VolumetricClouds\WeatherTextures\` 下 `PartlyCloudy` / `PartlyCloudy_Thin` / `Rain` / `Fog` / `Heatwave` / `Superheatwave` **各 75 帧**；`ElectricalStorm` / `Sandstorm` 该目录 0 帧（另用一套资产） |

- **计时器类名字提取结果 = 0 条**（Timer / Elapsed / Remaining / Countdown 全无）
  ⇒ 与实服 `probe` 结果一致：**没有组件计时器**
- 沙尘暴专用参数：`SandstormDuration` / `SandstormSweepFrameInterval` / `SweepSlowMediumDuration`
- 抽选函数：**`GetRandomWeatherVaration`**（蓝图内原拼写就是 `Varation`，少一个 i）
- 变体体系：`Has Variation` / `ExistingVariations` / `CurVariationName` / `Loop Variations`
- `WeatherChangeStartTime` 是蓝图变量，但**运行期恒 0**（与本需求稿的"判死"判据吻合）

⇒ **修正模型**：

```
天气时长 ≈ WeatherEventLengths[id]（按 id 映射） + 过渡(120 s) + 帧加载等待（不定）
```

**触发条件是「新天气的云图帧全部加载完成」，不是「当前序列播完」** —— 这解释了为什么同一天气每次时长都不同（加载快慢不同），也解释了此前的"载入等待"观测。

### C. "偏短段"成因（新发现）

- `recent[]` 的"段"= **名称变化**，**不等于**天气类型持续时长
- Cen 实测 `PartlyCloudy_Thin` 段仅 **520.3 / 627.7 s**，而其前后都是 `PartlyCloudy`
  ⇒ **同一天气类型内的"变体切换"被记为新段**，段长被人工切短
- `recent[].wxId` 恒为 **-1** ⇒ `recent[].id` 用的是**序列显示名**（`PartlyCloudy` / `Rain` / `Sandstorm`），
  与 `presetTable` 的**预设资产名**（`Rain_SE` / `Sand_Dust_Storm` / `Clear_Skies_SE`）是**两套命名**，无法自动互映
- 所有超长段（53,059 / 86,182 s）均带 `atSource=observedWindow` ⇒ 属窗口污染，已排除

⇒ **结论：不要用 `recent[]` 的段长推断"天气时长"**（会把一个类型切成多段）。
