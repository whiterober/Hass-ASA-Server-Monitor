# 离线导出「玩家名单」——前端调用说明

> 日期：2026-11-04 ｜ 用途：让前端（或其后端）拿到**最新**的 `players[]` + `tribes{}`，无需人工勾名单
> 产物：`<DinoData>\<服缩写>_players.json.gz`（只含这两段，几十 KB）

---

## 1. 一句话

**两种接法，任选其一：**

| 接法 | 谁执行 | 何时用 |
|---|---|---|
| **A. RCON 命令**（本次新增） | 插件在服务器进程内起导出器 | 想在网页上"点一下立刻刷新" |
| **B. exe 直调 + 静态托管** | 你的后端或 Windows 计划任务 | 只要定时刷新、前端读静态文件即可 |

> 浏览器**不能**直接执行 exe，必须由后端/计划任务代跑。

---

## 2. 接法 A：RCON 命令（推荐）

### 2.1 触发导出

```
TransferIdentityFix.ExportPlayers light
```

| 参数 | 说明 |
|---|---|
| `light` | 只输出 `players[]` + `tribes{}`；**省略则输出全量**（cryopod/structures/facilities…） |
| `ark=<存档路径>` | 指定要解析的存档（`.ark` 或 `.arkrbf`，**路径中空格用 `+`**）；省略则用 `config.json` 的 `auto_parse_ark_path` |
| `abbr=<服缩写>` | 配合 `ark=` 使用，决定 `serverId` 与产物名前缀；省略则用当前地图缩写 |

**立刻返回**（不等导出完成）：

```json
{"ok":true,"light":true,"out":"D:\ARK Server\DinoData\Ext_players.json.gz","cooldownSeconds":60,"msg":""}
```

拒绝时（不是异常，是护栏）：

```json
{"ok":false,"light":true,"out":"","cooldownSeconds":60,"msg":"cooldown: 43s left"}
{"ok":false,"light":true,"out":"","cooldownSeconds":60,"msg":"busy: previous export still running"}
```

### 2.2 查状态 / 判断新鲜度

```
TransferIdentityFix.ExportStatus
```

```json
{"ok":true,"out":"D:\ARK Server\DinoData\Ext_players.json.gz",
 "exists":true,"bytes":48211,"ageSec":12,"running":false,"cooldownLeftSec":48}
```

- `running=true` ⇒ 导出器仍在跑，**不要**再发 `ExportPlayers`（会被 busy 挡）
- `ageSec` = 产物距今秒数；前端建议 **> 900 s 显示"数据偏旧"**
- `cooldownLeftSec > 0` ⇒ 这期间再触发会直接被拒

### 2.3 护栏（重要）

| 护栏 | 行为 |
|---|---|
| **single-flight** | 上一轮没跑完 → 直接 `busy`，**不会**起第二个进程，避免两个进程抢写同一文件 |
| **冷却 60 s** | 冷却内直接 `cooldown`，防止 1 秒轮询变成"解析风暴" |
| **固定文件名** | 每次覆盖同名产物 ⇒ **永不堆积**；写入是 `.tmp → gzip → .gz` 原子替换，读不到半截文件 |

> 建议节奏：**需要时触发 + 状态轮询（5~10 s 一次）**，不要在 `ageSec` 还很小的时候重复触发。

---

### 2.4 指定存档：历史档 / `.arkrbf`

省略 `ark=` 时用的是 `config.json → auto_parse_ark_path`（当前线上档）。想解析**别的档**（历史备份、或 `.arkrbf` 自动备份）就追加参数：

```
TransferIdentityFix.ExportPlayers light ark=D:\ARK+Server\Servers\Ast\ShooterGame\Saved\SavedArks\Astraeos_WP\Astraeos_WP_04.11.2026_02.10.56.arkrbf abbr=Ast
```

| 要点 | 说明 |
|---|---|
| 空格写成 `+` | 命令是空格分词，路径里的空格必须写成 `+`（插件会还原成空格） |
| `.ark` / `.arkrbf` 都行 | 两者**同为 SQLite**（`SQLite format 3` 在文件第 0 字节），exe 直接读，无需转换 |
| 建议带上 `abbr=` | 决定 `serverId` 与产物名；不带则用当前地图缩写 |
| **不会覆盖线上产物** | 带 `ark=` 时产物名追加存档名：`Ast_players_Astraeos_WP_04_11_2026_02_10_56.json.gz`（非字母数字字符→`_`，截断 60 字符） |
| 单飞 + 冷却同样生效 | 历史档通常比线上档大，耗时数十秒量级；期间再发会被 `busy` 挡 |

返回（结构不变，`out` 指向历史档产物）：

```json
{"ok":true,"light":true,"out":"D:\\ARK Server\\DinoData\\Ast_players_Astraeos_WP_04_11_2026_02_10_56.json.gz","cooldownSeconds":60,"msg":""}
```

> ⚠️ **`ExportStatus` 只认线上档**：它的 `out` / `exists` / `bytes` / `ageSec` 永远指向 `<abbr>_players.json.gz`。
> 查历史档进度只能用 `running` / `cooldownLeftSec`，产物请直接按上面的 `out` 路径去读。

实测（2026-11-04）：`Ast` 的 `Astraeos_WP_04.11.2026_02.10.56.arkrbf` 解析成功，产物 1,468 B，解出 `players=12` / `tribes=13`。

## 3. 接法 B：exe 直调

```powershell
ark_save_reader.exe "<save.ark>" "<DinoData\Ext_players.json>" Ext light
```

| 位置 | 含义 |
|---|---|
| 1 | 存档路径（`.ark` 或 `.arkrbf`，两者同为 SQLite） |
| 2 | 输出路径（成品实际为 `<该路径>.gz`） |
| 3 | 服缩写（写进 `serverId`，也决定文件名习惯） |
| 4 | 任意值 ⇒ 轻量模式（只出 players/tribes） |

成功标志：退出码 `0`，stderr 出现 `players-only: players=N tribes=M out=…`。

## 4. 产物结构与字段

```json
{
  "serverId": "Ext",
  "arkPath": "D:\ARK Server\...\Extinction_WP.ark",
  "players": [
    {"pid":1234567890,"eosId":"0002…(32hex)","name":"账号名","characterName":"角色名","roles":{"1234567890":"角色名"}}
  ],
  "tribes": {
    "1912594779": {
      "name":"基纽特战队","ownerName":"…","ownerPid":1234567890,"ownerEosId":"0002…",
      "members":[{"name":"…","pid":1234567890,"eosId":"0002…"}],
      "alliances":[{"id":3,"name":"…"}]
    }
  }
}
```

| 字段 | 说明 |
|---|---|
| `players[].pid` | PlayerDataID（**账号级**，跨图稳定） |
| `players[].eosId` | EOSID（32 hex，玩家唯一） |
| `players[].name` | 账号显示名 |
| `players[].characterName` | 角色名 |
| `players[].roles` | `{pid: 角色名}`，多角色地图会有多条 |
| `tribes[<tribeId>]` | 部落名 / 族长 / 成员（含 pid+eosId）/ 联盟 |
| **无等级字段** | 按约定不加（需要等级请走在线接口） |

## 5. 前端接入样例（后端代理 RCON）

```js
// 后端：POST /api/players-refresh?server=Ext
async function refreshPlayers(server) {
  await rcon(server, 'TransferIdentityFix.ExportPlayers light');   // 立即返回
  for (let i = 0; i < 20; i++) {                                   // 最多等 40 s
    await sleep(2000);
    const st = JSON.parse(await rcon(server, 'TransferIdentityFix.ExportStatus'));
    if (st.exists && !st.running) return st;                       // 完成
  }
  throw new Error('export timeout');
}

// 前端：拿数据（后端把 <abbr>_players.json.gz 解压后透传）
const data = await fetch('/api/players?server=Ext').then(r => r.json());
const tribeName = data.tribes[String(player.tribeId)]?.name ?? '(无部落)';
```

> 静态托管方案更简单：计划任务每 5~10 分钟生成一次，前端直接
> `fetch('/data/Ext_players.json')`，用文件 mtime 判断新鲜度。

## 7. 排错表

| 现象 | 原因 | 处理 |
|---|---|---|
| `{"ok":false,"msg":"missing auto_parse_reader_exe / auto_parse_ark_path in config.json"}` | 配置缺两项 | 补配置后 `TransferIdentityFix.ReloadConfig` |
| `msg:"reader exe not found: …"` | exe 路径不对 | 核对路径（含空格需保持原样） |
| `msg:"CreateProcess failed err=2"` | exe 不存在 | 同上 |
| `msg:"ark not found: …"` | `ark=` 指的路径不存在（或空格没写成 `+`） | 核对路径与 `+` 替换 |
| `msg:"missing auto_parse_reader_exe / auto_parse_ark_path in config.json (or ark=<path>)"` | 没配 `reader_exe`，且也没给 `ark=` | 补 `auto_parse_reader_exe` 或带上 `ark=` |
| `msg:"busy: previous export still running"` | 上一轮还在跑 | 等 `ExportStatus.running=false` |
| `msg:"cooldown: Ns left"` | 60 s 冷却中 | 等冷却或调大间隔 |
| `exists:false` 且 `running` 一直 true | 导出器卡住 | 看插件日志 `EXPORT_SPAWN` / 手工跑一次 exe 对照 |
| 产物 `ageSec` 很大但 `ok:true` | 只触发了但没成功 | 查 exe 是否被旧版覆盖（md5 对照本报告 §6） |

---

## 8. 一句话总结

**前端发一条 `ExportPlayers light` → 轮询 `ExportStatus` → 读 `<服缩写>_players.json.gz`**；
插件端有 single-flight + 60 s 冷却 + 固定文件名，重复调用不会刷爆服务器、也不会堆出多份文件。
