### 2.3 Bob 为什么永久为空（已被接受）

Bob 的 `ServerOpsKitAPI\config.json`：

```json
"reconnect": { "enabled": false, ... }
"auto_parse_enabled": false
```

插件的 `TickStateMachine()` 有两道早退门禁：

```cpp
if (!config_.reconnect.enabled && !config_.auto_parse.enabled /* ... */) return;
...
if (!config_.reconnect.enabled) return;
```

两项都为 false ⇒ 函数进去就返回 ⇒ **Bob 从不打印任何 `STATE_MACHINE` 行**。

实测佐证：Bob 日志里有 `PLAYER_POS=5`（说明当时确实有人在线），但 `STATE_MACHINE=0`。

**处理方式**：Bob 仍然返回 `ok: true`，但带 `degraded: true` + `degradedReason: "events_not_logged"`，避免前端把它当成「没人上线」。

### 2.5 日志行格式（逐字确认）

```
11/11/26 13:40 [ServerOpsKitAPI][info] STATE_MACHINE player=00023cf443714568b5e273e50d6e152b state=Idle has_ctrl=1 has_char=1 has_ps=1 pawn_ctrl_ok=1 spawned4ctrl=0 user=嘎巴菜 ctrl=嘎巴丸 char=嘎巴丸
11/11/26 13:40 [ServerOpsKitAPI][info] STATE_MACHINE player=00023cf443714568b5e273e50d6e152b transition=Idle->Completed reason=not_whitelisted
11/11/26 13:40 [ServerOpsKitAPI][info] STATE_MACHINE player=00023cf443714568b5e273e50d6e152b event=new_player state=Idle
11/11/26 13:52 [ServerOpsKitAPI][info] STATE_MACHINE player=00023cf443714568b5e273e50d6e152b event=player_left final_state=3
```

关键点：

1. 时间戳格式 `MM/DD/YY HH:MM` —— **精确到分钟，没有秒**。API 输出秒统一补 `00`。
2. 玩家标识 `player=<32 位十六进制>`（EOS ID，全小写）。
3. **`event=` 行本身不带玩家名**，名字只在 `state=Idle` 行里（`user=` / `ctrl=` / `char=`）。
4. `player_left` 带 `final_state=3`，**但日志无法区分「正常退出」与「掉线」**，所以不输出 `reason` 字段（避免造假数据）。
5. 一条 `event=new_player` 之后通常会跟若干条 `state=Idle` 行（周期性），名字可从这些行取。

### 2.6 日志噪声

每服 30 小时约 2.3 MB / 2.3 万行，其中绝大部分是无关的周期日志：

```
AUTO_KEEP_ALIVE  9431 条    BAG_SCAN  9428 条    AUTO_GIVE_PENDING  3458 条
AUTO_TRANSFER    1027 条    WXHIST     184 条    DEATH_CRYO          124 条
AUTOPARSE_RUN      98 条    STATE_MACHINE 28 条（Isl，全服最多）
```

→ **先做子串预筛**（`'STATE_MACHINE' not in line` 直接跳过）可剪掉 99% 的行，解析耗时可忽略。

### 3.1 行正则

LOG_LINE_RE = re.compile(

### 3.2 时间戳换算

日志时间 = **服务器本地时间**（UTC+8），无秒：

```python
import calendar, datetime
def _logts(mo, dd, yy, hh, mi):
    try:
        dt = datetime.datetime(2000 + int(yy), int(mo), int(dd), int(hh), int(mi))
        return int(calendar.timegm(dt.timetuple())) - _TZ_OFFSET_SEC   # _TZ_OFFSET_SEC = 8*3600
    except Exception:
        return 0
```

> 实施注意：后端若已在别处做过 ARK 日志时间换算（如 `ShooterGame.log` 的 `[YYYY.MM.DD-HH.MM.SS:mmm]` 解析），**优先复用同一个时区口径**，不要另起一套。实施前先 grep 确认现成函数名。

### 3.3 文件排序（跨轮转、跨进程）

```python
def _log_files(abbr):
    d = os.path.join(_srv_win64(abbr), 'logs')
    if not os.path.isdir(d):
        return []
    out = []
    for fn in os.listdir(d):
        if not (fn.startswith('ArkApi_') and fn.endswith('.log')):
            continue
        p = os.path.join(d, fn)
        try:
            st = os.stat(p)
        except OSError:
            continue
        # pid 用于识别进程边界
        m = re.match(r'^ArkApi_(\d+)_', fn)
        out.append({'path': p, 'name': fn, 'pid': m.group(1) if m else '',
                    'mtime': st.st_mtime, 'size': st.st_size})
    out.sort(key=lambda x: (x['mtime'], x['name']))
    return out
```

**必须按 mtime 升序**（后缀大 = 更旧），跨文件才能把「上一份文件里 join、下一份文件里 leave」的会话接起来。

### 3.4 事件与会话配对

两遍逻辑，一遍扫完即可：

```python
# 第一遍：收集 事件 + 名字映射
events = []          # [(ts, eos, 'join'|'leave', pid)]
names  = {}          # eos -> {'user':..., 'char':..., 'ts':...}

# 第二遍：按 ts 配对
events.sort(key=lambda x: (x[0], 0 if x[2] == 'join' else 1))
open_map = {}        # eos -> {'joinAt': ts, 'pid': pid}
sessions = []
for ts, eos, kind, pid in events:
    if kind == 'join':
        prev = open_map.get(eos)
        if prev:
            # 同一个人未收尾又 join：把上一段按未收尾处理，从新段重开
            sessions.append({'eosId': eos, 'joinAt': prev['joinAt'], 'leftAt': None,
                             'state': 'unclosed_rejoin'})
        open_map[eos] = {'joinAt': ts, 'pid': pid}
    else:
        prev = open_map.pop(eos, None)
        if prev:
            sessions.append({'eosId': eos, 'joinAt': prev['joinAt'], 'leftAt': ts,
                             'state': 'closed'})
        else:
            sessions.append({'eosId': eos, 'joinAt': None, 'leftAt': ts,
                             'state': 'leave_without_join'})
```

### 3.5 进程边界处理（防止「幽灵在线」）

服务器重启后，正在线玩家的 `player_left` **不会**被写入日志（进程直接退出）。若不处理，这些会话会永远显示为在线。

**处理办法**：按 mtime 顺序遍历文件，当相邻两个文件的 `pid` 不同（进程换代），把上一代留下的所有 `open_map` 会话按「上一个文件的最后一行时间」收尾：

```python
if prev_pid and cur['pid'] != prev_pid:
    last_ts = _file_last_ts(prev_file)    # 上一文件末行时间
    for eos in list(open_map.keys()):
        if open_map[eos]['pid'] == prev_pid:
            sessions.append({'eosId': eos, 'joinAt': open_map[eos]['joinAt'],
                             'leftAt': last_ts, 'state': 'closed_by_restart'})
            open_map.pop(eos, None)
```

`state` 枚举（供前端区分）：

| state | 含义 |
|---|---|
| `closed` | 正常配对到 `player_left` |
| `closed_by_restart` | 进程换代时仍在线，已按上一代末尾时间收尾 |
| `unclosed_rejoin` | 未收到 leave 就又 join，上一段按「未知结束」处理 |
| `leave_without_join` | 只看到 leave，join 在更早（已被轮转删掉）的日志里 |
| `online` | 仍在 open_map 中，且未超龄 |

### 3.6 在线判定与超龄保护

```python
OPEN_STALE_SEC = 6 * 3600      # 无 leave 且超过 6 小时 → 不认为是「在线」
```

- 仍在 `open_map` 且 `now - joinAt <= OPEN_STALE_SEC` → `state: 'online'`
- 超过 → `state: 'stale_open'`（可能被日志轮转截断，或 leave 行丢失）

### 3.7 名字回填

```python
for s in sessions:
    n = names.get(s['eosId']) or {}
    s['playerName'] = n.get('user') or ''
    s['charName']   = n.get('char') or n.get('user') or ''
```

因为名字行是周期性打印的，同一玩家在 30 小时日志里必有至少一条 `user=` 行 —— 实测 4 个有事件的服，名字全部取到（`嘎巴菜` / `whiter.rober` / `JaronV5`）。

**兜底**：若 `playerName` 为空，前端显示 EOS 前 8 位；后端不编造名字。

## 4. 架构与数据流

```

        │  只读、按 mtime 升序拼接
        ▼

        ▼

        ▼

        │
        ▼
前端
```

**不落任何文件、不写任何数据**，纯读 + 内存缓存。

## 5. 缓存与性能

### 5.1 两级缓存

```python
_FILE_CACHE = {}     # path -> {'mtime':, 'size':, 'events': [...], 'names': {...}, 'lastTs': int, 'pid': str}
_SESS_CACHE = {}     # abbr -> {'ts': now, 'data': {...}}

FILE_CACHE_MAX = 64          # 超出时清最旧的一半
SERVER_CACHE_TTL = 60        # 秒
```

- 文件 `(mtime, size)` 未变 → 直接复用已解析结果（日志只在追加或轮转时变）
- 服务级 TTL 60 s，`?fresh=1` 强制重算

### 5.2 实测耗时预估

| 场景 | 数据量 | 预估耗时 |
|---|---|---|
| 单服首次（冷缓存） | 2.3 MB / 2.3 万行 | 60~150 ms（子串预筛后真正走进正则的 < 300 行） |
| 单服命中缓存 | — | < 5 ms |
| 11 服全量（冷） | ~25 MB / 25 万行 | 1~2 s |
| 11 服全量（命中） | — | < 20 ms |

→ **默认只支持单服查询**；若前端要全服，请分 11 次并发请求（各服独立缓存，互不阻塞）。

### 5.3 一处必须注意

后端是 `ThreadingHTTPServer`（若属实），并发请求会同时扫同一批文件。用 `threading.Lock()` 包住 `_player_sessions_scan` 的冷计算部分，避免重复扫描；命中缓存时不加锁。

> 实施前确认后端 HTTP 服务类型（`HTTPServer` 还是 `ThreadingHTTPServer`），再决定是否需要锁。

| `seconds` | int / null | 会话时长；无法计算时为 `null` |
| `state` | string | `closed` / `closed_by_restart` / `unclosed_rejoin` / `leave_without_join` / `online` / `stale_open` |
| `playerName` | string | 可能为空字符串（此时前端显示 EOS 前 8 位） |
| `coverage.hours` | float | **真实可解析窗口**，前端必须以此为准，不要假设 48 |
| `degraded` | bool | `true` = 该服不产生事件日志（目前仅 Bob） |

### 7.4 错误码

| 场景 | code | body |
|---|---|---|
| 缺 `server` | 400 | `{'ok':false,'error':'server required','servers':[...]}` |
| `server` 不在白名单 | 400 | `{'ok':false,'error':'unknown server','servers':[...]}` |
| 目录不存在 | 200 | 正常返回，`coverage.files=0`、`sessions=[]`、`degradedReason='log_dir_missing'` |
| 解析异常 | 500 | `{'ok':false,'error':'scan failed: ...'}` |

> 目录不存在故意返回 200 而不是 404 —— 让前端统一处理，少一条分支。

## 8. 前端调用（一句话）

> `GET https://data.whiterober.ccwu.cc/api/player-sessions?server=<Abbr>`（`<Abbr>` ∈ Bob / Isl / Sco / Cen / Abe / Ext / Ast / Rag / Val / Los / Gen），返回该服**近约 30 小时**（以响应里的 `coverage.hours` 为准）的玩家上下线会话：`sessions[]` 里每条含 `eosId` / `playerName` / `charName` / `joinAt` / `leftAt`（epoch 毫秒）/ `seconds` / `state`，按时间倒序；`online[]` 是当前仍在线的人；`degraded=true` 表示该服（目前只有 Bob）不产生事件日志、数据必为空，请显示「该服暂不支持」而不是「无人上线」。

## 9. 边界与已知空缺

| 场景 | 表现 | 处理 |
|---|---|---|
| **Bob** | 永远 0 条 | `degraded:true`（已接受） |
| 空服（Sco/Abe/Ext/Rag/Los/Gen 等） | 数据本来就是 0 | 正常 0 条，`degraded:false` |
| 玩家秒进秒退（< 1 分钟） | 时间精度只到分钟，`seconds` 可能为 0 | 允许，`seconds` 最小 0 |
| 服务器重启时有玩家在线 | 无 `player_left` 行 | §3.5 进程边界收尾 → `closed_by_restart` |
| join 在已删除的老日志里 | 只剩 leave 行 | `leave_without_join`，`joinAt=null` |
| 日志轮转删除太快 | 窗口缩短 | 响应带真实 `coverage`，不做假承诺 |
| 同一玩家反复进出 | 多段会话 | 正常，`unclosed_rejoin` 标记异常段 |
| 日志目录被清空 | `files=0` | `degradedReason='log_dir_missing'` |
| 中文名 | `user=嘎巴菜` | 日志是 UTF-8；读文件用 `errors='replace'` 防个别坏字节 |

## 11. 风险与回滚

| 风险 | 等级 | 缓解 |
|---|---|---|
| 改 21,557 行生产文件出错 → **全站页面挂** | 高 | ① 改动前 `shutil.copy2` 整份备份 `dino_backend.py.bak_<ts>` ② 新增代码全部用 `_ps_` 前缀隔离 ③ 路由层 try/except 兜底 ④ 改完先 `python -m py_compile` ⑤ 重启后立刻打 V10 五个接口 |

## 13. 后续可选增强（P2，不在本次范围）

## 14. 与「改 dll」方案的取舍（备查）

| 维度 | 本方案（后端解析日志） | dll 方案（L2 插件落盘） |
|---|---|---|
| 部署 | 后端重启 1 次 | 11 服各投 dll + 重启 |
| 代码量 | ~170 行 Python | ~140 行 C++ |
| 窗口 | 29~39 h（受日志轮转） | 自行滚动，可保 48 h |
| 名字 | 靠 `user=` 行关联 | 钩子直接拿 |
| 时间精度 | 分钟 | 毫秒 |
| Bob | 空 | 有 |
| 出错半径 | 全站 | 单服 |
| 生产文件 | 动 21,557 行文件 | 不动后端 |

**本次选择理由**：数据量极小（30 小时 13 次上下线）、用户已放弃 48 小时硬要求、可接受 Bob 空缺 → 用一次后端部署换掉 11 次 dll 投放。
