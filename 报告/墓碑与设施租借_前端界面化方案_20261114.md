# 墓碑 与 设施租借 —— 前端界面化方案

- 日期：2026-11-14
- 适用：`Server Ops Kit`（`ServerOpsKitAPI`）插件 + `dino_backend` 后端 + 前端页面
- 性质：**方案文档**。第 3 章为"现在就能做"，第 4 章为"需新增插件接口后能做"
- 依据：插件源码实测（`TransferIdentityFixAPI.cpp`）+ 实服产物实测（Isl / Cen / Sco）

---

## 1. 结论先行：两项功能的可界面化程度

### 1.1 墓碑（Gravestone）

| 能力 | 现状 | 说明 |
|---|---|---|
| 在地图/列表里**显示墓碑** | ✅ 可做 | 数据已在 `<abbr>_cryo.json.gz` 的 `structures[]` 里 |
| 显示墓碑**归属部落 / 自定义名 / 坐标** | ✅ 可做 | 字段齐全 |
| **管理员手动把死亡包移到墓碑** | ✅ 可做 | 有现成 RCON 命令 `TransferIdentityFix.MoveDeathBag` |
| **批量把待处理包移至各部落墓碑** | ✅ 可做 | `TransferIdentityFix.MoveAllPendings`（必须传部落 ID） |
| 列出**墓碑里存了哪些物品** | ❌ 做不到 | 没有任何数据出口（见 2.2 实测） |
| 远程**取出 / 清空**墓碑 | ❌ 做不到 | 无命令 |
| 创建 / 移动 / 删除墓碑 | ❌ 做不到 | 无命令（`TestSpawnTomb` 是实验用途，不建议暴露） |

### 1.2 设施租借（Borrow）

| 能力 | 现状 | 说明 |
|---|---|---|
| 查询"谁借了哪块建筑、还剩多久" | ❌ 做不到 | 租借状态**只在内存**，无任何输出（无命令、无文件、无 JSON） |
| 远程**强制归还（全部）** | ✅ **已可做** | **命令已存在**：`TransferIdentityFix.BorrowRestore`（`CmdBorrowRestore` → `RestoreBorrows(manual=true)`）；<br>✅ 0.9.1 起另有 `CmdBorrowRestoreRcon`，返回 `{ok,released}` |
| 远程**归还单条** | ❌ 做不到 | `RestoreBorrows` 是全量遍历，无索引参数 |
| 由前端**发起借用** | ❌ 做不到（受限） | `TransferIdentityFix.Borrow` 已存在，但必须 `issuer` 是**在线玩家**且**正在瞄准**结构，无法远程指定建筑 |
| 只做**玩法说明页**（图文，无数据） | ✅ 可做 | 零插件改动 |

> **2026-11-14 复核纠正**：本节早前写"远程强制归还 ❌ 做不到"是**错的** —— `BorrowRestore` 早已存在并能真归还。
> 真正缺的是①**查询列表** ②**结构化返回** ③**单条归还**。

> **一句话**：墓碑可以做成"地图展示 + 管理员手动转移"的完整页面；设施租借目前**没有任何对外接口**，要做界面必须先加插件命令（第 4.2 节给了完整设计）。

## 2. 现状事实（代码与实测证据）

### 2.1 墓碑系统是**全自动**的，没有管理命令

死亡后的流程（插件内部，无人干预）：

1. 玩家死亡 → 生成死亡包（`DeathItemCache`）/ 尸体
2. 约 1 秒后做归属判定（`tomb_judge_ready_` 队列），把装备/遗物归类
3. 找**该部落最近的墓碑**（`TombInfo { team, x, y, z, yaw }`，按 `StructureBP_Gravestone*` 类名扫描全场 actor）
4. 转移到墓碑容器，并把该包的销毁计时**刷新到 14 天**
5. **找不到墓碑** → 死亡包原地保留 15 天
6. 被**研磨机击杀** → 不转移（会单独发通知）

通知相关配置（`config.json`）：

| 键 | 默认 | 含义 |
|---|---|---|
| `tomb_notify_enabled` | `true` | 墓碑系统游戏内通知总开关 |
| `tomb_notify_min_interval_seconds` | `30` | 同部落同节点通知节流（防刷屏） |

### 2.2 墓碑的**数据出口**：只有 `structures[]`，内容物没有任何出口

实服实测（`GET /dino-data/<abbr>_cryo.json.gz`）：

| 服 | `structures[]` 总数 | 其中 Gravestone | `facilities[]` 中 Gravestone | `item.json.gz` 中 containerClass 含 Gravestone |
|---|---|---|---|---|
| Isl | 134 | **7** | 0 | **0** |
| Cen | 35 | **1** | 0 | **0** |
| Sco | 64 | **1** | 0 | **0** |

`structures[]` 里的墓碑样本（真实数据）：

```json
{"class":"StructureBP_Gravestone_3_C_2144735163","name":"My FISH",
 "tribeId":1621369181,"tribeName":"北境游骑兵",
 "x":-265489.59,"y":-259545.92,"z":-6162.5}
```

结论：
- 墓碑**能列出**（位置 / 名字 / 部落）
- 墓碑里**存了什么完全查不到** —— `facilities[]` 不含墓碑，`item.json.gz` 里也没有任何 `containerClass` 是 Gravestone 的物品

### 2.3 设施租借：仅游戏内触发，状态纯内存

| 项 | 现状 |
|---|---|
| 触发方式 | ① **望远镜左键**（`ToggleBorrowForPC`：再点一次 = 立即归还）② **信号枪右键**（`ServerStartWeaponAltFireHook`）③ 聊天 `/tif borrow`、`/tif borrowrestore` |
| 前置条件 | 瞄准目标；目标部落 ≠ 自己部落；`IsTribeAllied()` 同盟；`IsBorrowableClass()` 在白名单 |
| 实现 | `GiveActorToMe(aim, true)` 把建筑临时给自己 |
| 时长 | **5 分钟**自动归还 |
| 冷却 | 同一建筑借用时即开始 **5 分钟**冷却 |
| 可借种类 | `config.json` 的 `borrowable_classes`（`class` 关键字 + 显示名），为空则用内置默认 |
| **状态存储** | `std::vector<BorrowEntry> borrows_` —— **纯内存**，重启/崩溃即清空 |
| **已有 RCON 命令** | ✅ `TransferIdentityFix.Borrow`（发起借用，需玩家在线且瞄准）<br>✅ `TransferIdentityFix.BorrowRestore`（**立即归还全部**）<br>⚠️ 两者走 `HandleCommand`，只有 `ChatSend` + `LogInfo`<br>✅ 0.9.1 起 `BorrowRestore` 另注册带 `RCONClientConnection` 的版本，返回 `{ok,released}` |
| **缺失的接口** | ❌ 查询列表（谁借了什么、还剩多久）<br>❌ 结构化返回（`released` 数量等）<br>❌ 单条归还 |

已记录缺陷（`发布\租借状态落盘方案.md`）：`expire_ms` 用了 `steady_clock`（进程启动起算），语义是"开机后 5 分钟"而非"借用后 5 分钟"。
**✅ 2026-11-14 S2b 已修复**：4 处写入/读取全部改为 `NowEpochMs()`（详见 §10.4）。

**2026-11-14 复核新增证据**：`ToggleBorrow` 内相邻两行混用两种时间基准 ——
`be.expire_ms`（19661 行，`steady_clock`+300000）与 `structure_borrow_cooldown_[aim]`（19667 行，`NowEpochMs()`+300000）。
同一件事两个坐标系 ⇒ 冷却能跨重启，到期不能 ⇒ 这是**确凿 bug**，非"只是隐患"。行号与全文 `steady_clock` 清单见 §10.4。
**✅ 已修复（S2b）**：借用相关函数内已无 `steady_clock`（其余 6 处属其它用途，按 §10.4 规定不动）。

## 3. 墓碑 UI 方案（现在就能做，零插件改动）

### 3.1 展示层：从 `structures[]` 取数

**接口**

```
GET https://data.whiterober.ccwu.cc/dino-data/<Abbr>_cryo.json.gz
```

- 响应头 `Content-Type: application/gzip`，响应体是 **gzip 字节**（不是 JSON 文本）
- 浏览器 `fetch` 后用 `DecompressionStream` 解压，或后端解压后转发
- **没有 304**：后端写 `ETag` 但不解析 `If-None-Match`，每次都是 200 全量
- 前端增量判断请用 `GET /dino-data/_lm.json` 比较字符串

**筛选规则**

```js
const tombs = (doc.structures || []).filter(s => /Gravestone/i.test(s.class || ''));
```

**字段字典（墓碑）**

| 字段 | 类型 | 说明 |
|---|---|---|
| `class` | string | `StructureBP_Gravestone_<n>_C_<instanceId>`；`_<n>` 是外观变体 |
| `name` | string | 玩家给墓碑起的名（空字符串 = 未命名） |
| `tribeId` | number | 所属部落 ID（0 = 无主） |
| `tribeName` | string | 部落名（可能为空） |
| `x` / `y` / `z` | number | 世界坐标（ARK 单位） |

**建议的展示功能**

1. 地图打点：按 `tribeId` 上色，hover 显示 `name` + 部落名
2. 列表：按部落分组，支持按名字搜索（`name` 为空显示"未命名墓碑"）
3. 统计卡：全服墓碑数 / 有名字的墓碑数 / 无主墓碑数
4. 点击墓碑 → 显示坐标 + 复制传送指令（若有）

### 3.2 运维操作层：两个现成命令

> ⚠️ 这两个命令会**移动游戏内实体**，属于写操作。建议前端只给管理员（level ≥ 2/3）显示，并且**必须二次确认**。

#### ① 单人转移

```
POST /api/srvctl/rcon
Authorization: Bearer <token>

{"servers":["Isl"], "message":"TransferIdentityFix.MoveDeathBag <target>"}
```

- `<target>` 两种形态：
  - **纯数字** → 当作**部落 ID**（该部落所有成员的包）
  - **非数字** → 当作**玩家**（在线名或 EOS ID）
- 行为：把该玩家/部落的死亡包移到**其部落最近的墓碑**，并把销毁计时刷新到 14 天；**没有墓碑时只在原地刷新计时**

错误响应（插件返回）：

| error | 触发 |
|---|---|
| `missing target` | 未传参数 |
| `invalid tribe id` | 传了 `0` |
| `player offline or not found` | 玩家不在线/找不到 |

#### ② 批量转移（按部落）

```
{"servers":["Isl"], "message":"TransferIdentityFix.MoveAllPendings <teamId>"}
```

- `<teamId>` **必须是部落 ID**（空 / 非数字 → `missing team` / `invalid team`）
- 空结果响应（可作"无事可做"判据）：

```json
{"ok":true,"pendingTotal":0,"pendingMoved":0,"pendingFailed":0,"noTomb":0,"remaining":0,"moved":[]}
```

- 单批上限取 `config.json` 的 `auto_transfer.move_batch_limit`（默认 20）

### 3.3 建议的 UI 交互

| 场景 | 交互 |
|---|---|
| 单玩家补偿 | 玩家列表 → "把死亡包移到墓碑" → 确认弹窗（显示玩家名 + 目标墓碑名）→ 调 `MoveDeathBag <玩家>` |
| 部落批量 | 部落详情 → "清理待处理包" → 确认弹窗（显示部落名 + 已选墓碑数）→ 调 `MoveAllPendings <tribeId>` |
| 结果反馈 | 成功：`ok=true`，提示"已移动 N 份"；失败：按 `error` 映射中文文案 |

### 3.4 墓碑这块**明确做不到**的事（避免前端白做）

1. 看不到墓碑里存了什么（无数据出口）
2. 不能远程取出/清空墓碑（无命令）
3. 不能创建/挪动/删除墓碑
4. 墓碑坐标是**世界坐标原值**，前端自行换算法才算地图像素位置

## 4. 设施租借 UI 方案（需新增插件接口）

### 4.1 为什么现在做不了

**2026-11-14 复核纠正**：早前写"18+ 条命令里没有任何 borrow 相关"是**错的**。

实测：现有 **66 条** `RegisterRconCommand*` 唯一命令（59 条带 `TransferIdentityFix.` 前缀 + 7 条别名）；
另有 `HandleCommand` 里 `if (name == ...)` 分发的 `tif.*` 聊天命令**不计入这 66 条**。
其中 **2 条已是 borrow 相关**（走 `HandleCommand`，无 `RCONClientConnection`，只能 `ChatSend`）：

| 命令 | 源码 | 行为 | 缺什么 |
|---|---|---|---|
| `TransferIdentityFix.Borrow` | `HandleCommand` | 发起借用（需在线玩家 + 瞄准） | — |
| `TransferIdentityFix.BorrowRestore` | `HandleCommand` | **立即归还全部** | 原无 JSON 返回（✅ 0.9.1 已补）、无单条归还 |

真正缺的是三点：

1. **无查询命令**：66 条注册命令里没有一条能列出"当前谁借了什么"（✅ 0.9.1 已由 `TransferIdentityFix.BorrowList` 解决）
2. **无结构化输出**：`borrows_` 只在内存，不写文件、不进任何 JSON；且原有两条命令只 `ChatSend`，程序无法读取结果（✅ 0.9.1 已解决：`BorrowList` + `BorrowRestore` 均返回 JSON）
3. **无持久化**：重启即丢（`expire_ms` 的错误时间基准已由 S2b 修复；进程内借用关系仍只在内存，属设计边界）

### 4.2 方案 A（推荐）：新增 **1 条** 命令 + 给 1 条现有命令补返回值

> **必要性评估结论（2026-11-14 复核，完整论证见 §16）**
>
> | 原设想 | 结论 | 理由 |
> |---|---|---|
> | `BorrowList` | **新增** | 唯一出口，无任何替代（无命令 / 无文件 / 无 JSON） |
> | `BorrowRelease` | **不新增** | `<all>` 与现有 `BorrowRestore` **100% 重复** |
> | `TombHistory` | **不新增** | 静态 TSV 完全覆盖；RCON 300 字符连 1 条都装不下 |
> | `BorrowHistory` | **不新增** | 同上 |
>
> 净效果：从"新增 4 条命令"降到"**新增 1 条 + 改 1 条现有命令的返回**"，
> 插件侧代码量约减半，风险面显著缩小。

#### A-1 新增：`TransferIdentityFix.BorrowList`（唯一真要新增的命令）

**请求**：`TransferIdentityFix.BorrowList [tribeId]`

- 不带参数 = 全服；带参数 = 只看该部落作为**借用方**的记录

**建议响应**

```json
{"ok":true,"count":2,"nowMs":1763100000000,
 "items":[
   {"index":0,
    "structClass":"StructureBP_Ceiling_Metal_C",
    "kind":"天花板",
    "origTribeId":1505147424,
    "origTribeName":"test的部落",
    "origOwner":"someOwner",
    "origOwnerPlayer":"板板",
    "borrowerEosId":"00023cf4…",
    "borrowerName":"嘎巴菜",
    "borrowerTribeId":1181886739,
    "expireAtMs":1763100300000,
    "remainSec":300,
    "x":-265489.59,"y":-259545.92,"z":-6162.5}
 ]}
```

#### A-2 改造：给现有 `BorrowRestore` 补 JSON 返回（**不新增命令**）

改造前形态（当时的 `CmdBorrowRestore`）：

```cpp
void Plugin::CmdBorrowRestore(const std::string& issuer) {
    if (borrows_.empty()) { ChatSend(issuer, "[TIF][提示] 当前没有待恢复的借用结构"); return; }
    const long long now_b = …steady_clock…;
    const int n = RestoreBorrows(true, now_b);
    ChatSend(issuer, "[TIF] 已立即恢复 " + std::to_string(n) + " 个借用结构归属");
    LogInfo("BORROW_RESTORE_MANUAL count=" + std::to_string(n));
}
```

**实际实现（0.9.1）**：聊天路径 `CmdBorrowRestore` **一行未改**，另开一个带 `RCONClientConnection` 的入口
`CmdBorrowRestoreRcon`，在 `RegisterRconCommandWithConnection` 里注册为同名命令
（`HandleCommand` 的聊天分支保留，两者互不干扰）：

```cpp
// .h
void CmdBorrowRestoreRcon(RCONClientConnection* connection, int request_id);

// .cpp
void Plugin::CmdBorrowRestoreRcon(RCONClientConnection* connection, int request_id) {
    if (borrows_.empty()) {
        bridge_->SendRconResponse(connection, request_id,
            "{\"ok\":true,\"released\":0,\"reason\":\"empty\"}");
        return;
    }
    const long long now_b = NowEpochMs();
    const int n = RestoreBorrows(true, now_b);        // 复用现有归还逻辑，不重写
    LogInfo("BORROW_RESTORE_RCON count=" + std::to_string(n));
    BorrowHist(... "released=" + std::to_string(n) + ",trigger=rcon" ...);
    bridge_->SendRconResponse(connection, request_id,
        "{\"ok\":true,\"released\":" + std::to_string(n) + "}");
}
```

> 为什么不直接给 `CmdBorrowRestore` 加参数：它只有 `issuer` 没有 connection，
> 改造会牵动聊天路径与 `HandleCommand` 分发；新开入口是**零回归风险**的做法。
> 实测：`{"ok":true,"released":1}`（Cen 2026-11-14 22:43）

**为什么不新增 `BorrowRelease`**：`<all>` 语义已完全被覆盖；`<index>`（单条归还）属于低频需求，
真要做时给 `BorrowRestore` 加一个可选参数 `index` 即可，**无需新增命令**。

#### 实现要点（给写代码的人）

| # | 要求 |
|---|---|
| 1 | `BorrowList` / `BorrowRestore` 都复用现有 `RestoreBorrows(bool manual, long long now_b)`，不要另写归还逻辑 |
| 2 | ✅ **已完成**：`expire_ms` 的 4 处 `steady_clock` → `NowEpochMs()`（行号见 §10.4），否则 `remainSec` 是错的 |
| 3 | `structClass` 取 `be.st->ClassPrivateField()…`；**不要输出裸指针** |
| 4 | 响应走 `SendRconResponse`（自动 `\uXXXX` 转义，中文安全） |
| 5 | `BorrowList` 几十条即可超 4 KB 单包 → **必须分页**（`limit` / `offset`），或只返精简字段 |
| 6 | `borrowerName` 走 `player_map`/`FindControllerForTarget` 解析；离线借用者可能取不到，返回空串 |
| 7 | 给 `BorrowRestore` 补 JSON 时**保留原 `ChatSend`**，不要为了结构化输出删掉游戏内提示 |

#### 前端调用（经后端）

```
POST /api/srvctl/rcon
{"servers":["Isl"], "message":"TransferIdentityFix.BorrowList"}
```

⚠️ **必须知道的坑**：后端 `/api/srvctl/rcon` 会把响应 `message` **截断到 300 字符**（`dino_backend.py` 第 5875 / 5905 行）。上面的 JSON 大概率超长 → **这条命令必须由后端加一个专用接口转发**，不能用通用 rcon 通道。

建议后端新增：

```
GET /api/plugins/borrow-list?server=Isl        → 透传插件 JSON，不截断
POST /api/plugins/borrow-restore              → body: {server}  （透传，返回 {ok,released}）
```

### 4.3 方案 B（零改动）：只做玩法说明页

若短期不改插件，前端只能做静态说明：

- 怎么借：瞄准 → **举望远镜**（左键）或 **信号枪右键**
- 条件：与目标部落**同盟**、目标是可借类型（地基/天花板等）
- 时长：5 分钟自动归还；再次举镜 = 立即归还
- 冷却：归还后 5 分钟内同一块不能再借
- **风险提示**（务必写进页面）：服务器重启会导致借用关系丢失，建筑可能不回原主

### 4.4 租借这块的**功能边界**

| 项 | 边界 |
|---|---|
| 前端不能发起借用 | 借用本质是"玩家瞄准某块建筑"，需要玩家在场 + 瞄准，无法远程指定 |
| 前端不能改时长 | 5 分钟硬编码，无配置项 |
| 重启会丢 | 内存态；即使有 `BorrowList` 也只能看到"当前进程内"的借用 |
| 免费版/付费版 | 租借属 `Server Ops Kit Lease`（免费件）与完整版共有，行为一致 |

## 5. 前端需要知道的**全部**接口

## 11. 传图自动二次加载白名单（本身即 `config.json` 可配置项，见 §12.1 A 类）

### 11.1 这个功能在代码里叫什么（已核实）

就是 **`reconnect.whitelist`** —— 一个**玩家名**数组：

```json
"reconnect": {
  "enabled": true,
  "host": "work.whiterober.cn",
  "port": 0,
  "whitelist": ["whiter.rober"],
  "max_reconnects_per_session": 1,
  "cooldown_seconds": 30
}
```

判定逻辑（`Plugin::IsWhitelisted`，源码 24449 行）：

```cpp
if (config_.reconnect.whitelist.empty()) return false;
if (config_.reconnect.whitelist.size() == 1 && config_.reconnect.whitelist[0] == "*") return true;
for (const auto& w : config_.reconnect.whitelist) { ... 名字匹配 ... }
```

- 名单为空 → **任何人都不会**走二次加载
- 名单恰好是 `["*"]` → **全体**都走
- 不在名单 → 日志出现 `STATE_MACHINE … transition=Idle->Completed reason=not_whitelisted`

⚠️ 与 `reconnect.enabled` 的关系：`enabled=false` 时整条 tick 链早退（Bob 就属于这种情况，见 `arkapi-log-events` 记录），**此时白名单配了也不生效**。

### 11.2 前端"配置白名单"需要什么

现状：**没有写配置的接口**。插件只读 `config.json`；改文件后需执行 `TransferIdentityFix.ReloadConfig` 才生效。

**建议后端新增 3 个接口**（推荐实现，前端零插件依赖）：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/plugins/config?server=<Abbr>` | 返回**可配置子集**（见 §12），路径类字段一律脱敏 |
| PATCH | `/api/plugins/config` | body `{server, patch:{...}}` → 校验 + 原子写 + 自动 `ReloadConfig` |
| POST | `/api/plugins/config/reload` | 手动触发 `TransferIdentityFix.ReloadConfig` |

**白名单写入的校验规则（必须做，否则会写坏）**

| 规则 | 说明 |
|---|---|
| 类型 | 必须是字符串数组 |
| 单条长度 | 1–64 字符 |
| 单条内容 | 去首尾空白；不允许逗号、引号、反斜杠（插件用**正则**解析，含引号会破坏 JSON） |
| 去重 | 忽略大小写去重 |
| 数量上限 | 建议 200 条 |
| `*` 特殊值 | 只允许"单独一条 `*`"；与其他条目混用时**前端必须强提示**"等于全体" |
| 空数组 | 允许，但**必须强提示**"等于关闭二次加载" |

### 11.3 生效与回滚

- 写入后调用 `TransferIdentityFix.ReloadConfig`（RCON），日志会出现 `CONFIG_RELOAD … whitelist_count=N`（源码 4229 行）
- 前端应展示 reload 的返回与 `whitelist_count`，作为"已生效"的凭据
- 回滚：每次 PATCH 前后端自动备份 `config.json.bak_<ts>`，一键还原 = 拷回 + 再 reload

### 11.4 风险

| 风险 | 后果 | 缓解 |
|---|---|---|
| 写坏 JSON | 插件解析失败（正则会取到旧值或默认值），白名单静默失效 | 写入前 `json.loads` 自检 + 保留备份 |
| 误配 `*` | 所有玩家都走二次加载，可能引发重连风暴 | 前端强提示 + 二次确认 |
| 只改文件不 reload | 看起来保存成功但不生效 | PATCH 接口内部自动 reload |
| `enabled=false` 时配白名单 | 白名单无效 | GET 时同时返回 `enabled`，前端显式提示 |

## 14. 插件端改造方案：台账"记录详细"且"几乎不耗性能"

> 目标：**字段尽量全**，同时对游戏线程**零额外遍历、零同步磁盘 IO**。
> 设计原则一句话：**在"本来就要执行的那行日志处"顺手记一条，先进内存，再由 tick 限时刷盘；只追加、不重写。**

### 14.1 为什么这样做就足够便宜（先给量级）

| 事件 | 真实频率 | 单条体积 | 每日增量 |
|---|---|---|---|
| 墓碑转移（`AUTO_TRANSFER` / 手动） | 几十~几百次/天（=死亡事件频率） | ≈ 370 B（17 列，含中文） | < 160 KB/天 |
| 租借（`BORROW` / `TOGGLE_BORROW`） | 几十次/天（人工操作） | ≈ 320 B（15 列） | < 20 KB/天 |

结论：**数据量小到可以忽略**。真正的风险不是数据量，而是"在游戏线程里做磁盘 IO / 遍历所有 actor"。
因此设计重点全部放在**异步化**与**零额外遍历**上。

### 14.2 落盘形态

| 项 | 决定 | 理由 |
|---|---|---|
| 文件名 | `<Abbr>_tomb_history.tsv` / `<Abbr>_borrow_history.tsv` | **必须按服分文件**：`D:\ARK Server\DinoData` 被 10 个地图进程共用，同名会互相覆盖（历史已踩过） |
| 格式 | TSV，首行为版本头 `#v1\t<列名...>` | 人可读、可 grep、无需引入 JSON 依赖 |
| 打开方式 | **只追加**（`std::ios::app`） | 不需要整文件重写 ⇒ 免去原子替换的开销与"丢失外来行"的风险 |
| 单写者 | 天然成立（文件属本服） | 追加写在本服唯一写者下是安全的 |
| 裁剪 | 行数 > `history_max_rows`（默认 20000）时，**仅在启动阶段**重写保留最近 N 行 | 避开运行期热点；启动期做一次重写成本可忽略 |
| 编码 | UTF-8 | 中文（部落名/玩家名）直接可读 |
| 磁盘上限 | 20000 行 × ~350 B ≈ **7 MB/服**，11 服最坏 **77 MB** | 实测量级：真实数据 90 天也远达不到上限 |
| **新引入的模式** | 实施前全项目落盘均为"原子替换"（`AtomicWrite`，11 处），**`ios::app` 为 0 处**；本次台账首次引入追加型 | 成立前提是"**按服分文件 + 单写者**"，两者缺一不可（`HistInitSinks` 在 abbr 为空时**直接禁用**而非兜底） |
| tag 为空时的行为 | **不落盘**（禁止兜底成无后缀文件） | 现有 `wx_history` 在 tag 为空时兜底写 `wx_history.tsv`，`DinoData` 里**确有一个无后缀 `wx_history.tsv` 残留**（实测存在）—— 新台账必须避免重犯 |

> 与 `wx_history_<Abbr>.tsv` / `volcano_history_<Abbr>.tsv` 的差异：那两份是"整表重写型"（需要原子替换 + 保留外来行），
> 本台账是**追加型**，因此更省：永不在运行期重写整个文件。

### 14.3 核心结构（新增约 120~160 行）

```cpp
// 版本头必须是**编译期常量字符串**，且与 §15.5 的列序逐字一致
static const char* kTombHistHeader =
    "#v1\tts\tkind\tteamId\ttribeName\tplayerName\teosId\ttombName\tx\ty\tz"
    "\tmovedCount\tmovedEquipment\tmovedPods\tmovedRelics\tresult\tnote\n";
static const char* kBorrowHistHeader =
    "#v1\tts\taction\tstructClass\tstructKey\tx\ty\tz\torigTribeId\torigTribeName"
    "\torigOwnerPlayer\tborrowerEosId\tborrowerName\tborrowerTribeId\texpireAtMs\treason\n";

struct HistorySink {
    std::mutex mu;
    std::vector<std::string> buf;              // 待刷缓冲（元素 = 已拼好的整行，含 \n）
    std::string path;                          // <DinoData>/<Abbr>_tomb_history.tsv
    const char* header = nullptr;              // kTombHistHeader / kBorrowHistHeader
    size_t dropped = 0;                        // 缓冲溢出丢弃计数
    size_t fail_streak = 0;                    // 连续写失败次数
    bool   disabled = false;                   // 连续失败 N 次后自动停用（防刷日志）
    bool   header_ok = false;                  // 版本头已就位（避免每轮 stat）
    long long next_flush_ms = 0;               // 下次允许刷盘的时刻（时间门禁，见下方 R11）
};

// 游戏线程调用：只做字符串格式化 + 入队，**不碰磁盘**
void Plugin::TombHist(const std::string& cols);   // cols 已用 '\t' 拼好
void Plugin::BorrowHist(const std::string& cols);

// tick 内调用：带时间门禁的限时刷盘
void Plugin::HistFlush(HistorySink& s, long long now_ms);
```

**入队（游戏线程，微秒级）**

```cpp
void Plugin::TombHist(const std::string& cols) {
    if (!config_.history_enabled) return;
    std::lock_guard<std::mutex> lk(tomb_hist_.mu);
    if (tomb_hist_.buf.size() >= 4096) { ++tomb_hist_.dropped; return; }  // 上限保护
    tomb_hist_.buf.emplace_back(cols);
}
```

**刷盘（tick 内，**必须自带时间门禁**）**

```cpp
void Plugin::HistFlush(HistorySink& s, long long now_ms) {
    // ①② 门禁必须在**取锁之前**，否则每帧都要抢一次锁
    if (s.disabled) return;
    if (now_ms < s.next_flush_ms) return;       // 未到节流窗口 → 直接返回（常态路径）
    std::vector<std::string> batch;
    {
        std::lock_guard<std::mutex> lk(s.mu);
        if (s.buf.empty()) return;              // 无事件 = 零开销（关键）
        batch.swap(s.buf);
    }
    if (s.header_ok == false) {                 // 只在首次写时 stat 一次，之后不再 stat
        std::error_code ec;
        bool existed = std::filesystem::exists(s.path, ec);
        std::ofstream h(s.path, std::ios::app | std::ios::binary);
        if (!h) { ++s.fail_streak; if (s.fail_streak >= 5) { s.disabled = true; LogWarn("HIST disabled " + s.path); } return; }
        if (!existed) h << kHistHeader;
        h.flush();
        s.header_ok = true;
    }
    std::ofstream of(s.path, std::ios::app | std::ios::binary);
    if (!of) { ++s.fail_streak; if (s.fail_streak >= 5) { s.disabled = true; LogWarn("HIST disabled " + s.path); } return; }
    for (auto& l : batch) of << l;
    of.flush();
    s.fail_streak = 0;
    s.next_flush_ms = now_ms + config_.history_flush_interval_seconds * 1000LL;
}
```

> `header_ok` 缓存把"每 5 秒一次 `filesystem::exists`"降为"进程生命周期内 1 次"。
> 若外部手动删了文件，下次 flush 时 `ofstream` 仍能创建新文件（只是缺版本头）——**可接受**，
> 因为读端遇到无 `#v1` 头会拒绝解析并提示"台账损坏，请检查"（比写端反复 stat 更划算）。

**调用时机（这里有个坑，必须按下面写）**

挂载点：`Plugin::TickStateMachine()`（源码 **24051** 行），由 `TickStateMachineBridge`（59 行）驱动。

⚠️ **tick 不是 1 Hz**：`TickStateMachineBridge` 有自适应节流 ——

```cpp
const int skip = g_active_plugin->GetTickSkipFrames();   // 63 行
if (++g_tick_skip_counter > skip) { … TickStateMachine(); }
```

**有玩家活跃时是全速（每帧，~60 次/秒）**，全员静止才降到 ~1 Hz。
所以 `HistFlush` **不能假设自己被 1 Hz 调用**，必须用 `next_flush_ms` 自己做时间门禁（见上代码 ①②）。
否则"零开销"不成立：每帧都要抢锁 + 可能每帧 stat 磁盘。

**结论**：`TickStateMachine()` 内先算一次 `const long long now_ms = NowEpochMs();`，然后
`HistFlush(tomb_hist_, now_ms); HistFlush(borrow_hist_, now_ms);` —— 两次调用在未到窗口时都是**纯比较 + 返回**。

**读回：插件侧不提供读回命令**（§16 已否决）。

前端直接 `GET /dino-data/<Abbr>_tomb_history.tsv` 读全量再切页 —— 文件只有几 KB～几 MB，
比"插件 seek 尾部 + 游标分页 + 字节预算自截断 + `brief` 精简模式"简单得多，也少一整类截断 bug。

### 14.4 采集点与"详细字段"（全部取自现有变量，不新增遍历）

#### 14.4.0 字段清洗（**所有列写入前必须过，否则前端会错列**）

TSV 的致命弱点是"一个非法字符毁一行"。部落名、玩家名、墓碑自定义名都是玩家可输入的自由文本，
**必须**在拼行之前清洗：

```cpp
// 把会破坏 TSV 结构的字符换成空格；同时限长，避免单行超 RCON/日志的 4 KB
inline std::string HistCell(const std::string& s, size_t max_len = 96) {
    std::string o;
    o.reserve(s.size());
    for (unsigned char ch : s) {
        if (ch == '\t' || ch == '\r' || ch == '\n') o.push_back(' ');
        else if (ch < 0x20) o.push_back(' ');        // 其它控制字符
        else o.push_back(static_cast<char>(ch));
    }
    if (o.size() > max_len) { o.resize(max_len); }   // 按字节截断；中文可能截半
    return o;
}
```

| 规则 | 说明 |
|---|---|
| `\t` / `\r` / `\n` → 空格 | 否则一次 `split('\t')` 就错列 |
| 其它 `< 0x20` 控制字符 → 空格 | 防止终端/日志渲染异常 |
| 单列长度上限 | 建议 **96 字节**（中文 32 字），超出截断 |
| 数值列 | 一律**空串**表示"无值"，不要写 `-` / `null` / `NaN` |
| 数值精度 | 坐标保留 **2 位小数**（`snprintf("%.2f")`），避免 `-265489.59000001` 这种噪声 |
| 引号 | **不加引号**（TSV 无引号语义），清洗后内容里的 `"` 保留即可 |

> 字节截断可能切到半个汉字 —— 前端 `TextDecoder` 默认 `fatal:false` 会渲染成替换符，
> 不影响其余列解析。若要更严谨，在 `HistCell` 里回退到 UTF-8 字符边界（多 6 行代码）。

### 14.5 性能预算与红线

| 项 | 预算 |
|---|---|
| 游戏线程每次记录开销 | 一次字符串拼接 + 一次 mutex 入队（**微秒级**），无磁盘、无遍历 |
| 刷盘频率 | 有事件时每 5 s 一次；无事件时 **0 次**（`buf.empty()` 直接返回） |
| 单次刷盘量 | 正常 1~5 行；极端 4096 行上限 |
| 内存占用 | 缓冲上限 4096 行 × ~350 B ≈ **1.4 MB 最坏**，常态 0 |
| 启动成本 | 仅当行数超 `history_max_rows` 时做一次裁剪重写 |

**红线（不可违反）**

1. 游戏线程**禁止**任何文件 IO / 目录遍历
2. 记录点**禁止**为了凑字段去遍历 actor 列表或调昂贵 API（字段只能取现有变量 + 最多一次 `GetActorLocation`）
3. **禁止**存裸指针（`BORROW_RESTORE ptr=` 就是反例）
4. 写失败**不得重试风暴**：连续 5 次失败自动停用 + 打一条 `HIST disabled` 告警
5. 时间一律 `NowEpochMs()`，**禁止** `steady_clock`
6. **所有文本列必须过 §14.4.0 的 `HistCell()`**：未清洗的自由文本（部落名/玩家名/自定义名）会直接毁掉整行 TSV
7. **tag 为空时禁止落盘**：不得像 `wx_history` 那样兜底写无后缀文件（否则 10 服互覆盖，历史已踩过）
8. `HistFlush` **必须在取锁前判时间门禁**：`TickStateMachine()` 可能是每帧调用（~60 Hz），不能假设 1 Hz

| `history_flush_interval_seconds` | `5` | 刷盘节流 |
| `history_max_rows` | `20000` | 超过后启动时裁剪 |
| `history_record_denied` | `false` | 是否记录"被拒/冷却"（噪音控制） |

**`history_max_rows` 对应的磁盘占用**：20000 行 × ~350 B ≈ **7 MB/服**，11 服最坏 **77 MB**。
真实数据量远小于此（§14.1：墓碑 <100 KB/天、租借 <20 KB/天），即使 90 天也只有几 MB。
调小该值可直接压缩上限（如设 2000 ⇒ 0.7 MB/服）。

### 15.1 三条路线对比（先选路线，再写代码）

### 15.2 路线 A：直接 GET 静态 TSV（零后端改动，首选）

#### 15.2.1 请求

```
GET /dino-data/<Abbr>_tomb_history.tsv
GET /dino-data/<Abbr>_borrow_history.tsv
```

- `<Abbr>` 取值：`Bob` / `Isl` / `Sco` / `Cen` / `Abe` / `Ext` / `Ast` / `Rag` / `Val` / `Los` / `Gen`
- 无需鉴权（与其它 `/dino-data/*` 一致）
- **不返回 304** ⇒ 增量判断**一律用 `/dino-data/_lm.json` 的 mtime**，不要靠 `If-Modified-Since`

#### 15.2.2 文件格式（严格按此解析）

- 第 1 行是**版本头**，以 `#` 开头：`#v1<TAB>ts<TAB>kind<TAB>teamId<TAB>…`
- 其后每行一条记录，列序**与版本头完全一致**，字段用 **`\t`（U+0009）** 分隔
- 编码 **UTF-8**（中文部落名/玩家名可直接读）
- **字段内不会出现 `\t` 和换行**（插件写入前按 §14.4.0 清洗）⇒ 可以安全 `split('\t')`
- 数值列空串 = 无值（不是 0）；坐标保留 2 位小数
- 文件**按时间升序**追加（最新在最后一行）

#### 15.2.3 解析代码（可直接抄）

```js
const LS = 0x09;
function parseHistoryTsv(text) {
  const lines = text.split(/\r?\n/).filter(s => s.length);
  if (!lines.length) return { cols: [], rows: [] };
  if (lines[0][0] !== '#') throw new Error('bad header');
  const cols = lines[0].replace(/^#v\d+\t/, '').split('\t');
  const rows = [];
  for (let i = 1; i < lines.length; i++) {
    const f = lines[i].split('\t');
    // 列数不符：v2 加列时旧前端也不能整表丢，按 header 长度截断/补齐
    if (f.length < 2) continue;                  // 只有 1 列的肯定是坏行
    if (f.length < cols.length) { while (f.length < cols.length) f.push(''); }
    else if (f.length > cols.length) { f.length = cols.length; }
    const o = {};
    cols.forEach((c, k) => { o[c] = f[k]; });
    // 数值列转 number
    ['ts','teamId','movedCount','x','y','z','origTribeId','borrowerTribeId','expireAtMs']
      .forEach(k => { if (k in o) o[k] = o[k] === '' ? null : Number(o[k]); });
    rows.push(o);
  }
  return { cols, rows };
}

// 倒序分页（前端做）：取第 page 页、每页 size 条
function pageDesc(rows, page = 1, size = 50) {
  const end = Math.max(0, rows.length - (page - 1) * size);
  const start = Math.max(0, end - size);
  return rows.slice(start, end).reverse();       // 最新在前
}
```

#### 15.2.4 增量刷新（关键，别每 3 秒拉一次）

```js
let lastSeen = null;
async function pollHistory(abbr) {
  const lm = await (await fetch('/dino-data/_lm.json', {cache:'no-store'})).json();
  const stamp = lm[`${abbr}_tomb_history.tsv`];
  if (!stamp || stamp === lastSeen) return;      // 没变就不拉文件
  lastSeen = stamp;
  const txt = await (await fetch(`/dino-data/${abbr}_tomb_history.tsv`, {cache:'no-store'})).text();
  render(parseHistoryTsv(txt));
}
// 建议 30~60 s 轮询一次 _lm.json 即可（台账是低频数据，没有实时性需求）
```

> 为什么不用 `If-Modified-Since`：`/dino-data/*` **不返回 304**，会白拉整个文件。

### 15.3 路线 B：走 RCON 命令（**已否决 —— 论证存档，不再实现**）

> **结论（2026-11-14）**：`TombHistory` / `BorrowHistory` 命令**不实现**。
> 保留本节是为把"为什么不做"讲清楚，避免后来人重复试错；技术分析本身仍然成立。

#### 15.3.1 命令语法（假设实现时的形态）

#### 15.3.3 ⚠️ 300 字符截断 + 4 KB 单包（这是必须遵守的硬约束）

两个限制叠加，结论比早前更严格 —— **走通用 `/api/srvctl/rcon` 通道连 1 条都拿不到**：

| 限制 | 值 | 后果 |
|---|---|---|
| `/api/srvctl/rcon` 响应截断 | **300 字符** | **关键瓶颈** |
| RCON 单包 | 约 **4 KB** | 插件侧硬上限，超过必然拆包/丢包 |

**算一笔账**（2026-11-14 复核修正，早前"单条 210 字符"估算偏低）：

```
外层包装 {"ok":true,"ledger":"tomb","count":1,"hasMore":true,"nextBeforeTs":1763099000000,"items":[…]}  ≈ 100 字符
单条记录（16 字段，中文部落名 + 坐标 2 位小数）                                                        ≈ 260 字符
合计                                                                                                  ≈ 360 字符  >  300
```

⇒ **`TombHistory 1` 走通用 rcon 通道仍会被截断成非法 JSON**。早前写"约 10~15 条"是错的。

**因此（硬结论）**：
1. **路线 B 只有在"后端提供专用转发接口"（= 路线 C）时才真正可用**；不能靠通用 rcon 通道
2. 若短期不想动后端，插件端可提供**精简模式** `TombHistory <limit> <beforeTs> brief`
   —— 只返 `ts,kind,teamId,result`，单条约 70 字符，`limit=2` 才勉强塞进 300 字符；**仅够做"最新一条"提示**
3. 插件端正常模式按字节预算自截断（约 3.5 KB），并在 `count` / `hasMore` 如实反映
4. **要看完整列表 → 必须走路线 A（静态 TSV）**

```js
async function fetchHistory(abbr, kind, limit = 20, beforeTs = null, token) {

```

### 15.4 路线 C：后端专用转发接口（**台账不用**；租借 `BorrowList` 仍需）

> 台账部分已随路线 B 一并否决（§16）。下面的规格**只对租借实时列表 `BorrowList` 有效**。

| 项 | 规格 |
|---|---|
| 方法/路径 | `GET /api/tif/history` |
| 鉴权 | 需 token（与 `/api/srvctl/rcon` 同级） |
| 参数 | `server=<Abbr>&kind=tomb\|borrow&limit=1..50&beforeTs=<ms,可选>` |

#### 15.8.9 A 档：前端可自行推导的字段（**无需插件改动，已实测验证**）

以下 4 个字段台账里是空的，但**前端用现有 `_cryo.json.gz` 就能算出来**（2026-11-14 Cen 实测）：

| 台账缺失字段 | 推导源 | 实测验证结果 |
|---|---|---|
| 墓碑 `tribeName` | `cryo.tribes[String(teamId)].name` | ✅ `1181886739` → **"人类的部落"** |
| 墓碑 `tombName` | 落点 `x`/`y` → 最近的 `structures[]`（`class` 含 `Gravestone`，阈值 400）→ `.name` | ✅ 距离 282.8 可匹配 |
| 租借 `origTribeName` | `cryo.tribes[String(origTribeId)].name` | ✅ `1228031745` → **"鱼人族"** |
| 租借 `borrowerName` | `cryo.players[]` 里 `eosId` 匹配 → `.name` | ✅ → **"whiter.rober"** |

**可直接抄的代码**

```js
// 1) 载入 cryo.json.gz 后建索引（每次文件更新重建一次即可）
function buildCryoIndex(cryo) {
  const tribeById = cryo.tribes || {};          // ⚠️ dict: "1181886739" -> { name, members: [...] }
  const playerByEos = {};
  (cryo.players || []).forEach(p => {           // ⚠️ players 是数组
    if (p.eosId) playerByEos[p.eosId.toUpperCase()] = p;
  });
  const tombs = (cryo.structures || []).filter(s => /Gravestone/i.test(s.class || ''));
  return { tribeById, playerByEos, tombs };
}

// 2) 墓碑 tribeName
const tribeName = idx.tribeById[String(rec.teamId)]?.name ?? '-';

// 3) 墓碑 tombName（落点 -> 最近墓碑，阈值 400）
//    注意：玩家没给墓碑起名时 name 本身就是空字符串 -> 返回 '-'
function tombNameOf(rec, idx) {
  if (!rec.x && !rec.y) return '-';
  let best = null;
  for (const t of idx.tombs) {
    const d = Math.hypot((t.x || 0) - rec.x, (t.y || 0) - rec.y);
    if (d < 400 && (!best || d < best.d)) best = { d, t };
  }
  return best?.t.name || '-';
}

// 4) 墓碑 playerName / eosId（0.9.0 起：优先用 eosId 列，回退到 charId）
function playerOf(rec, idx) {
  // ① 0.9.0 起 manual_player 行自带 eosId（auto 行在线玩家也有）
  const eosCol = String(rec.eosId || '').toUpperCase();
  if (eosCol) {
    const p = idx.playerByEos[eosCol];
    return { name: p?.name || p?.characterName || '-', eos: eosCol };
  }
  // ② 回退：auto 行用 charId 去 tribes[].members[] 找
  const pid = String(rec.charId || '');
  if (!pid) return { name: '-', eos: '-' };
  const m = (idx.tribeById[String(rec.teamId)]?.members || [])
              .find(x => String(x.pid) === pid);
  return { name: m?.name || '-', eos: m?.eosId || '-' };
}

// 5) 租借 origTribeName / borrowerName
const origTribeName = idx.tribeById[String(rec.origTribeId)]?.name ?? '-';
const borrowerName  = idx.playerByEos[(rec.borrowerEosId || '').toUpperCase()]?.name ?? '-';
```

#### 15.8.10 C 档：物品分类（`movedEquipment/Pods/Relics`）的替代方案

**插件为什么没记**（有意取舍）：

- 需要**遍历物品**并读 `UPrimalItem` 的**类名**来判定"装备/低温仓/遗物"
- 而**全项目现有代码里没有任何一处**读过 `item->ClassPrivateField()`
- ⇒ 等于在"每次死亡转移"的**高频路径**上引入一个**未经验证的原生 API 调用点**，
  物品处于异常状态时有**崩服风险**，而收益只是 3 个统计数字

**替代方案：用 `_item.json.gz` 查"当前有什么"（前端实现，零风险）**

```
GET /dino-data/<Abbr>_item.json.gz
```

| 能回答 | 不能回答 |
|---|---|
| 这个**包/箱子现在**装了什么 | 当时**搬进去的是什么**（历史快照无从追溯） |

**结论**：

- 需求是「**查看某个容器现在有什么**」→ 用 `_item.json.gz`，不需要改插件
- 需求是「**历史记录里写明当时搬了 2 件装备 + 1 个球**」→ 只能接受留空，
  或接受"插件端加物品分类"的崩服风险（需要 1–2 轮试错编译 + 重启）

#### 15.8.12 租借状态反推规则（历史台账兼容 + 0.9.2 后简化）

**0.9.2 之前的问题**：`manual_restore` 的 `cancel_all` / `cmd` / `rcon` 三种，以及 `auto_restore`，
`structKey` 列是**空的**——因为一次归还多台，单个 key 表达不了。

**0.9.2 起已修**：归还改为**逐台写行**，每行都有 `structKey` + 坐标 + 借用者 EOSID，
因此新数据只需按 `structKey` 直接 `delete` 即可，不必再做"全量清空 / 到期子集"的特判。

**但历史行（0.9.1 及更早）仍然 `structKey` 为空**，所以下面的回放代码保留兼容分支。

##### 四种归还形态对照（源码核实，2026-11-14）

| `action` | `reason` 里的 trigger | `structKey`（0.9.2 起） | 历史行（≤0.9.1） | `reason` 里的 `by=` |
|---|---|---|---|---|
| `manual_restore` | `cancel_toggle` | ✅ 有值 | 0.9.0 起有值 | 玩家 EOSID |
| `manual_restore` | `cancel_all` | ✅ 有值（逐台各一行） | **空**（一行汇总） | 玩家 EOSID |
| `manual_restore` | `cmd` | ✅ 有值 | **空** | 命令发起者 |
| `manual_restore` | `rcon` | ✅ 有值 | **空** | 字面量 `rcon` |
| `auto_restore` | `expire` | ✅ 有值 | **空** | 字面量 `system` |

> ⚠️ 只有 `expire` 不是全量：`RestoreBorrows(false, now)` 里有
> `if (!manual && now_b < it->expire_ms) continue;`，未到期的不动。
> 但被还掉的那几台可以用 **`expireAtMs <= 该行 ts`** 精确算出来，因此仍可还原。

##### 可直接抄的回放代码

```js
// rows: parseHistoryTsv() 的结果（时间升序）
// serverStartedAtMs: 后端 /api/health 的 startedAt（可选，但强烈建议传）
function replayBorrows(rows, serverStartedAtMs) {
  const active = new Map();   // structKey -> { rec, since }

  for (const r of rows) {
    // ① 服务器重启 = borrows_ 内存清空 = 隐式全量归还
    if (serverStartedAtMs && r.ts < serverStartedAtMs) { active.clear(); continue; }

    if (r.action === 'borrow') {
      const key = r.structKey || `${r.structClass}@${r.ts}`;   // 旧数据无坐标时兜底
      active.set(key, { rec: r, since: r.ts });
      continue;
    }

    if (r.action === 'manual_restore') {
      if (r.structKey) active.delete(r.structKey);   // 0.9.2 起：逐台行，直接删
      else active.clear();                           // 兼容 ≤0.9.1 的全量汇总行
      continue;
    }

    if (r.action === 'auto_restore') {
      if (r.structKey) { active.delete(r.structKey); continue; }   // 0.9.2 起
      // 兼容 ≤0.9.1：只还到期子集，用 expireAtMs <= 该行 ts 判定
      for (const [k, v] of [...active]) {
        if (Number(v.rec.expireAtMs || 0) <= r.ts) active.delete(k);
      }
      continue;
    }
  }
  return [...active.values()];
}
```

##### `BorrowList` 与台账反推的分工（两个都要用，不互相替代）

| 需求 | 用哪个 | 原因 |
|---|---|---|
| 看**现在**谁借了、还剩几秒、在哪个坐标 | **`TransferIdentityFix.BorrowList`** | 内存实时数据，权威；含 `remainSec` |
| 画**历史**（谁什么时候借、多久还的） | 台账 + `replayBorrows()` | 台账是事件流，含完整时间线 |
| 服务器重启后老数据对不上 | 台账 + `startedAt` 分界 | 重启即 `borrows_` 清空，重启前的借用一律视为失效 |

##### 三个必须注意的点

| # | 注意 | 后果 |
|---|---|---|
| 1 | **重启 = 隐式全量归还**，台账里没有"重启"这一行 | 不处理 `startedAt` 会把已失效的借用一直显示为"占用中" |
| 2 | `structKey` 可能是空的（0.8.9 之前的历史行） | 用 `${structClass}@${ts}` 兜底成唯一 key，避免互相覆盖 |
| 3 | `expire` 不是全量 | 若当成 `active.clear()`，会把未到期的借用也误删 |

## 16. 新增 RCON 命令的必要性评估（结论：4 → 1）

> 起因：实施前复核"到底该加几条命令"。结论是原设想 4 条里**只需 1 条**，
> 另有 1 条现有命令**改返回即可**。本节保留完整论证，供后续复用判断标准。

### 16.1 评估前先纠正三处事实错误（源码实测）

| 文档早前表述 | 实测结果 | 影响 |
|---|---|---|
| "18+ 条命令里没有任何 borrow 相关" | 现有 **66 条** `RegisterRconCommand*` 唯一命令（59 条带 `TransferIdentityFix.` 前缀 + 7 条别名）；`TransferIdentityFix.Borrow` / `BorrowRestore` 确实存在，但它们走另一套分发（`HandleCommand` 里的 `if (name == ...)` 字符串比较，无 `RCONClientConnection`），因此**不在上述 66 条之内**，也无法返回结构化 JSON | 命令清单基线错了 |
| "远程强制归还/取消 ❌ 做不到" | **错**。`BorrowRestore` 就是强制归还（`RestoreBorrows(manual=true)`，归还**全部**） | 该能力已具备 |
| "需新增 `BorrowRelease <all\|index>`" | `<all>` 与 `BorrowRestore` **100% 重复** | 不必要 |

> 教训：**"没有"这个结论必须先去源码数命令**，不能凭印象。
> **66 条** `RegisterRconCommand*` 的完整清单可用 `grep 'RegisterRconCommand' | sort -u` 得到；
> 另需单独 grep `if (name == "tif.` 才能看到 `HandleCommand` 那一套聊天命令。

### 16.2 逐条论证

#### `BorrowList` —— 必做（唯一不可替代）

| 判断维度 | 结果 |
|---|---|
| 现有命令可替代？ | **否**。66 条注册命令 + `HandleCommand` 的 `tif.*` 里没有一条能列借用状态 |
| 有其它数据出口？ | **否**。`borrows_` 是纯内存 `vector`，不写文件、不进任何 JSON |
| 数据量是否超 RCON 单包？ | 几十条 × ~200 B ≈ 数 KB，**4 KB 单包勉强**，必须分页 |
| 结论 | **新增**（代价：1 条命令 + 分页） |

#### `BorrowRestore` 补 JSON —— 必做（但不新增命令）

| 判断维度 | 结果 |
|---|---|
| 现有行为够用吗？ | 业务逻辑够（真能归还），但原**只 `ChatSend`**，程序读不到 `released`（✅ 0.9.1 已补 JSON） |
| 改造成本 | **约 4 行**（两处 `SendRconResponse`），行为零变更 |
| 为什么比"新增 `BorrowRelease`"好 | 不增加命令面、不重复实现归还逻辑、不引入"两个命令做同一件事"的维护风险 |
| 结论 | **改返回，不新增命令** |

#### `TombHistory` —— 不做

| 判断维度 | 结果 |
|---|---|
| 有替代出口？ | **有**。日志改成追加型 TSV 后，就是静态文件 `GET /dino-data/<Abbr>_tomb_history.tsv` |
| RCON 通道能承载吗？ | **不能**。单条 16 字段 ≈ 260 字符 + 包装 ≈ 360 > **300 字符截断** ⇒ 连 1 条都拿不到 |
| 命令能带来什么静态文件做不到的？ | 几乎没有。文件只有几 KB～几 MB，前端读全量再切页完全可行 |
| 不做的收益 | 省 1 条命令、省约 80 行（尾部 seek + 游标 + 字节预算自截断 + `brief` 精简模式）、省"截断边界"一类 bug |
| 结论 | **不做** |

#### `BorrowHistory` —— 不做

同 `TombHistory`。且租借记录量更小（<20 KB/天），静态文件代价更低。

### 16.3 判断标准（可复用到以后）

遇到"要不要新增 RCON 命令"，按顺序问四个问题：

| # | 问题 | 若"是" |
|---|---|---|
| 1 | **现有命令里真的没有等价物吗？**（必须实际 grep，且要同时查 `RegisterRconCommand*` 与 `HandleCommand` 两套分发，不能凭印象） | 先复用/改造 |
| 2 | **数据能不能落到静态文件让前端直接读？** | 优先文件，命令次之 |
| 3 | **返回体能否塞进 300 字符**（`/api/srvctl/rcon` 截断）？<br>塞不进就要后端加专用接口 | 加接口 = 隐性成本，要一起算 |
| 4 | **它是一次性查询，还是需要写操作 + 即时确认？** | 只有写操作要即时反馈时，命令才明显优于文件（≤5 s 延迟） |
