## 1. 需求

用户口径（2026-11-11）：

1. **要能查看玩家传服路径**，并且**标注各个服停留期间是否有档**（有档 = 该服在该时间段存在可用回档点）。
2. **要能查看档内玩家背包内容与当前档的差异**（2026-11-11 改口径：原为「占用格数」，现改为对比差异 —— 回档会丢什么、会回来什么）。

性质：**纯只读查询能力**，不新增任何写档 / 停服 / 启服动作。回档执行链路（`plan` / `execute` / `rollback`）完全不动。

### 1.1 验收目标（一句话版）

- 输入一个玩家（角色名 / 账号名 / eosId / pid），能拉出「他在哪几台服待过、每段起止时间、每段该服有没有档、最近可用档是哪一个」。
- 选中「某个服 + 某个回档点 + 某个玩家」，能显示「回档后他的背包会失去 / 会回来哪些物品，各自差多少」，并附一行「现 N 格 → 档内 M 格」。

## 2. 现状盘点（可直接复用的资产，均已实测）

### 2.1 能力 A 的数据源已经齐全

| 需求元素 | 现成来源 | 位置 |
|---|---|---|
| 玩家**进出各服**的流水 | `Full_Serveur_Backup\PlayerProfile\connect-*.zip` / `disconnect-*.zip`（只读文件名，几百个文件毫秒级） | `ark_backup.py::read_presence(abbr)` → `players[eosId].events[{kind,ts}]`，已按 ts 升序，**上限 40 条** |
| 玩家**拥有哪些角色（pid）**、在哪些服 | 各服 `<Srv>_cryo.json.gz` 的 `players[]` | `ark_backup.py::pid_index(servers)` → `{pid: [服...]}` |
| 某服**有哪些回档点** | 地图目录内 `*.ark` / `*.arkrbf` + 自建 `pre_restore.ark` + legacy 档 | `ark_backup.py::list_points(abbr)`（不算 sha256，毫秒级） |
| 回档点**时间戳** | `points[].tsEpoch` / `rbf[].tsEpoch` / `legacy[].tsEpoch` / `ownBackup.tsEpoch` | 同上 |
| 档内**角色是否存在** | `ark_save_reader.exe <档> <出> <服> light` → `players[]` | `ark_backup.py::run_exe(ark_abs, abbr, out_base=...)`（已有 600s 结果缓存 + 串行 `_EXE_LOCK`） |

### 2.2 能力 B 的数据源已经齐全（关键结论）

`<Srv>_item.json.gz`（插件每次存档后由 exe 全量导出）中，每条物品自带容器归属：

| 字段 | 用途 |
|---|---|
| `containerType` | 取值含 **`player`** —— 只取这一类即「玩家背包」 |
| `playerName` | 仅 `player` 容器有值 → 直接定位到人 |
| `containerId` | 同一容器所有堆共用 → **distinct 计数 = 占用格数** |
| `class` / `quantity` / `durability` / `qidx` 等 | 明细下钻 |

⇒ **当前档的背包格数不需要改 exe、不需要新解析器**，直接读现成 gz 即可。
⇒ **历史档**（任一 `.ark` 快照）目前只有 `light` 调法（只出 `players`+`tribes`），要算格数必须**全量跑**（见 §4.3）。

### 2.3 🔴 时间基准陷阱（务必写进代码注释）

| 来源 | 时间基准 |
|---|---|
| `.ark` 快照文件名 `_DD.MM.YYYY_HH.MM.SS` | **UTC** |
| `PlayerProfile\connect-/disconnect-YYYYMMDDHHMMSS` | **本地时间**（实测文件名时间 == 文件 mtime） |
| `points[].tsEpoch`（`list_points` 内部） | 已统一成 epoch（按 UTC 解析） |
| `read_presence().events[].ts` | 已统一成 epoch（按本地时间解析） |

⇒ 两侧都是 epoch 即可安全比较；**但绝不能拿原始字符串互相比大小**，也不能把两套解析函数混用。

### 2.4 已知限制

- `read_presence` 每玩家 `events` **只保留最近 40 条**（防老服流水膨胀）⇒ 传服路径首段可能"从中间开始"，前端必须显式标注「更早记录已截断」。
- `read_presence` 的时间来自文件名；同一玩家**同名不同 eosId** 是两个玩家，不能按 `name` 聚合。
- 一个玩家可有**多个 pid**（`pid` 跟角色走，角色级唯一、跨图稳定；`eosId` 跟玩家走）⇒ 传服路径按 **eosId** 聚合，回档冲突按 **pid** 比对（沿用原方案 §5.5.3）。
- Bob（BobsMissions）在安全回档浮窗里**不显示**（`app_core.js` v6035 既有口径），传服路径同样排除，但要在时间轴上提示「该时段曾在 Bob，本模块不覆盖」。

## 3. 能力 A：玩家传服路径 + 停留段是否有档

### 3.1 数据模型

```
Trace(eosId, name)
 └─ characters: [{pid, characterName, servers:[...]}]        ← pid_index + cryo players
 └─ segments: [                                              ← 本次新增
      {
        server: 'Ext',                                        ← 服缩写
        tIn:  1730784000, tOut: 1730822400,                   ← epoch；tOut 可为 null（未闭合）
        tInStr/tOutStr,                                        ← 展示用（本地时间）
        open: false,                                          ← true = 至今仍在 / 缺 disconnect
        closeReason: 'disconnect' | 'inferred' | 'open',
        hasSave: 'inside' | 'near' | 'none',                   ← 🟢/🟡/🔴
        points: [                                             ← 该服档点（裁剪后）
          {id, kind, name, tsEpoch, ts, mb, deltaSec, role:'inside'|'before'|'after'}
        ],
        best: {id, tsEpoch, deltaSec} | null,                 ← 推荐回档点（|delta| 最小且不晚于 tOut）
        pidVerified: null | true | false                       ← 深检后才有值
      }
    ]
```

### 3.2 停留段构造算法

对每台服取 `read_presence(abbr).players[eosId].events`（已按 ts 升序），做**栈式配对**：

1. 遍历 events：
   - `connect` 且当前无开启段 → 开段 `{server, tIn=ts}`
   - `disconnect` 且当前有开启段 → 闭段 `{tOut=ts, closeReason='disconnect'}`
   - 连续 `connect` → 视为「断线重连 / 无 disconnect 记录」：闭段 `tOut=ts, closeReason='inferred'`，立刻开新段
     > **用户口径（2026-11-11，重申两次）**：
     > - 有 `disconnect` 记录 = 玩家**传图走了**（跨服传送 / 上传角色）→ 文案「**传图 HH:MM**」
     > - 没有记录 = **没传图直接下线**（关游戏 / 掉线 / 崩溃都不生成记录）→ 文案「**下线 HH:MM 前**」（时间只能给上界）
     > - open 段 → 「至今在线 / 下线时间未知」
     > ⛔ 禁止把两种情况都写成「下线」—— 这直接把「传图」这个关键信号丢了。
     > 💡 **设计价值**：`disconnect` 记录其实是「该玩家确实从这里传走了」的**硬证据**，是「传服路径」连线的锚点（本服离开时刻 + 目标服进入时刻 = 一次传服）。
2. 遍历结束仍有开启段 → `open=true`，`tOut=null`（展示「至今 / 未知」）
3. 跨服合并成一条时间轴，按 `tIn` 升序；相邻段之间若有空档，标 `gap`（该玩家在两服之外，可能离线）
4. 首段若 `events` 长度达到 40（触顶）→ 标 `truncatedBefore=true`

> 深检可选（L2）：对同一 eosId 在 `pid_index` 里有多个 pid 时，segment 上挂该服命中的 pid 列表，展示「在本服的角色：板板(pid=288266681)」。

### 3.3 「是否有档」两级判定

**L1 时间近似（免费，默认走这条）**
取该服 `list_points(abbr)` 的全部档点（`points` + `rbf` + `ownBackup` + `legacy`），对每段 `[tIn, tOut]`：

| 等级 | 判据 | 标注 |
|---|---|---|
| `inside` | ∃ 档点 `tIn ≤ ts ≤ tOut`（open 段的 tOut 视为 now） | 🟢 窗口内有档 |
| `near` | 否则 ∃ 档点 `ts ∈ [tIn - 6h, tOut + 6h]`（open 段只看 tIn - 6h 之后） | 🟡 仅邻近档（需人工确认） |
| `none` | 以上都不成立 | 🔴 无档（该段不可回） |
| `nodir` | `list_points` 返回 `mapdir_unknown` / `dir_missing` | ⚪ 该服档目录不可读 |

`best` 选取规则：优先 `inside` 里**离 tOut 最近**的档（回到该段结束前一刻最不伤进度）；无 `inside` 则取 `near` 里 |delta| 最小者。

**L2 精确校验（按需，点「深检」才跑）**
对 `best`（或用户手动选的档）调 `run_exe(档, 服, light)`，检查 `players` 里是否存在该 eosId 名下的 pid：

- 有 → `pidVerified=true`，标注「该档内确有此角色」
- 无 → `pidVerified=false`，标注「⚠ 时间匹配但档内无该角色（可能是传送中/该段是别的小号）」

> 成本：单档约 5 秒（本地盘）～数十秒（大档/UNC）。**一次只解析 1~2 个档**，不做批量。

### 3.4 边界与降级

| 场景 | 处理 |
|---|---|
| 某服 `PlayerProfile` 目录缺失 | 该服整段标记 `noPresence`，不影响其他服 |
| 某服 `cryo.json.gz` 过期（> 1800s） | 仍用，但 `pid_index` 侧标注 `ageSec` 供前端提示 |
| 玩家只在一台服出现 | 时间轴只有一段，正常展示，不做「传服」措辞 |
| 用户按 `name` 搜索命中多个 eosId | 列出候选让用户点选，不自动合并 |
| `list_points` 耗时 | 11 服全扫目录（毫秒级/服），可一次性并发；**不做 sha256** |

## 4. 能力 B：玩家背包内容差异（目标档 vs 当前档）

### 4.1 目标与方向（口径已于 2026-11-11 变更）

- **不再以「占用格数」为主视角**，改为「选定回档点 ↔ **当前线上档**」的背包内容差异
- **方向以当前档为基准**（用户定）→ 输出语义是：
  - 🔴 **回档后会失去**：现在有、档内没有
  - 🟢 **回档后会回来**：档内有、现在没有
  - 🟡 **数量会变化**：两边都有但数量不同
- **格数保留为一行小字**：`现 87 格 → 档内 63 格（-24）`；仍然**不做百分比、不显示上限**

### 4.2 差异口径（写死）

| 项 | 口径 |
|---|---|
| 比对范围 | 只该玩家的 `containerType === 'player'`（**主背包 + 快捷栏合并**后比较）；不含恐龙背包 / 箱子 / 冰柜 / 专储 |
| 聚合键 | **物品名**（`class` 去掉实例后缀，如 `PrimalItemResource_Metal_C`）；同名多堆**先求和再比**（exe 逐堆输出，例 300+200 → 500） |
| 输出三类 | `lost[]`（-N）/ `gained[]`（+N）/ `changed[]`（旧→新，Δ） |
| 零差项 | 默认**不列**；提供「显示未变化项」开关（默认关） |
| 分类汇总 | 按 `kind` 给一行：资源 Δ-320 · 消耗 Δ+45 · 弹药 Δ-60 …（供快速判断“丢了什么类型的东西”） |
| 格数小字 | `slots.cur` / `slots.point` / `slots.delta`，仅展示，不参与差异计算 |
| 不比对 | 耐久 / 品质 / 坐标（本需求只要「物品名字 + 数量」；逐堆明细留作后续） |

### 4.3 数据源分两条路

| 目标 | 数据源 | 是否要跑 exe |
|---|---|---|
| **当前档**（基准侧） | 现成 `DinoData\<Srv>_item.json.gz` | ❌ 不用，直接读 |
| **历史回档点**（对比侧，`auto:` / `rbf:` / `legacy:` / `own:pre_restore`） | 对该 `.ark` / `.arkrbf` **全量解析**一次 | ✅ 要，产物落 `_offline\` |

> 两侧必须**同一服**（跨服背包不可比）；`point=active` 时两侧相同，接口直接返回空差异。

### 4.4 历史档全量解析的代价与策略

- 现有调法：`run_exe(..., 'light')`（第 4 参任意值 = 只出 players/tribes，~1.5 KB）
- 全量调法（**待实测确认**）：去掉第 4 参（不带 `light`）→ 产物含 `cryopods` / `structures` / `facilities` / 物品，体积约 light 的 **7.6 倍**（本地实测口径）
- 成本：单档 ~5 秒（83 MB 本地盘）；Isl 100+ MB 档更久
- 策略：
  1. `_EXE_LOCK` 串行（exe 自身无 single-flight、会写同目录 `.db`/`.snap` 缓存，**必须串行**）
  2. 产物落 `DinoData\_offline\<服>__inv__<档名>.json`，**绝不覆盖线上 `<Srv>_item.json.gz`**
  3. 结果缓存键 = `绝对路径 + size + mtime`（沿用 `_EXE_CACHE` 思路），TTL 30 分钟
  4. **只在用户选中某个档时才解析该档**（用户 2026-11-11 明确：「选中某个档时才解析，千万别一次性解析完」）—— **禁止**任何形式的批量预解析 / 全服全档预缓存 / 后台自动排队跑全部档；一次请求只对应一个档
  5. 前端点击「背包差异」时带入 `server + point + player`，解析**就那一个档**，结果按需缓存以便重复打开不重算
  6. 差异计算在后端做完、只回聚合结果（不回全量物品），避免几 MB 的 JSON 走 CF
- 产物清理：解析完删 `.db` / `.snap`（复用 `_cleanup_exe_side`）

### 4.5 安全边界

- 全程 **只读**：不 stop / 不 start / 不 saveworld / 不 swap；与 `execute` 链路零耦合
- 权限：`lbRoleLevel() >= 3`（与安全回档浮窗一致）
- 速率：历史档解析走串行队列，队列长度上限 4，超限返回 `busy`

```json
  "changed": [{"name": "兽皮", "cls": "PrimalItemResource_Hide_C", "kind": "resource", "cur": 1200, "point": 900, "delta": -300}],
  "same": [],
  "note": "lost=回档后会失去；gained=回档后会回来；changed=数量变化；只统计玩家本人背包（不含恐龙背包）"
}
```

字段语义：
- `slots` 仅一行小字展示，**不参与差异计算、不给百分比**
- `summaryByKind` 按 `kind` 汇总（同一 kind 内 quantity 求和后做差）
- `lost` / `gained` / `changed` 三层互斥（某一物品只能落在其中一类）
- 中文名靠现有 `item_zh` 映射；缺失时回退 `cls`
- `baseline.fromItemGz=true` 时必须同时回 `ageSec`，前端要提示「基准数据生成于 N 分钟前」

## 7. 安全护栏

| 层 | 措施 |
|---|---|
| 1 | 两个接口**纯只读**：不 stop/start/saveworld/swap，不改任何 `.ark` |
| 2 | 产物只写 `DinoData\_offline\`，命名含 `__inv__` 前缀，绝不覆盖线上 `<Srv>_item.json.gz` / `<Srv>_cryo.json.gz` |
| 3 | exe 调用全局串行（`_EXE_LOCK`）+ 队列上限 4 + `creationflags=0x08000000` |
| 4 | 权限 `>= 3`；`server` 参数走白名单校验（防路径穿越：拒绝含 `/` `\` `..` 的值） |
| 5 | 历史档解析超时 150s（沿用 `run_exe` 默认），超时清理 `.db`/`.snap` 后返回 `exe_timeout` |
| 6 | 结果缓存键含 `size+mtime`，档被替换后自动失效（不会把旧解析结果套在新档上） |
| 7 | 前端 `trace` 若单服 400ms 未回，先渲染已完成部分（渐进渲染），不做全屏 loading |

1. **时区错配**（§2.3）→ 一旦混用，会把「有档」判成「无档」。缓解：两个解析函数各自归一到 epoch，加单元自测用例。

### 12.4.1 🔴 布局陷阱：新增块会把「可选回档点」列表挤成 0 高（实测）

`.arbk-list` 的样式是 `flex:1 1 auto; min-height:0; max-height:min(480px,60vh); overflow-y:auto`，`.tc` 又是固定高度 flex 列 —— 一旦新增块展开，**唯一可收缩的就是这个列表**，实测被压到 **4px**（整个回档点列表肉眼消失）。

正确做法（预览已验证）：
- 给 `.tc` 开 `overflow-y:auto; flex:1 1 auto; min-height:0`（整个内容区滚动）
- 给 `.arbk-list` 补 `flex:0 0 auto`（保持自身上限 480px，不再被压缩）
- 新增块本身**不要**自己限高（统一由 `.tc` 滚动），否则出现「两个滚动条」

> ⚠️ 这是临时预览补丁。正式实施时更稳的做法是：新增块默认折叠（折叠时不占高），展开时给 `.tc` 加一个 `.tc--scroll` 类统一控制，避免内联样式散落。
