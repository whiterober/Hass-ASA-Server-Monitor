## 一、需求定义

### 1.1 原始需求
在**聚落详情**的设施区，把当前**平铺**的设施 chips 按「**区域**」分组展示。

### 1.2 分组判据（用户原话数学化）
| # | 规则 | 数学表达 |
|---|---|---|
| 1 | 每个分组区域的设施**基本是同一个 z 坐标** | z 相近 |
| 2 | 分组依据 = **同一 z 坐标的离散聚集点**，并**高于该 z 坐标正向一定范围内**的区域 | 簇内 `z ∈ [base, base + TOL]`，**base 不向下扩张** |
| 3 | **基本不存在低于同一区域 z 坐标的设施还算在同一区域** | base 只升不降 ⇒ 天然满足 |
| 4 | *(2026-09-12 补充)* **同一个 z，但相对独立的两堆设施，算两个不同区域** | 层内再做 **x/y 平面聚类** |
| 5 | *(2026-09-12 补充)* **默认不命名**；若区域内有小型标识牌（木质/金属/Bob 等），**自动用标识牌命名** | 区域内查找 sign，取其文字 |

## 三、算法设计

### 3.1 总体流程（两级聚类）
```
输入：某聚落的全部设施 F = [{z, x, y, cls, name}]
① z 分层   → 得到 L 层（升序 + base 只升不降）
② 层内平面聚类 → 每层内用 lbDbscan(pts(x,y), eps_xy) 拆成若干「区域」
③ 区域命名 → 区域内查找命名源（sign > 自定义名 > 编号）
④ 渲染     → 按「层」分组，层内按「区域」分块，每块带区域标题
```

### 3.2 第 ① 步：z 分层（严格照搬用户第 2、3 点）
```js
function lbFacLayerize(items, tol) {          // items 已按 z 升序
  var layers = [], cur = null;
  items.forEach(function(it){
    if (cur === null || it.z > cur.base + tol) {
      cur = { base: it.z, zMin: it.z, zMax: it.z, items: [] };
      layers.push(cur);
    }
    cur.items.push(it);
    if (it.z > cur.zMax) cur.zMax = it.z;
  });
  return layers;
}
```
- **`base` 创建后不再更新** ⇒ 新层 base 必更高 ⇒ **低于本区基准者绝不并入**（用户第 3 点） ✅

### 3.3 第 ② 步：层内平面聚类（用户补充第 1 点）
```js
function lbFacSplitAreas(layerItems, epsXY, minPts) {
  var pts = layerItems.map(function(it, i){ return { x: it.x, y: it.y, _i: i }; });
  var clusters = lbDbscan(pts, epsXY, minPts || 2);   // 复用现有实现
  return clusters.map(function(clu){
    return { items: clu.map(function(p){ return layerItems[p._i]; }) };
  });
}
```
- **`epsXY` 建议 1500~2000**（远小于聚落聚类 8000，用于区分"同一楼层的两栋楼/两个房间群"）
- **`minPts = 2`**（单点独立成"零散"区，避免孤立设施被强行并入邻近堆）
- 可选增强：若簇内仍有大间隙，追加 `lbSplitOversize(clu, epsXY)` 二次拆分

#### 3.3.1 ⚠️ `epsXY` 实测校准（本次新增，**决定成败的关键参数**）

对两个大基地按不同 `epsXY` 实测「区域数」：

| 部落 | 设施数 | 层数 | eps800 | eps1200 | **eps1800** | eps2500 |
|---|--:|--:|--:|--:|--:|--:|
| `1621369181` | 366 | 9 | 55 区 | 39 区 | **27 区** | 24 区 |
| `1912594779` | 876 | 18 | 148 区 | 117 区 | 98 区 | **86 区** |

**关键结论**：
1. **即使 eps=2500，仍存在 24 / 86 个区域** ⇒ **「同一 z 下的独立设施堆」在真实数据中大量存在，用户补充需求 1 完全必要** ✅
2. **eps 过小 → 碎片化**：单层 66 设施在 eps=800 时裂成 14 区（明显过度）
3. **eps 过大 → 过度合并**：单层 159 设施在 eps=2500 时并成 1 区（丢失真实分区）
4. **参考尺度**（ARK 实际）：同房间储物箱间距 ≈200~400；房间/功能区间距 ≈1000~2000；独立建筑 ≥3000

**⇒ 推荐 `epsXY = 1800`（默认）**，并提供**自适应模式**（更稳）：
```js
// 自适应：以该层「最近邻距离」的中位数 ×30 作为 eps，夹在 [1200, 2500]
function lbFacAreaEps(items){
  var k = Math.min(items.length, 200), nn = [];
  for (var i = 0; i < k; i++){
    var best = Infinity;
    for (var j = 0; j < items.length; j++){ if (i === j) continue;
      var d = Math.hypot(items[i].x-items[j].x, items[i].y-items[j].y); if (d > 0 && d < best) best = d; }
    if (isFinite(best)) nn.push(best);
  }
  if (!nn.length) return 1800;
  nn.sort(function(a,b){ return a-b; });
  var med = nn[Math.floor(nn.length/2)];
  return Math.max(1200, Math.min(2500, med * 30));
}
```
> 说明：密集区自动收紧 eps、稀疏区自动放宽 ⇒ 避免"一个大基地被切成 148 块"或"独立两栋楼被并成一块"

### 3.4 第 ③ 步：区域命名（三级回退，用户补充第 2 点）
| 优先级 | 命名源 | 条件 | 示例 |
|--:|---|---|---|
| **1** | **标识牌文字** | 区域内存在 sign 且有文字 | 「龙舍 A 区」 |
| **2** | **设施自定义名** | 区域内设施带 `name`（非 `?`），**取出现最多者；同频取位置最靠中心者** | 「夹层」「建材」「L4」 |
| **3** | **默认不命名** | 都没有 | 显示为层标记，如「第 3 层 · 12 项」 |

- **标识牌归属**：sign 按其 `(x, y, z)` 就近归入区域（距离 ≤ `epsXY`）
- **多标识牌**：取**离区域几何中心最近**的一个；或按文本长度取最长的（可配置）
- **⚠️ 前置**：命名源 1 依赖后端补采（见 2.4）

### 3.5 呈现形态（建议）
```
▼ 第 5 层  z -2412 ~ -1513   91 项
   ├ 【夹层】  56 项      ← 区域标题（带命名源徽章：📛 自定义名 / 🔖 标识牌）
   ├ 【建材】  17 项
   └ 未命名    18 项
▼ 第 4 层  z -3980 ~ -2562  116 项
   └ ...
```
- 每个区域一个 `<details>`（默认展开最高层、其余折叠）—— 避免 100+ chips 一眼刷屏
- 区域标题右侧显示项数 + 命名源图标

**现状**（`lbSettlementBuildingName` L4153-4165）—— **墓碑与大型广告牌混在同一档**：

**目标**（墓碑降到大型广告牌与床之后）：

var billboard = cands.filter(s => /Sign_Large_Metal|Sign_Large_Wood|MetalSign_Large|WoodSign_Large/i.test(s.class));

## 十一、★ 性能评估与优化（2026-09-12 用户要求 2）

### 11.1 现存基础设施已高度优化（重要发现）
| 组件 | 优化情况 |

### 11.3 四项低开销保证措施
| # | 措施 | 做法 |
|---|---|---|
| 1 | **懒计算** | 仅在聚落详情展开时计算（与现有 `_fList` 构造同批），不对所有聚落预算 |

### 11.5 ★ 资源缓存上限修复（2026-09-12 v1029，用户报告“资源缓慢加载”）
