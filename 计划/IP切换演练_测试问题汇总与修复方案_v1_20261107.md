## 二、P0-1：verify 判据时序 bug（最优先）

### 现象
Abe 起服完成、日志已打出 `Server has completed startup and is now advertising for join`，但编排一直停在「等待服务器对外开放加入」（`phase=verify, pct=90`），直到 600 秒超时才判失败。

### 根因（已定位）
`_restart_tick()` 的 verify 分支：

```python
elif _restart_log_has_after(srv, (RESTART_VERIFY_NEEDLE,), st.get('verifyAt') or 0):
```

- `_restart_log_has_after()` 要求「含 needle 的日志行时间戳 **>= since_ts**」
- `verifyAt` 是 `_restart_startq_state(srv) == 'ok'` 时才设置的时刻 —— 即**启动队列收割完成**的时刻
- 队列收割本身就晚于 `advertising` 那一行（差十几~几十秒）
- ⇒ `广告行时间 < verifyAt` ⇒ **恒不成立** ⇒ 每台必卡 600s

**佐证**：
- Abe 日志 `advertising` 行 = `[2026.11.06-18.55.51]` = 本地 `02:55:51`（`_restart_line_ts` 用 `calendar.timegm` 按 UTC 解析，时间换算正确，不是时区问题）
- 日志仅 58 行，`RESTART_LOG_SCAN_LINES=400` 完全覆盖，不存在扫描不够
- 进入 verify 时 `st['startqAt'] = 0` 被清零 ⇒ 之后拿不到"下发起服"的时刻

### 修法（两方案对比，推荐 B）

**方案 A（局部修）**：在编排里把时间窗修对
1. 在 startq 分支下发队列**之前**记录一个不清零的 `st['bootReqAt'] = now`
2. verify 分支的 `since_ts` 改用 `st.get('bootReqAt') or st.get('verifyAt')`
3. 兜底：`RESTART_VERIFY_TIMEOUT` 超时前做一次「不带时间过滤」的复查

**方案 B（推荐 · 从根源统一）**：编排**不再自己扫日志**，直接信任启动队列的判定
- 队列 worker 已经用 `SRVCTL_BOOT_MARKS` 里程碑扫描判定 `advertising`（`done_boot = bool(marks.get('advertising'))`，pct=100）
- 编排只需轮询 `_restart_startq_state(srv) == 'ok'` 即可，**不重复实现第二套判据**
- 历史 done 清理的前提 **已具备**：`_srvctl_startq_new()` 入队时已执行
  `q['done'] = [x for x in q['done'] if x.get('server') not in add]`（约 L6621），无需新增代码
- 好处：全部功能（手动启动 / 回档后启动 / 编排起服）**只一个启动完成判据源**，不会再出现
  「队列说已完成、编排说还在等」这种自相矛盾
- `verify` 阶段可简化为：等 `_restart_startq_state(srv)` 变 `ok` → 直接进 `done`；`_restart_log_has_after` 仅作为诊断日志用，不再作为成功条件

> ✅ **已定（用户 2026-11-07）：采用方案 B。**

### 影响文件
- `独立后端/dino_backend.py`：`_restart_tick()` startq / verify 分支

### 验证方式
- 真跑一轮，观察 `restart.log` 应出现 `advertising OK <srv>`，且该台 `phase` 在 1~2 个 tick 内变 `done`
- 用已上线的 Abe 反向验证：修后不应再出现「日志有 advertising 但仍等待」

## 三、P0-2：多余的任务进度条

### 现象
编排运行时，任务列表除编排行外，还各自出现「存档后终止」与「启动」的独立进度条。

### 根因
编排内部复用手动路径，每次都新建任务行：
- `_restart_exec_saveworld()` → `_srvctl_run('ipwatch', [srv], 'saveworld', None)`
- `_restart_exec_savekill()` → `_srvctl_run('ipwatch', [srv], 'savekill'/'kill', None)`
- 起服 → `_srvctl_startq_new('ipwatch', [srv])`

### 修法
给这两个入口加 `silent=True`（或 `parent='restart'`）：
- 照样执行、照样回执给编排状态机
- **不建任务行**

### 风险与连带确认
1. `lbTaskAbort(server)` 依赖任务行 → 编排中止改走 `/api/tasks/abort {all:true}`（已存在）
2. 启动队列概览行 `heavyCount` 统计是否依赖任务行 → 需确认
3. 手动操作路径保持不变（默认 `silent=False`）

### 影响文件
- `独立后端/dino_backend.py`：`_srvctl_run()`、`_srvctl_startq_new()`、`_restart_exec_*`

## 四、P0-3：角标/状态不跟随更新

### 现象
编排把服停了/起了，界面服务器角标（在线/离线、玩家数、版本）不变化。

### 根因（已核实）
- 任务列表有轮询：`lbTaskSyncStart()` → `setInterval(lbTaskSync, 1500)`
- 服务器状态**没有轮询**：`/api/srvctl/status` 只在 `lbSrvCtlFetch()` 显式调用时拉（开窗 / 手动操作后 2 秒 / 个别事件）

### 修法
前端检测「任务列表存在 restart 行且非终态」时，把 `lbSrvCtlFetch()` 调频到 5~10 秒；任务结束后恢复。与 P1-2 合并成一个「活跃态轮询」机制，避免各处单独加定时器。

### 影响文件
- `app_core.js`：`lbTaskSync()` / `lbSrvCtlFetch()`

## 八、P2-1：并发优化（存档停服段）

### 现状（先厘清：哪一段真的串行）

| 编排阶段 | 是否并发 | 说明 |
|---|:---:|---|
| 公告 / 宽限期 | ✅ 并行 | 11 台各自独立计时 |
| **起服** | ✅ 已复用 | `_srvctl_startq_new('ipwatch',[srv])` 进**全局启动队列**，天然吃重压池 ≤2 |
| **存档 → 校验 → 停服** | ❌ 严格单台 | **不经过启动队列**，跑在编排自己的状态机里：`_restart_tick()` 取 `_cands[0]`，`_RESTART['current']` 只有一个值 |

> ⚠️ 措辞澄清（用户 2026-11-07 质疑）：三个功能**确实共用同一个全局队列**（`_SRVCTL_STARTQ` + `SRVCTL_STARTQ_HEAVY_MAX=2`），所有 `start` 一律入队（v6014 起）。
> 所谓「未复用并发」**只指存档/校验/停服这一段**，起服段是复用了的。

### 关键约束（用户指正）
集群目录是 11 台**共用**的单一目录（`_restart_cluster_dirs()`），`_restart_cluster_quiet_sec()` 扫全目录取最新 mtime 天生是全局语义，**无法拆成按服务器维度**。

### 可行方案
1. **基于同一静默快照放行**：静默通过后允许 2 台同时进 `savekill`（共享同一次「目录无写入」前提），而非第二台重新等 180s
2. **缩短静默窗口**：`RESTART_CLUSTER_QUIET` 180s → 60~90s（需先评估玩家跨服传送频率）
3. **串行但压单台耗时**：优化存档回执 / 停服确认的等待

### 风险
集群目录写入多半来自玩家跨服传送；放宽并发 = 放宽「传送被截断」的保护，**安全性 vs 速度需用户拍板**。

> ✅ **已实施（2026-11-07 13:18，v6221）**：用户拍板「放行 2 台 + 静默窗口保持 180s」。
> 新增 `RESTART_PARALLEL = 2`；选台由 `_cands[0]` 单台改为按空槽位批量取（`_cands[:_free_slots]`）；
> 进入 savekill 时写日志 `enter savekill X (parallel n/2)`；`_restart_push_batch()` 显示「处理中 A,B」。
> 预期总时长 45~60 分钟 → **30~40 分钟**。
> 安全性依据：存档写各自 `Servers\<srv>\`，不碰共用集群目录；且每台停服前仍复检三重静默护栏。

## 九-B、P2-3：ASAM 界面直接启动会绕过全局重压池

### 现象
重压池（`SRVCTL_STARTQ_HEAVY_MAX = 2`）的计数来自 `_startq_heavy_count()`，只统计 `_SRVCTL_STARTQ['active']` 里 `heavy=true` 的项。
**从 ASAM（ASA Dedicated Manager）界面直接点启动**，绕过后端 ⇒ 队列里没有这条记录 ⇒ 重压池统计不到 ⇒ 可能与队列内的启动同时进入 world_load（实际并发 >2）。

### 已确认的边界
- 后端侧所有 `start` 都已强制入队（v6014：含单台启动与失败重试）
- 安全回档完成后启动、IP 重启编排起服，也都走 `_srvctl_startq_new`
- ⇒ **唯一缺口就是「绕过后端的外部操作」**

### 修法设想（未实施）
1. **兜底观测**：`_startq_worker` 每 tick 用 `_srvctl_proc_snapshot()`（已存在，转发 ASA `/server-status`，10s 缓存）比对 —— 若发现「不在 `active` 里但进程状态为 `Starting`」的服，视为外部启动，记日志并在概览行提示「外部启动 N 台」
2. **软保护**：检测到外部启动时，队列**暂缓放行**新槽位，直到该外部启动离开重压期（或超时）—— 避免 3 台同时 world_load
3. 不在前端做限制（ASAM 是独立程序，拦不住），只做检测 + 让路

### 影响文件
- `独立后端/dino_backend.py`：`_startq_worker()`、`_startq_view()`

### 验证方式
- 在 ASAM 界面手动启动一台，同时让队列里也有待起服的台，观察概览行是否提示「外部启动」且队列暂缓

## 十三、跨功能一致性全面排查（用户 2026-11-07 要求「再次全面检查」）

> 排查范围：`_srvctl_run`（手动动作执行器）/ `_srvctl_startq_new`（启动队列）/ `_restart_exec_*`（编排）/ `arkbackup`（回档）四个入口。

### 新发现的不一致（本轮排查新增）

| # | 本该一致的点 | 现状 | 后果 | 级别 |
|:--:|---|---|---|:---:|
| A | **起服前的守门**（回档中 / 服务器硬锁） | `/api/srvctl/action` **入口**有 `_ARKBK_HOLD` + `_srv_lock` 检查（约 L12670）；但 `_srvctl_startq_new()` **直接调用**的两处（编排 L9985、回档 L422）**完全不经过这两道守门** | 编排可能在回档进行中把该服起起来；回档也不会被启动队列阻断 | 🔴 高 |
| B | **任务行标识** | `_srvctl_run` 用 `'<srv>|<action>'` 作 key（不含发起人）⇒ 编排调 `_srvctl_run('ipwatch',[srv],'savekill')` 与手动 savekill **完全同一行** | P0-2 的真相：不是「额外新建」，而是编排与手动**共用同一行**；两者并发时会互相覆盖进度 | 🟡 中 |
| C | **存档/停服并发度** | 手动路径 `_srvctl_run` 用 `_SRVCTL_POOL`（max_workers=4）**并发**；编排同一动作**严格单台串行** | 同一种「存档停服」两种节奏，编排慢且行为不可预期 | 🟢 低 |
| D | 进程幂等判据 | 仅 `_srvctl_startq_new` 有（`_cfg_proc_start` 进程存在则跳过）；`kill` / `saveworld` / `savekill` 无类似「已在执行则跳过」 | 重复下发风险 | 🟢 低 |
| E | 服务器软锁 | 编排加 `restart|<srv>` soft 锁；**启动队列不加任何锁** | 锁覆盖不全，外部无法从锁表看出“该服正在队列启动” | 🟡 中 |

### 已确认一致的部分（无需改）

| 点 | 结论 |
|---|---|
| 动作执行路径 | 全部走 `_srvctl_run` → `_srvctl_one`（仅 5 个调用点，无旁路） |
| 终止前玩家护栏 | 统一在 `_srvctl_one` 内部（`_srvctl_terminal_gate`），编排与手动同源 |
| `force` 语义 | v6196 起编排不再传 `force=True`，与手动一致 |
| 重压池 | 单一 `_SRVCTL_STARTQ` + `HEAVY_MAX=2`，所有 `start` 统一入队（v6014） |
| 入队清历史 done | `_srvctl_startq_new` 已做（方案 B 的前提已具备） |
| 启动幂等 | 队列用真实进程 `_cfg_proc_start` 判定，重启后端不失效 |

### 建议修法

1. **把「起服前守门」下沉到 `_srvctl_startq_new()` 内部**（而不是只放在路由入口）——
   入队前检查：`_ARKBK_HOLD.get(srv)` 存在则拒绝；`_srv_lock` 为 hard（rollback/restore）则拒绝。
   这样编排、回档、手动三条路径自然统一，不会再有旁路。
2. 入队时给该服加 `queue` 软锁（`_srv_lock_set(srv,'queue','queue|%s'%srv,...)`），收割完成/失败时释放。
3. 任务行 key 加发起人命名空间（如 `ipwatch|savekill|Abe` vs `manual|savekill|Abe`）——
   **或**按 P0-2 方案给编排内部动作 `silent=True` 不建行，只保留编排行。
4. 并发度统一：若 P2-1 决定放开编排并发，则直接复用 `_SRVCTL_POOL` 的并发模型，避免又造一套。

## 十四、方案复核与补强（2026-11-07 03:45 二次复核）

> 对上面所有方案做批判性复核 —— 重点是「方案 B 是否真的能跑通」「还有哪些没写到的」。

### 🔴 R1：方案 B 的致命漏洞 —— 进程已存在时队列会**静默跳过**，编排将永远等

`_srvctl_startq_new()` 开头有一段幂等判据：

```python
_ts = _cfg_proc_start(_s, force=True)
if _ts:
    _skip_proc[_s] = u'进程已存在（启动于 %s）' % ...
else:
    _keep.append(_s)
servers = _keep          # ← 被跳过的服根本不进 queue/active/done
```

**后果**：编排起服时若该服进程尚未完全退出（kill 延迟、残留），`_srvctl_startq_new` 会把它跳过 ⇒ 队列里没有它 ⇒ `_restart_startq_state(srv)` **永远返回 `idle`** ⇒ 方案 B 只等 `'ok'` ⇒ 照样卡到 600s 超时。

**必须补齐的状态处理**（方案 B 不能只处理 ok）：

| `_restart_startq_state` 返回 | 编排应做的动作 |
|---|---|
| `ok` | → `done`（原方案 B 只写了这个） |
| `fail` | → **立即** `_restart_step_fail`，不必等 600s（队列已判死） |
| `run` / `queue` | 继续等（正常） |
| **`idle`** | 入队后 N 秒仍 idle ⇒ 说明被跳过或未登记 ⇒ **重新入队一次**，仍 idle 则降级为"直接查日志兜底"或判 fail |

### 🔴 R2：入队返回值未校验

`_srvctl_startq_new()` 返回 `_startq_view()`。编排应在下发后立即检查返回的 `active`/`queued` 是否包含该服；不包含就说明被跳过，**当场处理**，不要空等一个人工超时。

### 🟠 O1：编排在任务列表里其实是 **11 条独立行**，不是 1 条

`_restart_push(srv)` 每台建一行 `restart|<srv>`（label「重启（IP 切换）」）⇒ 11 台就是 11 条。
再加上各自的 `savekill` / `start` 行 ⇒ **一次编排最多 33 条任务行**。这是 P0-2「用户看到一堆多余进度条」的更完整真相。

建议：后端额外维护一条 `restart|__batch` **汇总行**（`已重启 x/11 · 当前 Abe`），单台明细行前端默认折叠。

### 🟠 O2：中止后 `fail` 标记永久残留

本轮中止后 11 台全标 `fail`、`done=[]`，`/api/ipwatch` 会一直返回这个失败态，直到下一次编排。但实际状态是：Abe 已上线、其余 10 台从未被动过 ⇒ **界面在说假话**。

建议：
- 中止时用独立状态 `aborted`（而非 `fail`），前端文案区分「已手动中止」与「真失败」
- 或提供「清除本轮记录」接口

### 🟡 O3：演练模式根本测不出 P0 类 bug

dry 分支里 `verify` 直接置 `ok`（不读日志）。这次 P0-1 正是「演练一切正常、真跑才暴露」。

建议：dry 也跑**真实判据**，只是**不据此判失败**——把「若真跑，此刻会不会通过」记进 msg/log。这样以后的演练能提前发现判据类问题。

### 🟡 O4：总超时 6 小时可能不够（修完 P0-1 后重算）

`RESTART_TOTAL_TIMEOUT = 21600`（6h）。最坏情况每台：
`saveworld 180 + savekill 300 + startq 1200 + verify 600 ≈ 2280s` ⇒ ×11 台 ≈ **7 小时 > 6h** ⇒ 整批会被总超时误杀。

实际每台 4~5 分钟，但配合 `RESTART_MAX_ATTEMPTS=2` 重试后可能逼近上限。建议 P0-1 修完实测一轮，按真实数据重设。

### 🟡 O5：`silent` 必须覆盖 `_srvctl_run` 里**三处** `_utask_put`

1. 开头登记（约 L5817，`action != 'start'` 分支）
2. savekill 进度回调 `_prog()`（约 L5830）
3. 收尾回写（约 L5868）

漏任何一处都会残留任务行 —— P0-2 的改法要明确写「三处一起跳过」。

### 🟢 O6：P2-1「同一静默快照放行」的快照会过期

放行第二台时沿用第一台的快照；若第一台存档期间集群目录又被写（玩家传送），第二台仍会放行 ⇒ 传送被截断。

建议：快照有效期 ≤60s，超时重判；或放行前复核一次 `_restart_cluster_quiet_sec()`。

### 🟢 O7：P2-3 外部启动检测应 **fail-open**

`_srvctl_proc_snapshot()` 依赖 ASA `/server-status`，失败时返回 `{}`。此时不能因为"看不到外部启动"就无限放行，也不能因此卡死队列 —— 明确 fail-open（记录"检测不可用"后照常放行）。

### 补强后的验证清单（P0-1 方案 B）

| # | 场景 | 预期 |
|:--:|---|---|
| 1 | 正常起服 | 队列判 ok → 编排 1~2 tick 内 `done` |

## 十五、终止动作全局串行闸（v6222，用户 2026-11-07 追问后新增）

> **用户质疑**：「那这么说的话 存档后终止、强制终止 也会有跨服的风险啊？」
> **结论：成立，而且比编排更严重。**

### 问题

| 路径 | 并发度 |
|---|---|
| 编排（P2-1 放开后） | 2 台 |
| **手动「存档后终止」/「强制终止」** | **4 台**（`_SRVCTL_POOL = ThreadPoolExecutor(max_workers=4)`） |

三重静默护栏（`_srvctl_terminal_gate`：L1 在线=0 / L3 集群目录 180s 无写入）只能保证「**发起那一刻**」无传送；
v6189 的终止前复检补了 40 秒存档空档，但**复检是各台独立**的 ⇒ 4 台可几乎同时通过、同时停服
⇒ 「玩家跨服传送窗口」瞬间清零。

### 已实施方案（用户拍板：存档并行 + 终止串行，间隔 5 秒）

| 项 | 内容 |
|---|---|
| 常量 | `KILL_SERIAL_GAP = 5`（秒）+ `_KILL_SERIAL = {lock: RLock, lastAt}` |
| 函数 | `_kill_serial_wait()`：取锁 -> 距上次终止不足 5s 则等待 -> 刷新 `lastAt` |
| 函数 | `_kill_serial_prepare(cfg)`：未过闸则等待并打 `_kill_serial_done` 标（防 savekill -> kill 二次等待） |
| 插入点① | `_srvctl_one` 的 `kill` 分支，**三重静默护栏检查之前** |
| 插入点② | `savekill` 的「终止前复检」**之前** |

**关键设计**：闸放在**复检之前**而非之后 —— 若先复检再等 5 秒，等待期间可能有人开始传送，复检结论会过期。
现在顺序是「排队 -> 轮到 -> 复检 -> 立即终止」。

### 覆盖面（全部经 `_srvctl_one`，一处改动全覆盖）

| 功能 | 调用链 | 过闸 |
|---|---|:---:|
| 手动强制终止 | `/api/srvctl/action` -> `_srvctl_run` -> `_srvctl_one('kill')` | ✅ |
| 手动存档后终止 | 同上（`'savekill'`） | ✅ |
| **自动重启（编排）** | `_restart_exec_savekill()` -> `_srvctl_run('ipwatch', …, 'savekill')` -> `_srvctl_one` | ✅ |
| 编排 Bob 的 kill | `_restart_exec_savekill()` -> `_srvctl_run(…, 'kill')` | ✅ |
| **安全回档停服** | `_arkbk_do_rollback()` 第 ④ 步 -> 直接 `_srvctl_one(server,'kill',…)` | ✅ |
| 任务条重试 | `lbTaskRetry` -> `/api/srvctl/action` -> 同上 | ✅ |

**不受影响**：SaveWorld + DinoData 稳定 + .ark 瘦档校验仍**并行**（写各自 `Servers\<srv>\`，安全）。

### 代价与收益

- 代价：每台终止最多多等 5 秒（编排 11 台最坏 +55s，但并行存档省下的时间远大于此）
- 收益：护栏从「发起那一刻无传送」升级为「**每次终止时刻都无传送**」
