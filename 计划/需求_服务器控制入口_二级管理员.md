## 一、背景与目标

### 1.1 用户原话
1. 在生存者浮窗加一个入口：服务器控制
2. 只有二级管理员（比系统拥有者低一级权限）有权限看到这个入口（二级管理员目前比普通玩家多的权限就只开放 服务器控制）
3. 功能是 HA 里的 服务器操作 里的所有功能
4. **迁移后，要完全脱离 HA**（新入口不依赖 HA）

### 1.2 目标
| # | 目标 | 判定 |
|---|------|------|
| G1 | 「生存者」浮窗新增「服务器控制」入口 | 二级管理员可见，其余人不可见 |
| G2 | 引入「二级管理员」新权限层级 | 拥有者可授权/撤销，缺省无此权限 |
| G3 | 覆盖「服务器操作」全部 19 项动作 + 新增 1 项（存档后终止）= **20 项** | 逐项对齐（§六） |
| G4 | **零侵入**：不改变现有权限行为 | `lbIsAdmin()` 与后端 3 处 admin 接口一行不改 |
| G5 | **零 HA 依赖** | 新入口运行时不调用任何 HA 接口/实体 |

### 1.3 明确不做
- 不做通用 RBAC 权限引擎（避免波及现有 20+ 处 `lbIsAdmin()` 调用）
- 不把任何服务端 token 下发到前端
- 不修改 HA 现有视图（`asa-server-ops` 原样保留，仅作人工兜底）

### 2.3 HA「服务器操作」的**真实实现**（读 AppDaemon 源码确认）

HA 那套 UI 只是转发壳，真正干活的是 **ASA Server Manager API**：

```
AppDaemon (asa_server_monitor_reliable.py)
  → POST {base_url}/{action}
    Authorization: Bearer <token>
    {"profileName": "<中文服务器名>", "message": "<rcon 文本>"}
```

- `base_url` = **`https://asa.whiterober.com`**（appsd.yaml 已确认）
- 端点：`/start` `/stop` `/kill` `/update` `/saveworld` `/fullbackup` `/destroy` `/rcon` `/players`
- `destroy` 超时放宽到 **600s**（其余 60s），失败重试
- AppDaemon 调用时**关闭了证书校验**（`verify_mode=CERT_NONE`）⇒ 后端对接需同样处理并标注风险

**⇒ 后端直连该 API 即可等价实现全部动作，HA 完全不参与。**

## 四、权限体系设计（零侵入）

### 4.1 数据结构（只加不改）
```json
{
  "whiterober": { "pwd": "...", "nick": "板板" },            // 系统拥有者：**不写 role**，代码自动返回 3
  "某玩家":     { "pwd": "...", "nick": "小明", "role": "admin2" },
  "普通玩家":   { "pwd": "...", "nick": "小红" }              // 无 role ⇒ 普通玩家
}
```
- `role` 缺省 ⇒ 视为 `player`（与现状完全等价）；老账号不写也照常登录
- **系统拥有者不依赖 `role` 字段**：`_role_level()` 优先判 `username == 'whiterober'` → 3（§4.4）

### 4.1.1 二级管理员初始名单（已定案）

> 用户口径：「用具体账号的方式，初始名单就是当前所有的普通用户，**新增用户不要自动加入二级管理员**」

当前 `accounts.json` 共 **9** 个账号（实测，全部无 `role` 字段）：

| 账号 | nick | 初始 role |
|---|---|---|
| `whiterober` | whiter.rober | **无需写入**（代码硬编码返回 3，见 §4.4） |
| `kanbujiandehai` | 咪 | **`admin2`** |
| `tb` | 嘎巴菜 | **`admin2`** |
| `hz` | JaronV5 | **`admin2`** |
| `athka` | 蒜头 | **`admin2`** |
| `asd` | Asdcent | **`admin2`** |
| `ali` | Ali | **`admin2`** |
| `suiyi` | 飞翔 | **`admin2`** |
| `luan` | Luan Luan | **`admin2`** |

- 落地方式：**只给 8 个普通用户批量写入** `role: "admin2"`；**`whiterober` 不写任何 role 字段**（系统拥有者靠代码判定，天然最高级）
- **新增账号不写 `role` ⇒ 自动为普通玩家**（符合"新增用户不要自动加入"）
- 本版**不做授权 UI**，留作未来扩展（§4.5 保留接口设计，不实现界面）

### 4.2 前端（只加新函数）
```js
function lbRoleLevel(){ ... }        // 3=拥有者(硬编码 whiterober) 2=二级管理员 1=普通玩家
function lbCanServerCtl(){ return lbRoleLevel() >= 2; }
```
- **`lbIsAdmin()` 一行不改**，现有 20+ 调用点零改动

### 4.3 登录响应（只加字段）
`/api/login`：`{ ok, nick }` → `{ ok, nick, role }`（追加）。老缓存无 `role` ⇒ 按 `player` 处理，无需迁移。

### 4.4 后端校验（新接口专用）
```python
def _role_level(username):
    if username == 'whiterober': return 3          # 系统拥有者：硬编码，不看 role 字段
    return 2 if (_accounts().get(username, {}).get('role') or '') == 'admin2' else 1
```
- 新接口要求 `_role_level(username) >= 2`
- **系统拥有者自动包含二级管理员全部权限**：等级 3 ≥ 2，同一判定天然满足，无需额外分支
- 拥有者不写 `role` 也不受影响（第 1 行优先命中，不读字段）
- **现有 3 处 `admin required` 保持原样**

### 4.5 授权管理（**本版不实现，仅留接口位**）

> 用户口径：「授权先不做（未来扩展）」

- 本版：**不做 UI、不做 `/api/set_role`**，初始名单一次性写入 `accounts.json`（§4.1.1）
- 未来扩展预留：入口放「系统管理」浮窗（仅 L3 可见）+ `POST /api/set_role` + `role_audit.log` 审计
- 未来若要收紧，直接改 `accounts.json` 的 `role` 字段即可，无需改代码

| 说明 | 「服务器控制功能使用，保存后即时生效，无需重启后端」 |
| 输入框 | `id="lbAsaToken"`，`type="password"`，`autocomplete="off"`，placeholder 显示当前掩码（如 `已配置 ****f12542d`；未配置显示 `未配置`） |
| 按钮 1 | `保存 Token` → `lbAsaTokenSave(this)` |
| 按钮 2 | `测试连通` → `lbAsaTokenTest(this)` |
| 消息区 | `id="lbAsaTokenMsg"` |

**行为**
1. 打开浮窗 → `lbAsaTokenLoad()`：`GET /api/server_config` → 取 `asa_token_masked` 填 placeholder（**绝不回显明文**）
2. 保存 → `POST /api/server_config {asa_token}` → 返回 `{ok, masked}` → 更新 placeholder + **清空输入框** + 提示「已保存」
3. 测试 → `POST /api/asa_test` → 后端用当前 token 调一次 `GET /server-status` → 返回 `{ok, count, ms, err}` → 显示「✅ 连通 · 11 台 · 312ms」或「❌ 401 未授权」

**安全**
- 前端**只拿到掩码**（后 6 位），token 原文永不下发
- 输入框密码型，保存后立即清空
- 保存/测试接口均仅系统拥有者可用（后端 `CFG_OWNERS` 校验）
- token 不入 git、不进前端产物、不进本计划文档

### 6.2 批量执行语义（**对齐 HA 现有实现，已读源码取证**）

HA `asa_server_monitor_reliable.py` 现有三个批量函数：

| HA 函数 | 语义 |
|---|---|
| `save_all_worlds()` | 全部服务器**并发** `asyncio.gather(*tasks)`；失败的**单独重试一轮** |
| `clear_dinos_all()` | 同样**并发** `asyncio.gather(..., return_exceptions=True)` |
| `full_save_and_kill_all()` | 先跑全图存档 → **`sleep(2)`** → 再对全部 kill |

**dino 后端照此实现（脱离 HA）**：
1. 前端提交 `servers: ['Isl','Sco','Ext']`（多选）
2. 后端对选中服务器**并发**请求 ASA API（`ThreadPoolExecutor`）
3. 失败的**自动重试 1 轮**（与 HA 一致）
4. 「存档后终止」→ 先并发 saveworld → **sleep 2s** → 再并发 kill
5. 返回 `results: [{server, ok, message, ms}]` ⇒ 前端按服务器分行渲染
6. 单服超时：`destroy` 600s，其余 60s；整体接口超时 = 单服超时 + 余量
7. 审计：`srvctl.log` 每服一行（时间/用户/服务器/动作/结果/耗时）
8. **并发限流**：`ThreadPoolExecutor(max_workers=4)` —— 11 台全选时不一次性打 11 个请求；
   原因：`destroy` 单服可占 600s，11 并发会占满线程池并拖慢后端其它接口（参考 R9）
9. **同服×同动作互斥**：内存锁 `{(server, action): ts}`，重复请求直接返回
   `{ok:false, code:'busy', message:'该服务器此操作正在执行中'}`，避免连点造成重复清理/重复终止

## 七、技术方案（后端直连 ASA API，零 HA）

### 7.1 架构
```
dino 前端  ──(username 鉴权)──▶  dino_backend  ──(Bearer token)──▶  ASA Server Manager
                                 /api/srvctl/*                        https://asa.whiterober.com
                                                                      /start /stop /kill /update
                                                                      /saveworld /fullbackup /destroy
                                                                      /rcon /players
```

### 7.2 新增后端接口
```
POST /api/srvctl/action?username=<u>     body: {"servers":["Isl","Sco"],"action":"start"}
POST /api/srvctl/rcon?username=<u>       body: {"servers":["Isl"],"message":"broadcast hi"}
GET  /api/srvctl/status?username=<u>&servers=Isl,Sco
```
统一逻辑：
1. `_role_level(username) >= 2`，否则 `401 level2 required`（**唯一鉴权入口**）
2. `servers[]` → `profileName[]`（后端内置 §2.4 映射表）；**空数组直接 400**
3. `action` → 白名单校验（仅 §六 允许值）
4. 逐个**并发**转发 `POST {asa_base}/{action}`，`{"profileName": profileName, "message": ...}`（§6.2）
5. 超时：`destroy` 600s，其余 60s；失败重试次数可配
6. **返回统一结构**（与 §6.2 一致）：
   ```json
   { "ok": true, "action": "start", "results": [
       {"server":"Isl", "profileName":"孤岛", "ok":true, "message":"...", "ms":1234, "retried":false},
       {"server":"Sco", "profileName":"焦土", "ok":false, "message":"...", "ms":60001, "retried":true}
   ] }
   ```
   顶层 `ok` = 全部成功；`results[]` 顺序与请求 `servers[]` 一致
7. **长任务策略**：`start/stop/kill/update/saveworld/rcon` **同步等待**返回（≤60s）；
   `destroy`（600s）、`fullbackup`（未知，可能更久）**改为异步 job**：立即返回 `{ok:true, jobId}`，前端轮询 `GET /api/srvctl/job?id=` 拿 `results[]`
7. 审计：`srvctl.log`（时间/用户/服务器/动作/结果/耗时）

### 7.3 配置项（token 改为**界面可配**，存 `server_config.json`）

> 存放位置已定：复用现成 `_srv_cfg_read()` / `_srv_cfg_write(doc)`（`SRV_CONFIG_FILE` = `server_config.json`）
> ⇒ **改 token 即时生效，无需重启后端**

```json
{
  "server_domain": "...",
  "asa_base": "https://asa.whiterober.com",
  "asa_token": "<仅服务器本地，永不下发>",
  "asa_timeout": 60,
  "asa_timeout_destroy": 600,
  "asa_verify_tls": false
}
```

**接口**
| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /api/server_config` | 公开读 | **仅返回** `server_domain` + `asa_token_masked`；**永不返回 `asa_token` 原文** |
| `POST /api/server_config` | 仅 owner（`CFG_OWNERS`） | 可写 `asa_token` / `asa_base`；写入后 `_srv_cfg_write()` 落盘 |
| `POST /api/asa_test` | 仅 owner | 用当前 token 调 `GET {asa_base}/server-status`，返回 `{ok, count, ms, err}` |

- **掩码规则（全局统一）**：`'****' + token[-6:]`（32 位 token ⇒ `****2542d` 样式的**后 6 位**）；未配置返回空串
- `asa_timeout*` / `verify_tls` 只由配置文件静态设定（不在界面暴露）
- `verify_tls:false` 沿用 AppDaemon 现状（对方证书链不完整）；**在风险 R2 中标注**

### 7.4 前端调用
```js
// 统一入口（多服）
lbSrvCtlCall(action, { servers: [], message: '' })   // → /api/srvctl/*?username=<dinoAuth.user>
// 例：lbSrvCtlCall('saveworld', { servers: ['Isl','Sco'] })
//     lbSrvCtlCall('rcon',      { servers: ['Isl'], message: 'broadcast hi' })
```
- 统一 loading / 禁用按钮（防连点）
- 错误中文化（可复用 `lbSrvResultZh()`）

| 后端 code / HTTP | 提示文案 |
|---|---|
| 400 `no_servers` | 请先选择服务器 |
| 400 `bad_action` | 不支持的操作 |

### 8.1 实服测试纪律（**最高优先级硬约束**）

> 用户原话：「该功能实服测试的时候只允许用 Bob 测试，严禁在没有我同意的情况下测试别的服务器」

| 服务器 | 允许的测试 |
|---|---|
| **Bob（俱乐部 / 7775）** | ✅ 全部动作均可实服测试（start/stop/kill/update/saveworld/fullbackup/destroy/rcon/存档后终止） |
| **其余 10 台**<br>Isl / Sco / Cen / Abe / Ext / Ast / Rag / Val / Los / Gen | ⛔ **任何写操作必须先获得用户逐次明确同意**；<br>未同意时**最多只能只读**（`GET /server-status` 查看状态与版本） |

**受管控的"写操作"清单**（一律算）：
`start` / `stop` / `kill` / `update` / `saveworld` / `fullbackup` / `destroy` / `rcon` / 存档后终止

**测试手段优先级**（能不进实服就不进）：
1. 前端假数据 / mock 模式
2. 后端 dry-run 开关（`asa_dry_run: true` 只打日志不真发）
3. **仅 Bob** 实服
4. 其他服 —— **必须先问用户**

**为什么是硬约束**：`kill` / `destroy` 会直接导致玩家掉线、存档丢失；对正在运营的服执行属最高等级事故。
